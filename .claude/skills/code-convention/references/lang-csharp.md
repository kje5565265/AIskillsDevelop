# C# 언어 층 (L2)

C# 코드를 쓸 때의 언어 차원 룰. **프레임워크 사정(Unity 등)은 L3가 override 한다** — 특히 §2 null 처리는 Unity에서 뒤집히므로 `framework-unity.md` 를 반드시 함께 본다.

---

## §1. 네이밍

| 대상 | 규칙 | 예 |
|---|---|---|
| 타입 (class / struct / interface / enum / record) | PascalCase | `SkillBehavior` |
| 인터페이스 | `I` 접두 + PascalCase | `IDamageable` |
| 공개 멤버 (public / protected 메서드·프로퍼티·이벤트) | PascalCase | `CurrentCooldown` |
| private / internal 필드 | `_camelCase` | `_elapsedTime` |
| `const` / `static readonly` 상수 | PascalCase | `MaxStackCount` |
| 지역 변수 · 메서드 파라미터 | camelCase | `targetCount` |
| 제네릭 타입 파라미터 | `T` 접두 | `TPayload` |
| 비동기 메서드 | `Async` 접미 | `LoadTableAsync` |

- **약어는 두 글자까지만 대문자 유지** — `UI`, `ID` 는 그대로, 세 글자 이상은 PascalCase (`Json`, `Http`, `Csv`).
- **불리언은 상태를 읽히게** — `is` / `has` / `can` / `should` 접두. `flag`, `check` 금지.
- **프로젝트가 다른 규칙을 정했으면 L4가 이긴다.** 기존 파일 안에서는 언제나 그 파일의 기존 스타일을 따른다(Part B §2).

## §2. null 처리

- **nullable 참조 타입(`?`)을 켠 프로젝트에서는 의미대로 붙인다.** `null` 이 정상 값이면 `T?`, 아니면 붙이지 않는다. 경고를 `!` 로 눌러 끄지 않는다.
- **공개 API 진입점에서 인자를 검증**한다. 내부 private 헬퍼마다 중복 검사하지 않는다.
- `?.` / `??` / `??=` 는 일반 C# 객체에 적극 사용한다.

> ⚠️ **`UnityEngine.Object` 파생 타입에는 `?.` / `??` 를 쓰지 않는다.** Unity가 `==` 를 오버로드해 "파괴된 객체"를 null로 취급하는데, null 조건 연산자는 그 오버로드를 타지 않아 **파괴된 객체를 살아있다고 판정**한다. 상세는 `framework-unity.md` §1.

## §3. 예외 vs 반환값

- **예외는 예외적 상황에만.** 정상 흐름에서 실패가 예상되면 `bool TryXxx(out T)` 또는 결과 타입을 쓴다.
- **삼키지 않는다.** `catch { }` 금지. 최소한 로그를 남기고, 복구 불가면 다시 던진다.
- `throw;` 로 다시 던진다. `throw ex;` 는 스택 트레이스를 지운다.
- **매 프레임 경로에서 예외를 흐름 제어로 쓰지 않는다** — 비용이 크다.

## §4. 비동기

- **`async void` 금지.** 예외를 잡을 수 없다. 이벤트 핸들러만 예외로 허용하고, 그 안은 try/catch 로 감싼다.
- **async 는 끝까지 전파**한다. `.Result` / `.Wait()` 로 블로킹하지 않는다 (데드락).
- **취소를 받는다.** 오래 도는 작업은 `CancellationToken` 을 파라미터로 받아 전달한다.
- 라이브러리성 코드는 `ConfigureAwait(false)`. **단 Unity 는 예외** — 메인 스레드 컨텍스트가 필요하다.

## §5. 자원 수명

- `IDisposable` 을 구현한 타입은 `using` 으로 받는다. 필드로 보관하면 소유자도 `IDisposable` 이 된다.
- **구독한 이벤트는 반드시 해제**한다. `+=` 를 쓴 지점마다 대응하는 `-=` 가 있어야 한다 (Part B §4의 Add/Remove 생명주기 검증).
- 익명 람다로 구독하면 해제할 수 없다. 해제가 필요하면 **메서드 그룹이나 보관한 델리게이트**로 구독한다.

## §6. 성능 — 할당을 의식한다

모바일·WebGL 타깃에서는 GC 스파이크가 곧 프레임 드랍이다.

- **매 프레임 호출 경로에서 할당하지 않는다** — LINQ, `foreach` 로 인한 열거자 박싱, 문자열 결합, 람다 캡처, `params` 배열.
- **LINQ 는 초기화·에디터·저빈도 경로에 한정.** 핫패스에서는 `for` 루프.
- **문자열**: 2~3개 결합은 보간(`$"..."`), 루프 안 누적은 `StringBuilder`. 로그 문자열을 조건 없이 조립하지 않는다.
- **컬렉션은 예상 용량으로 생성**한다 — `new List<T>(capacity)`.
- **`struct` 는 작고(≈16바이트 이하) 불변일 때만.** 그 외에는 `class`. 큰 struct 의 값 복사가 더 비싸다.
- **박싱 주의** — `enum` 을 `object` 로, 값 타입을 인터페이스로 받는 경로.

## §7. 가시성과 불변성

- **접근 제한자를 명시**한다. 기본값에 기대지 않는다.
- **기본은 `private`.** 필요한 만큼만 연다.
- 생성 후 안 바뀌는 필드는 `readonly`.
- 프로퍼티는 필요한 쪽만 연다 — `{ get; private set; }`.
- **공개 컬렉션을 그대로 노출하지 않는다.** `IReadOnlyList<T>` 로 내보내거나 복사본을 준다.

## §8. 주석

### 무엇을 쓰나

- **「왜」를 쓴다. 「무엇」은 코드가 말한다.** `// 카운트를 1 증가` 같은 주석은 소음이다. `// 서버가 0-based 로 주므로 보정` 이 주석이다.
- 자명하지 않은 **제약 · 전제 · 함정**을 남긴다 — 호출 순서 의존, 외부 시스템의 이상 동작, 성능상 일부러 비직관적으로 짠 부분.
- **주석이 필요할 만큼 복잡하면 먼저 이름과 구조를 고칠 수 있는지 본다** (`SKILL.md` Part A 원칙 2).

### 형식

- **언어(한국어/영어)는 L4(`project-rules.md`)에서 정한다.** 정해져 있지 않으면 **그 파일의 기존 주석 언어를 따른다.** 한 파일 안에서 섞지 않는다.
- XML 문서 주석(`///`)은 **외부에서 쓰는 공개 API** 에만 단다. 모든 private 멤버에 다는 것은 소음이다.
- **`// TODO:` 에는 제거 조건이나 시점을 함께 적는다.** 조건 없는 TODO는 영구 잔존한다.
- **임시 디버그 로그의 마커 형식과 제거 절차는 `SKILL.md` Part D 가 원본이다.** 여기서 다시 정의하지 않는다 — 언어 무관 규칙이라 층마다 두면 사본이 갈린다.

### 금지

- **주석 처리된 코드를 남기지 않는다.** 이력은 버전 관리가 갖는다. 살릴 계획이 있으면 그 이유를 주석으로 적고 코드는 지운다.
- **주석 어투 다듬기 금지** — 작업 대상이 아닌 주석을 "겸사겸사" 고치지 않는다 (`SKILL.md` Part B §2).
- **주석을 근거로 판단하지 않는다** — 주석과 실제 동작이 어긋나면 주석을 고치고, 주석 근거로 세운 계획은 폐기한다 (`SKILL.md` Part B §1).

## §9. 컬렉션 선택

| 용도 | 선택 |
|---|---|
| 크기 고정 + 순회만 | 배열 `T[]` |
| 추가 · 삭제가 있음 | `List<T>` |
| 키로 조회 | `Dictionary<K,V>` |
| 존재 여부만 확인 | `HashSet<T>` |
| 선입선출 / 후입선출 | `Queue<T>` / `Stack<T>` |

- **`List<T>` 를 `Contains` 로 반복 조회하지 않는다.** 선형 탐색이다 — `HashSet`/`Dictionary` 로 바꾼다.
- **순회 중에 컬렉션을 수정하지 않는다.** 제거가 필요하면 역순 `for` 이나 별도 목록에 모았다 처리한다.
- **반환 타입은 인터페이스로** — `IReadOnlyList<T>` / `IEnumerable<T>`. 단 매 프레임 경로에서 `IEnumerable<T>` 순회는 열거자 할당을 부를 수 있으니 구체 타입을 쓴다(§6).

## §10. 타입 설계 · 최신 문법

- **`record` 는 값 동등성이 필요한 불변 데이터**에 쓴다. 단 **Unity 직렬화 대상에는 쓰지 않는다** — 인스펙터에 노출되지 않는다.
- **`init` 접근자**로 생성 후 불변을 표현한다. 생성자 인자가 많아지는 것보다 읽기 쉽다.
- **`enum` 에는 명시적 값을 부여**한다. 순서를 바꾸거나 중간에 추가할 때 직렬화·저장된 값이 어긋난다.
- **여러 개의 `bool` 플래그로 상태를 표현하지 않는다.** 불가능한 조합이 생긴다 — `enum` 이나 상태 객체로 바꾼다.
- 패턴 매칭으로 타입 분기를 하기 전에 **Part A 원칙 1(다형성)** 을 먼저 검토한다.

## §11. 파일 · 네임스페이스 구성

- **파일 하나에 공개 타입 하나.** 파일명 = 타입명. 작은 보조 타입(전용 enum·struct)은 예외로 같은 파일에 둘 수 있다.
- **네임스페이스는 폴더 구조와 일치**시킨다.
- `using` 은 파일 상단에 모으고, **본인 수정으로 안 쓰게 된 것은 즉시 제거**한다. 무관한 위치의 미사용 `using` 은 보고만 한다 (`SKILL.md` Part B §2).
- **`partial` 은 코드 생성물과 짝을 이룰 때만** 쓴다. 긴 클래스를 나누는 용도로 쓰지 않는다 — 그건 분리 대상이라는 신호다.

## §12. 기타

- `var` 는 우변에서 타입이 명백할 때 쓴다. `var result = Process();` 처럼 타입이 안 보이면 명시한다.
- **매직 넘버 금지.** 이름 있는 상수로 뽑거나 데이터로 뺀다.
- `#region` 으로 긴 클래스를 접어 숨기지 않는다. 접어야 할 만큼 길면 **분리 대상**이다 (Part A 원칙 2).
