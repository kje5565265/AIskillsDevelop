# skill-pipeline

이 저장소에서 **스킬을 만들고 실 프로젝트로 내보내는 절차**의 단일 진실원.

> ⚠️ **이 스킬은 AI_Develop 전용이다. 실 프로젝트에 배포되지 않는다.**
> 다른 스킬들과 성격이 반대다 — 나머지는 **배포되기 위해** 만들고, 이것은 **배포하는 쪽이 쓰는 도구**다.
> 배포 대상 목록은 §5.2 에 있고, **목록에 없는 스킬은 복사하지 않는다** (§5.5).

- **§3 파이프라인** — 6단계와 각 단계가 하는 일, **⑥의 문서 동기화**
- **§4 스킬 작성 규칙** — 겹침 판정 · 이름 · `description` · 마스터 단일 진실원
- **§5 이식** — 배포 대상 · 마커 블록 · 재배포 절차
- **§6 문서 배치** — 스킬 설계·검토 문서를 어디 두고 **언제 비우나**

> **절 번호가 §3 부터 시작하는 이유** — 이 내용은 원래 저장소 진입점 문서의 §3~§6 이었다. 여러 문서가 그 번호로 인용하고 있어, **옮기면서 번호를 그대로 유지**했다. 재배열하면 참조가 전부 깨진다.

> **진입점이 원본인 것들** — 미러 수정 · 배포 범위 · 설계 판정은 **파국 방지 룰**이라 진입점 §0.2 가 원본이다. 여기서는 절차 맥락에서 다시 짚는 것이며, **문구가 어긋나면 진입점 쪽이 맞다.**

## 3. 스킬 개발 파이프라인 — 6단계

```
① 스킬 제작 → ② 미러링 → ③ 테스트 → ④ 이식 → ⑤ 이식 후 재테스트 → ⑥ 마무리
```

| # | 단계 | 하는 일 |
|---|---|---|
| **①** | **스킬 제작** | 필요 제기 → 원본 조사 → 설계 대화 → **플랜 문서** → 교차 검증 → `.claude/skills/` 에 구현 |
| **②** | **미러링** | **세 쌍을 맞춘다** — `.claude/skills/` → `.agents/skills/`, 루트 `CLAUDE.md` → `AGENTS.md`, **`templates/CLAUDE.md` → `templates/AGENTS.md`.** templates 갱신은 곁다리가 아니라 **배포 기준을 갱신하는 일**이다 (§2) |
| **③** | **테스트** | 이 저장소에서 **각 에이전트가 자기 CLI 로** 확인 (§3.4) |
| **④** | **이식** | 사용자가 지정한 프로젝트에 배포 (§5) |
| **⑤** | **이식 후 재테스트** | 그 프로젝트에서 **같은 방식으로 다시** 확인 |
| **⑥** | **마무리** | 기록 · **세 문서 동기화**(§3.5) · 커밋 |

**테스트가 두 번인 것이 핵심이다.** ③은 스킬 자체가 동작하는지, ⑤는 그 프로젝트에서 실제로 도달하는지를 본다. 층 판정·프로젝트 고유 룰은 ⑤에서만 검증된다.

**②가 ③보다 먼저인 것도 핵심이다.** 미러가 어긋난 채로 테스트하면 **Codex·Cursor 는 낡은 사본을 읽는다.** 그 상태의 통과·실패는 아무것도 증명하지 못한다. 그래서 미러링은 별도 판단이 필요한 일이 아니라 **시퀀스에 박힌 정규 단계**다 — 할지 말지 · 언제 할지를 묻지 않는다.

### 3.1 스킬 제작 (①)

| 단계 | 산출물 |
|---|---|
| 필요 제기 — 만들 스킬을 사용자가 정한다 | — |
| **원본 조사** — `Origin_AISkills` 에서 재사용할 것을 찾는다 | — |
| **설계 대화** — 쟁점을 좁히고 결정과 근거를 남긴다 | — |
| **플랜 문서 작성** | `docs/skills/<스킬명>/plan.md` |
| **교차 검증** — Claude·Codex **양쪽**에 검토받고 답을 대조한다 | `docs/skills/<스킬명>/review.md` |
| **구현** — `.claude/skills/` 에 만들고 `.agents/skills/` 로 미러 | 스킬 |

원본 조사의 위치는 `Origin_AISkills\OriginProject\원본 .claude\` 다 (별도 개인 저장소). 사용자가 이전 개인 프로젝트(UE5)에서 실전 검증한 자산이며, 사고 기록과 커밋 해시가 박혀 있어 신뢰도가 높다. 다만 **UE5 + Perforce 전제**라 Unity + Git 으로 번역해야 한다. 무엇을 가져오고 무엇을 버릴지는 플랜 문서에 근거와 함께 적는다.

> `Origin_AISkills` 의 `CascaduerRND` · `KimodoRND` 는 **R&D 폴더이며 참조하지 않는다.** 그쪽 스킬은 외부 스킬팩 유래다.

**설계 대화와 플랜 문서가 이 파이프라인의 본체다.** 설계 결정은 대화 중에 여러 번 뒤집히므로, 근거를 남기지 않으면 다음 세션이 같은 논의를 반복한다. 플랜 문서에는 **결정 이력 표**(무엇을 왜 그렇게 정했는가)와 **미결정 항목**을 반드시 둔다.

### 3.2 교차 검증은 생략하지 않는다 (①)

**모든 스킬은 Claude 와 Codex 양쪽에 검토받고 답을 대조한다.**

- **독립적으로 받는다.** 상대 답을 보여준 뒤 물으면 그쪽에 끌려간다. 각자 자기 칸만 채우게 한다
- **갈린 지점이 본체다.** 일치 항목은 한 줄로 넘기고 불일치에 시간을 쓴다
- **양쪽이 일치해도 검증된 것이 아니다.** 둘은 같은 브리핑을 읽으므로 **브리핑이 틀렸으면 둘 다 틀린다**
- 받은 답은 **고치지 않는다.** 이름·경로가 나중에 바뀌면 해당 회차 절 머리에 스냅샷 경고만 붙인다
- 검토자는 맥락이 0이다. **저장소가 뭐 하는 곳인지부터** 브리핑에 넣는다

**고정 질문 4개 — 매번 묻는다.** 스킬 고유 질문은 그 뒤에 붙인다.

| | 묻는 것 |
|---|---|
| **F1** | **기존 스킬과 2중 조건이 생기는가** — 같은 상황에서 다른 지시를 하는 곳. 겹치면 흡수/포인터/분리 중 어느 판정인지도 |
| **F2** | **이 설계가 당신에게 실제로 도달하는가** — 가벼운 작업에서도 지시를 따르겠는가, 건너뛰겠는가. 건너뛴다면 어떤 문구였다면 따랐겠는가 |
| **F3** | **always-on 파국 방지 룰이 적절한가** — 더 남겨야 하나, 과한가, 중복이 drift 를 만드는가 |
| **F4** | **실제로 돌렸을 때 깨질 지점** — 특히 Windows + Git Bash + PowerShell 혼재 |

**문서 골격은 기존 `review.md` 를 복사해 쓴다.** 빈 양식 파일을 따로 두지 않는다 — 실제 사례가 더 정확하고, 규칙이 두 곳에 있으면 어긋난다.

브리핑 끝에 **재론 불필요**(이미 결정된 것)와 **범위 밖**(이식 제안 금지 · 지금은 설계 단계이니 `SKILL.md` 작성 금지)을 명시한다. 안 적으면 검토자가 바로 구현하러 간다.

#### 무엇으로 띄우나 — 검증은 서브에이전트, 테스트는 CLI ★

**교차 검증(②)은 서브에이전트로, 테스트(③·⑤)는 CLI 로 돌린다.** 둘은 대체 관계가 아니다.

| | 교차 검증 (§3.2) | 테스트 (§3.4) |
|---|---|---|
| 방식 | **서브에이전트** (읽기 전용 에이전트 사용) | **CLI 헤드리스 고정** |
| 보는 것 | **설계에 구멍이 있는가** | **실제 도구에서 스킬이 뜨는가** |

**테스트를 서브에이전트로 대체할 수 없다.** §3.4 가 요구하는 것은 *"테스트인 줄 모르는 **새 헤드리스 세션**이 실제로 어떻게 행동하는지"* 인데, **서브에이전트는 부모 세션 안의 별도 컨텍스트일 뿐 사용자가 도구를 새로 켠 상황이 아니다.** 시스템 프롬프트와 스킬 로드 경로가 달라, 정작 보려는 그 동작을 재현하지 못한다.

**반대로 교차 검증은 CLI 일 필요가 없다.** 격리 수준이 사실상 같고(양쪽 다 이쪽 대화를 보지 않는다), 스크립트와 출력 파싱이 없어 왕복이 준다.

**다만 검증도 CLI 로 돌려야 하는 경우가 있다.**

| 상황 | 왜 |
|---|---|
| **한도가 빡빡할 때** | 거부·중단된 응답을 **결과로 세는 것**을 막아야 한다. CLI 는 최종 객체의 `subtype` · `is_error` · 턴 수로 판정할 수 있지만, **서브에이전트는 잘린 보고서와 완결된 보고서를 구분할 신호가 없다** (§3.4 전제 ④와 같은 문제) |
| **답변이 아주 클 때** | 서브에이전트 결과는 **부모 컨텍스트에 그대로 들어와 남은 턴 전부에 다시 실린다.** CLI 는 파일로 남아 필요한 만큼만 읽는다 |

**회차끼리 비교할 때는 같은 방식으로 받는다.** 한 스킬 안에서 1회차를 CLI 로 받았으면 그 스킬의 다음 회차도 CLI 다. 방식을 섞으면 답이 갈렸을 때 **설계 때문인지 방식 때문인지** 가릴 수 없다.

### 3.3 진입점은 반드시 양쪽 — 그리고 바이트 동일 (②)

| 파일 | 누가 읽나 |
|---|---|
| `CLAUDE.md` | Claude Code |
| `AGENTS.md` | **Codex · Cursor** |

`CLAUDE.md` 만 만들면 **Codex 와 Cursor 는 아무 지시도 못 받는다.** 그래서 **두 파일을 바이트 동일한 미러로 둔다.**

**포인터 방식을 버렸다.** 이전에는 `CLAUDE.md` 가 단일 출처이고 `AGENTS.md` 는 *"먼저 `CLAUDE.md` 를 읽어라"* 라는 다리 + 최소 안전망이었다. **그 다리를 건널지가 모델 재량**이라 규칙 전달이 보장되지 않는다. §1.3 의 판정을 그대로 적용하면, 도구가 보장하는 것은 `AGENTS.md` 가 컨텍스트에 들어가는 것까지다 — **그러면 규칙 전문이 거기 있어야 한다.**

**미러 규칙**

- **두 파일은 바이트 동일하다.** H1 을 포함해 **의도적 차이를 하나도 두지 않는다** — 차이가 하나라도 있으면 "이 차이는 정당한가"를 매번 판정해야 하고 해시 대조가 죽는다
- 그래서 **H1 은 파일명이 아니라 저장소명**을 쓴다. `# CLAUDE.md — ...` 를 `AGENTS.md` 에 넣으면 거짓이 된다
- **수정은 `CLAUDE.md` 에서만 하고 `AGENTS.md` 로 복사한다.** `.claude/skills/` → `.agents/skills/` 와 같은 방향이다 (§4.3)
- **두 파일의 diff 가 있으면 실패로 본다.** 스킬 미러와 동일한 판정이다
- **문서 안에서 자기 파일을 가리키지 않는다** — *"`CLAUDE.md` 를 읽어라"* 같은 문장은 미러에서 자기 참조가 되어 무의미해진다

`AGENTS.md` 는 **가장 중요한 것을 문서 앞쪽에** 둔다. Codex 는 `AGENTS.md` 에 크기 제한이 있어 뒤로 밀리면 잘릴 수 있다. 미러이므로 **`CLAUDE.md` 의 절 순서가 곧 잘림 우선순위**다.

**라우팅 표에는 실제로 존재하는 스킬만 적는다.** 만들 예정인 스킬을 미리 적으면 에이전트가 없는 파일을 읽으러 간다. 반면 **안전망 룰**(금지 조항)은 스킬 존재와 무관하게 그 자체로 유효하므로 미리 넣어도 된다.

### 3.4 테스트 — 각자 자기 CLI 로 (③·⑤)

**Claude·Codex 양쪽 CLI 를 헤드리스로 띄워 검증한다.**

> **누가 띄우는지는 상관없다. 어느 에이전트든 두 CLI 를 다 부를 수 있다.** `claude.exe` 와 `codex.exe` 는 그냥 실행 파일이고, 셸에서 부르면 된다. 정해진 것은 **테스트 대상 도구가 자기 CLI 여야 한다**는 것뿐이다 — Codex 에서 스킬이 뜨는지는 `codex.exe` 로만 알 수 있다.
>
> **특히 Codex 쪽을 빠뜨리면 안 되는 이유가 있다** — Claude 파서는 관대하고 **Codex 는 엄격해서, Claude 에서만 테스트하면 Codex 전용 실패를 통째로 놓친다** (전제 ⓪-1).

> **여기서 CLI 는 선택이 아니라 고정이다.** 서브에이전트로 대체하지 않는다 — 이유는 §3.2 「무엇으로 띄우나」.

| 에이전트 | CLI |
|---|---|
| Claude | `%USERPROFILE%\.vscode\extensions\anthropic.claude-code-<버전>-win32-x64\resources\native-binary\claude.exe` |
| Codex | `%USERPROFILE%\.vscode\extensions\openai.chatgpt-<버전>-win32-x64\bin\windows-x86_64\codex.exe` |

**둘 다 PATH 에 없다.** VS Code 확장 안의 바이너리를 직접 호출한다. **확장이 여러 버전 깔려 있으면 최신 것을 쓴다.**

```powershell
# Claude — 쓰기·실행 도구를 막는다. 결과 판정에 stream-json 이 필요하다 (전제 ④)
& $claude -p "<프롬프트>" --output-format stream-json --verbose `
          --disallowed-tools Bash PowerShell Edit Write NotebookEdit

# Codex — 읽기 전용 샌드박스가 쓰기를 막는다
& $codex exec --sandbox read-only "<프롬프트>"
```

**막는 방식이 다르다.** Claude 는 **도구를 빼서**, Codex 는 **샌드박스로** 막는다. Codex 는 도구가 붙어 있고 실행만 거부되므로, *"고쳐줘"* 류 프롬프트에서 **실제로 수정을 시도했다가 차단당하는 로그**가 남는다 — 그 로그가 **스킬이 어디까지 도달했는지의 증거**가 된다.

> **자기 세션에서 자문자답하지 않는다.** *"저는 이 스킬을 로드합니다"* 는 증거가 아니다. **테스트인 줄 모르는 새 헤드리스 세션**이 실제로 어떻게 행동하는지만 증거가 된다. 작업한 세션은 이미 맥락을 알고 있어 더더욱 안 된다.

#### 돌리기 전에 — 전제 여섯

**⓪-1 `SKILL.md` 의 YAML frontmatter 가 유효한지 파서로 확인한다.** ★★ **깨져 있으면 그 스킬은 아예 안 뜨고, 테스트 전체가 무의미해진다.**

**Claude Code 의 파서는 관대하고 Codex 는 엄격하다.** 그래서 **Claude 에서 잘 뜨는 스킬이 Codex 에서는 통째로 안 뜰 수 있고, 그 상태로 몇 주가 지나간다.**

| 깨뜨리는 것 | |
|---|---|
| **`description` 값이 백틱으로 시작** | 백틱은 YAML 예약 문자라 plain scalar 를 시작할 수 없다 |
| 값 **일부만** 따옴표로 감싸기 | 따옴표 밖에 콜론·`#` 이 남으면 키로 해석된다 |
| 값 안의 `: `(콜론+공백) | 매핑으로 파싱된다 |

> **해법은 하나 — 값 전체를 작은따옴표로 감싼다.** 우리 `description` 에는 `"큰따옴표"` 가 자주 들어가므로 작은따옴표가 안전하다.

```bash
python -c "import io,yaml; print(yaml.safe_load(io.open('<경로>',encoding='utf-8').read().split('---')[1]))"
```

**두 경로 모두 검사한다** (`.claude/skills/` · `.agents/skills/`).

> **실측 (2026-08-24)** — `git-procedure` 7회차에서 Codex 로더가 `invalid YAML: did not find expected key` 로 스킬을 못 읽었다. `description` 일부만 따옴표로 감싼 문법 오류였다.
>
> **재발 (2026-09-09)** — `work-log` 개발 중 전 스킬을 검사해보니 **`document-convention` 이 같은 이유로 깨져 있었다.** `description` 이 백틱으로 시작해 **Codex 에서는 로드된 적이 없을 가능성이 있고, 배포된 세 프로젝트에 그대로 나가 있었다.** Claude 에서는 정상 로드돼 **누구도 눈치채지 못했다.**
>
> **한 번 당하고도 재발했으므로 절차에 박는다.** 눈으로 보면 못 잡는다 — 파서로 돌린다.

**⓪-2 테스트 스크립트를 UTF-8 BOM 있음으로 저장한다.** ★ 프롬프트에 한글이 들어가는데, **PowerShell 5.1 은 BOM 없는 `.ps1` 을 시스템 ANSI 로 파싱한다.** 그러면 문자열 안의 한글이 깨지면서 **따옴표 짝이 무너져 파서 에러로 죽는다** — 테스트가 한 건도 안 돌아간다.

> 훅 파일에 같은 이유로 BOM 을 강제하고 있는데(`.claude/hooks/*.ps1` 머리 주석), **테스트 스크립트는 그 규칙 바깥에 있어 매번 다시 밟는다.** 저장소 문서는 BOM 없음이 규칙이므로, **`.ps1` 만 예외**라는 것을 기억해야 한다.
>
> **실측 (2026-09-09)** — `work-log` ③ 테스트 첫 시도가 이 이유로 통째로 실패했다. 에러가 파서 단계에서 나서 *"테스트가 실패했다"* 가 아니라 *"스크립트가 안 돌았다"* 였고, 다행히 구분이 명확했다.

**① 실행·쓰기 도구를 막고 띄운다.** 테스트 프롬프트는 커밋·수정을 시키는 문장이라, 막지 않으면 **테스트가 남의 저장소를 실제로 바꾼다.** 막아도 스킬 로드는 그대로 관측된다. 층 도달까지 봐야 해서 실제 편집이 필요하면 **계획 모드**로 돌린다.

**② 워크스페이스 신뢰가 켜져 있어야 한다.** 꺼져 있으면 그 저장소의 `.claude/settings.json` 이 통째로 무시된다 — 권한뿐 아니라 **훅도 안 돈다.** 경고 문구가 권한만 언급해서 훅이 죽은 것을 놓치기 쉽다. `~/.claude.json` 의 해당 프로젝트 항목에서 확인하며, **대소문자만 다른 중복 키가 생길 수 있고 CLI 는 대문자 경로 쪽을 본다.**

**③ 훅 주입은 에이전트 응답으로 판정할 수 없다.** 주입된 문구는 대화 기록에 실리지 않으므로 **안 보인다고 안 돈 것이 아니다.** 실행 로그를 파일로 받아 훅 실행 줄을 확인한다. 스크립트 자체는 표준 입력에 프롬프트를 물려 따로 확인할 수 있다.

**④ 한도에 걸린 응답을 결과로 세지 않는다.** ★ 사용량 한도로 **거부된 요청은 「스킬이 안 떴다」와 겉보기가 똑같다.** 응답만 보면 통과로 오판한다. 최종 결과 객체의 `subtype` · `is_error` · 턴 수로 판정하고, 한도로 끊긴 것이면 **결과가 아니라 미실시로 처리해 다시 돌린다.** 중간에 잘린 세션도 마찬가지다 — 스킬은 떴는데 응답이 끊겨 절차 준수 여부를 볼 수 없다.

> **①·③·④ 는 같은 실패 유형이다** — **없는 것과 못 한 것을 구분하지 못하는 것.** 테스트는 *"무엇이 일어났나"* 뿐 아니라 *"관측이 유효했나"* 를 함께 봐야 한다.

#### 고정 테스트 4항목 — 매번 돌린다

| # | 무엇을 보나 | 통과 기준 |
|---|---|---|
| **T1** | **뜨는가** | 그 스킬의 정면 질문에 로드 + 내용 정확 |
| **T2** | **가벼운 작업에도 뜨는가** | 한 줄·한 글자 수정에서도 로드. **흔한 실패** |
| **T3** | **레퍼런스까지 도달하는가** | 스킬만 읽고 끝나지 않고 **하위 층(L4·프로젝트 고유 룰)** 까지 |
| **T4** | **여러 스킬이 걸리면 다 뜨는가** | 대상이 섞인 작업에서 **전부** 로드 |

**T3 도 흔한 실패다** — 감지는 되는데 레퍼런스를 안 읽으면 실전에서 무용지물이다. 스킬 고유 질문은 이 4개 뒤에 붙인다.

#### 결과 기록

**개발 이력 문서**로 남긴다 (`docs/develop-history/`). 미해결·미검증 항목은 `## 보류` 표에 **재개 조건과 함께** 넣는다 — 그래야 다음 세션이 집어서 이어간다.

**한쪽만 확인할 수 있는 것은 그쪽에 넘긴다.** 예를 들어 *"무엇이 스킬 목록 예산을 쓰고 있는가"* 는 그 에이전트의 자기 환경에서만 보인다.

### 3.5 ⑥ 마무리 — 세 문서를 `SKILL.md` 에 맞춘다 ★

**기준은 언제나 `SKILL.md` 다.** 에이전트가 런타임에 읽는 것은 그것 하나이고, `plan.md` · `review.md` 는 **그것을 만들기 위한 부속**이다. 어긋나면 부속을 고친다.

**⑥에서 하는 네 가지**

1. plan 의 결정과 **SKILL 의 현재 내용이 어긋나는 곳**을 찾는다
2. 어긋나면 **plan 을 고친다** — 단 덮어쓰지 않고 **정정 표기**로
3. 이번 회차의 review 판정을 **plan 결정 이력으로 흡수**한다
4. 흡수가 끝나면 **review 를 비운다** (§6.1)

#### 정정은 덮어쓰기가 아니다

plan 에 *"X 로 정했다"* 가 있고 SKILL 이 Y 면, **X 를 Y 로 바꿔 쓰지 않는다.** 「X → Y 로 뒤집음, 근거」로 남긴다.

**뒤집혔다는 사실 자체가 정보다.** 지우면 다음 사람이 X 를 다시 제안하고, 같은 논의를 처음부터 반복한다.

#### plan 을 `SKILL.md` 의 요약본으로 만들지 않는다 ★★

**같은 내용이 두 곳에 있으면 다시 어긋난다. 그게 지금 고치려는 그 문제다.**

| plan 에 남긴다 | plan 에서 버린다 |
|---|---|
| **왜 그렇게 정했나** | 무엇을 하는가 → `SKILL.md` |
| **버린 대안과 그 이유** | 절차 · 형식 · 예시 → `SKILL.md` |
| **뒤집힌 결정과 뒤집은 근거** | 담당 범위 표 → `SKILL.md` 머리 |
| **미결정과 판단 시점** | 절 구조 → `SKILL.md` |

> **절 번호가 어긋나는 사고의 원인이 정확히 이것이다.** plan 이 SKILL 과 **같은 절 구조**를 가지면 **어긋날 번호가 생긴다.** 결정 이력만 있으면 어긋날 것 자체가 없다.
>
> **실측 (2026-08-25)** — `git-procedure` 에서 **7쌍**이 어긋나 있었고, 그 구멍에서 실제로 오정정이 한 번 났다.

#### 「왜」는 `SKILL.md` 에서 복구되지 않는다

**동기화를 「plan 을 비우는 것」으로 오해하지 않는다.**

SKILL 은 *"에셋은 줄 판정을 하지 않는다"* 라고만 쓴다. *"dirty 기준으로 막을까 검토했는데 실측해보니 매일 아침이 잠기더라"* 는 plan 에만 있다. **실측이 근거인 결정은 결과만 보고 되짚을 수 없다.**

그리고 이것이 진입점 §0.2 **설계 판정** 룰이 막는 사고다 — *"문서에 근거가 안 보인다고 「룰이 틀렸다」로 결론내지 않는다."* **근거가 안 남으면 그 판정이 매번 반복된다.**

## 4. 스킬 작성 규칙

### 4.1 한 번에 하나씩 — 기존 스킬과 충돌하지 않아야 한다

**한 번에 한 스킬씩 만든다.** 그리고 만들기 전에 **기존 스킬 전부를 훑어 같은 대상을 다루는 곳을 찾는다.**

**절대 금지 — 2중 조건.** 같은 상황에서 두 스킬이 다른 지시를 하면 에이전트는 어느 쪽을 따를지 모른다. **"다른 스킬에서는 맞는데 이 스킬에서는 틀리다"는 답이 나오는 순간 룰 전체의 신뢰가 무너진다.**

겹침을 발견하면 **셋 중 하나로 귀결**한다.

| 판정 | 처리 |
|---|---|
| **흡수** | 새 스킬이 가져가고 **기존에서 제거한다** |
| **포인터** | 한쪽이 원본, 다른 쪽은 **가리키기만** 한다 |
| **분리** | 겹쳐 보였지만 **대상이 실은 다르다** — 경계를 문서에 명시 |

**검증** — 같은 질문 문장을 두 스킬 각각에 물어 **답이 갈리지 않는지** 확인한다. 갈리면 아직 안 끝났다.

> 겹침을 **없애는 것이 목표가 아니다.** 겹쳐도 되지만 **어느 쪽이 원본인지 한 곳에 적혀 있어야** 한다.

판정 결과는 그 스킬의 `plan.md` **담당 범위** 절에 남긴다. 나중에 같은 논의가 반복되지 않게 하기 위함이다.

### 4.2 이름은 눈으로 보고 알 수 있어야 한다

이름만 보고 **무엇을 담당하는 스킬인지 즉시 구분**되어야 한다. 이유가 둘이다.

1. **가독성** — 라우팅 표에 여러 스킬이 늘어서면, 이름이 모호한 것 하나가 표 전체를 읽기 어렵게 만든다
2. **트리거 매칭** — 스킬 발동은 모델이 `description` 을 보고 판단한다. **사람들이 실제로 쓰는 단어**와 매칭돼야 뜬다

> `code-architecture-rules` → **`code-convention`** 개명이 이 이유였다. 팀은 "코드 컨벤션"이라고 부르지 "코드 아키텍처 룰"이라고 하지 않는다.

**판정법** — 이름을 라우팅 표에 넣어보고, **담당 범위가 다 연상되는지** 본다. 일부만 연상되면 틀린 이름이다.

| | |
|---|---|
| ❌ `dev-log` | 개발 이력만 연상됨. 실제로는 문서 위치·링크·계획 형식까지 담당 |
| ✅ `document-convention` | `code-convention` 과 짝을 이뤄 역할이 즉시 갈린다 |

접미는 성격을 드러낸다 — **`-convention`**(무엇을 지키나) · **`-procedure`**(어떤 순서로 하나) · **`-routine`**(언제 무엇을 하나).

### 4.4 `description` 은 짧게 — 목록 예산은 공유다

세션 시작 시 컨텍스트에 들어가는 것은 **스킬 이름 + `description` 목록**뿐이다. `SKILL.md` 본문은 **선택된 뒤에** 로드된다. 즉 **`description` 이 발동을 좌우하는 유일한 근거**다.

그 목록에는 **전체 스킬이 나눠 쓰는 예산**이 있다. Codex 기준 **컨텍스트 윈도우의 2%, 모르면 8,000자**이며, 넘치면 이렇게 처리된다.

| 단계 | 처리 |
|---|---|
| 1 | **`description` 을 줄인다** — 뒤가 잘린다 |
| 2 | **스킬을 목록에서 아예 뺀다** + 경고 |

**2단계가 치명적이다.** 목록에 없으면 뜰 방법이 없다.

**잘리는 것은 항상 뒤다. 그래서 순서가 길이보다 중요하다.**

| 순서 | 넣는 것 |
|---|---|
| **1** | **대상 + 트리거 키워드** — 잘리면 안 되는 것을 첫 문장에 |
| 2 | 분량이 기준이 아니라는 사실 한 조각 |
| 3 | 부가 트리거 |
| **4** | 역할 설명 — **잘려도 무해한 것을 맨 뒤에** |

**뺄 것** — 로드한 뒤 따를 규칙(본문에 있다) · 그 판단의 근거 설명 · 유사어 중복(`"코드 컨벤션"` 이 `"코딩 컨벤션"` 을 잡는다).

목표는 **250자 안팎**이다. 우리 첫 두 스킬은 450여 자로 시작해 절반으로 줄였다.

> 활성 스킬 목록 총량은 **대부분 우리 통제 밖**(사용자가 설치한 스킬팩 · 플러그인)이라 예산을 넘는 일이 실제로 있고, 그때 **끝부분이 잘린다.** 그래서 트리거 키워드를 첫 문장에 둔다. 측정 수치는 개발 이력 DH:skill-cli-test · DH:entrypoint-diet 에 있다.
>
> 사용자가 *"리팩터 좀 해줘"* 라고 할 때는 **아직 파일을 안 건드린 상태**다. 그 순간을 잡으려면 키워드가 살아 있어야 한다. 파일 기반 트리거만으로는 계획 단계를 놓친다.
>
> **근본 해결은 예산을 크게 쓰는 스킬을 끄는 것**이며 우리 통제 밖이다. **줄여야 할 쪽은 우리가 아니지만**, 우리가 할 수 있는 것은 **짧게 유지하고, 살아야 할 것을 앞에 두는 것**이다.

### 4.3 마스터가 단일 진실원이다

**수정은 `.claude/skills/` 에서만 한다.** 나머지는 전부 복사본이다.

- **공용 층**(`SKILL.md` · `lang-*.md` · `framework-*.md` · `platform-*.md` · `_detection.md`)은 **전 프로젝트 · 전 경로 바이트 동일**해야 한다
- 프로젝트마다 다른 것은 `references/project-rules.md` **하나뿐**이다
- 프로젝트 사본에서 공용 층을 고치지 않는다. **마스터를 고치고 재배포**한다 (§5.3)

**`.agents/skills/` 는 변형본이 아니라 복사본이다.** Codex 를 덮으려면 필요하지만(§1.2), 갈라 쓰기 시작하면 단일 진실원이 깨진다.

- Codex 용으로 내용을 **갈라 쓰지 않는다**
- `SKILL.md` 안에 `.claude/skills/...` 같은 **호스트별 경로를 박지 않는다.** `references/...` 상대 경로만 쓰면 어느 쪽에 놓아도 동작한다
- 두 폴더의 diff 가 있으면 **실패로 본다**

## 5. 이식

### 5.1 개발이 먼저다 — 이식 이야기를 먼저 꺼내지 않는다

**스킬을 완성하기 전에는 프로젝트 이식·배포를 제안하지 않는다.** 착수 시점은 사용자가 정한다.

- "이제 Project_A 에 이식할까요?" · "Project_B 로 리허설할까요?" 같은 제안 금지
- 설계 판단이 필요할 때 이식을 **가정**하고 묻지 않는다. 지금 만드는 것은 **AI_Develop 안에서 먼저 완성**하고, 이식은 그 뒤의 별개 작업이다
- 특정 프로젝트의 기존 구조(폴더 관례·문서 배치 등)에 맞추려고 설계를 굽히지 않는다. **마스터의 규약이 먼저이고, 프로젝트가 거기에 맞춘다**

**「제안」뿐 아니라 「확인」도 금지다.** *"Project_A 재배포까지 할까요?"* 처럼 **적용 범위를 선택지로 내미는 질문도 하지 않는다.** 선택지로 냈다는 것 자체가 지금 그것을 해도 되는 시점처럼 보이게 만든다.

- 변경이 배포 대상에 걸리는 것을 발견하면, **AI_Develop 안의 작업을 전부 끝낸 뒤 "이 변경은 배포 시 함께 나간다"고 한 줄 알리고 멈춘다.** 되물어 답을 받아내려 하지 않는다
- 기본 범위는 **언제나 AI_Develop 안**이다. 물어보지 않아도 정해져 있다
- **배포 착수는 사용자가 통보한다.** 그 말이 나오기 전까지 실 프로젝트(§5.2 의 `Projects\`)는 읽기만 한다

> 프로젝트 문서들이 지금 중구난방인 것은 알려진 상태이며, **이식 시점에 성격별로 재폴더링**한다. 그때 다룰 문제를 지금 앞당기지 않는다.

### 5.2 배포 대상 — 스킬과 프로젝트

**배포되는 스킬** ★

| 스킬 | 배포 |
|---|---|
| `code-convention` · `document-convention` · `git-procedure` · `session-routine` · **`work-log`** | **나간다** |
| **`skill-pipeline`** | **안 나간다** — AI_Develop 전용. 배포하는 쪽이 쓰는 도구다 |

> **목록에 없는 스킬은 복사하지 않는다.** 그리고 **스킬 폴더를 통째로 복사하지 않는다** — 배포할 스킬을 **이름으로 지정**해 복사한다. `git add -A` 를 금지하는 것과 같은 이유다. 통째로 복사하면 **자체 스킬이 딸려 나간다.**

**배포 대상 프로젝트**

| 프로젝트 | 스택 | 이식 상태 |
|---|---|---|
| _(배포할 때 행을 추가한다)_ | | ⬜ 미착수 |

> **이 표는 조직마다 다르다.** 스킬 원본 저장소에는 비워 두고, 실제로 배포하는 조직의 작업 사본에서 채운다.

각 프로젝트는 **별도 저장소**이며 이 저장소와 **서로 다른 트리**다. 로컬에서는 공통 상위 폴더 아래에 나란히 둔다.

```
<작업 루트>\
├─ AI_Develop\        ← 이 저장소
└─ Projects\
   ├─ Project_A\
   └─ Project_B\
```

| 작업 | 세션 여는 위치 |
|---|---|
| 스킬 개발 · 문서 작성 | `<작업 루트>\AI_Develop` |
| **프로젝트 이식** | **`<작업 루트>`** (양쪽이 하위에 있음) 또는 `--add-dir` |

### 5.3 진입점의 스킬 절은 마커로 감싼다

배포된 프로젝트의 `CLAUDE.md` · `AGENTS.md` 는 **우리 것과 프로젝트 고유 내용이 한 파일에 섞여 있다.** 재배포 때마다 "어느 절이 우리 것인가"를 손으로 판정하면 매번 실수 위험이 생긴다.

**블록이 성립하는 근거는 소유 규칙이다.** 스킬은 이 저장소에서만 만들고 **우리만 수정한다.** 프로젝트 쪽에서 스킬 규칙을 고칠 일이 없으므로, 그 구간은 통째로 우리 것이라고 선언할 수 있다. 그래야 Claude·Codex 가 여러 프로젝트에 수정사항을 내릴 때 **무엇을 덮어도 되는지 판단할 필요가 없어진다.**

**그래서 우리가 관리하는 구간을 마커로 감싼다.**

```markdown
<!-- AI-SKILLS:START — AI_Develop 에서 배포된다. 이 블록 안을 직접 고치지 말 것 -->

(스킬 라우팅 · 경로 규칙 · 판단 기준 · 안전망)

<!-- AI-SKILLS:END -->
```

- **블록의 원본은 `templates/` 다.** 재배포 때 조립하지 않고 거기서 그대로 가져온다 (§5.5 ③·⑤)
- **재배포는 블록 통째 교체**다. 절을 찾아 고치지 않는다
- **블록 밖은 프로젝트 소유다.** 절대 건드리지 않는다
- **블록 안은 우리 소유다.** 프로젝트가 여기 고유 내용을 넣으면 다음 재배포에서 날아간다
- 마커는 **HTML 주석**이다. 헤딩으로 하면 목차에 나타나 문서 구조를 오염시킨다
- **마커가 없거나 짝이 안 맞으면 배포 실패로 본다.** 통째 교체의 전제가 무너지기 때문이다

#### 배포 대상에서는 「블록만」 동일하다 ★★

**§3.3 의 「진입점 두 파일은 바이트 동일」은 이 저장소 규칙이지 배포 대상 규칙이 아니다.**

| | 두 진입점의 관계 | 왜 |
|---|---|---|
| **AI_Develop** | **파일 전체가 바이트 동일** | 두 파일 **전체가 우리 소유**다. 차이가 하나라도 있으면 *"이 차이는 정당한가"* 를 매번 판정해야 한다 |
| **`templates/`** | **파일 전체가 바이트 동일** | 배포 기준이므로 같은 이유 |
| **배포 대상 프로젝트** | **`AI-SKILLS` 블록만 동일** | 블록 밖은 **각 도구의 사용 설명서**다. 서로 달라도 정상이다 |

**배포된 프로젝트에서 두 파일이 다른 것은 사고가 아니다.** 그 프로젝트는 Claude 와 Codex 에게 **다른 일을 시킨다** — 예컨대 Claude 는 UI 가이드와 diff 검토, Codex 는 엔진 코드와 에디터 툴. **시키는 일이 다르면 규칙도 다른 것이 맞다.**

- **블록만 교체한다. 두 파일 각각에서.** `CLAUDE.md` 를 `AGENTS.md` 로 통째 복사하지 않는다
- **해시 대조도 블록만 본다.** 파일 전체를 대조하면 **정상 상태를 배포 사고로 보고하게 된다**
- 블록 밖이 어긋나 보여도 **정리하지 않고, 지적하지도 않는다.** 우리 소관이 아니다

> **왜 이 규칙이 필요한가** — 이전 절차는 *"블록 교체 뒤 `CLAUDE.md` 를 `AGENTS.md` 로 복사한다"* 였다. 그러면 **`AGENTS.md` 에만 있던 프로젝트 규칙이 우리 배포 때문에 사라진다.** 같은 절에 *"블록 밖은 프로젝트 소유다. 절대 건드리지 않는다"* 가 있는데도 그랬다 — **두 문장이 정면으로 충돌했고, 블록 밖이 동일할 때만 둘 다 성립했다.**
>
> **실측 (2026-09-09)** — 한 배포 프로젝트의 상태를 보니 `CLAUDE.md` 에는 출시 계획과 아키텍처 원칙이, `AGENTS.md` 에는 git 원격 SSH 주의와 UI/UX 역할 분담이 각각 들어 있었다. **어느 쪽도 낡은 것이 아니라 도구별로 필요한 내용이었다.** 옛 절차대로 복사했으면 뒤쪽 둘이 소실됐다.

> 프로젝트가 블록 안 내용을 고쳐야 할 사정이 생기면 **마스터를 고치고 재배포**한다 — §4.3 과 같은 원칙이다.

### 5.4 배포물에는 문서 폴더도 포함된다

스킬만 넣으면 **규칙이 가리키는 폴더가 없다.** `document-convention` 은 `docs/develop-history/` · `docs/plan/` 을, `work-log` 는 `docs/work-log/` 를 요구하는데, 대상 프로젝트에는 대개 없다.

**`templates/docs/` 를 프로젝트 `docs/` 로 복사한다.** 각 폴더에는 `README.md` 가 들어 있다.

- **빈 폴더는 git 에 올라가지 않는다.** README 가 폴더를 남기는 역할을 겸한다
- README 는 **그 폴더가 무엇을 담는 곳인지**와 **규칙의 단일 진실원이 어느 스킬인지**를 알려준다. 규칙 본문을 복제하지 않는다
- **`docs/work-log/` 에는 `work-log.md` 도 함께 넣는다.** 절 두 개(`## 열린 보류` · `## 최근 작업`)만 있는 빈 파일이다 — **없으면 첫 기록 때 파일을 새로 만들면서 절 구조가 갈린다**
- 프로젝트에 이미 비슷한 이력 문서가 있으면 **덮어쓰지 말고 관계를 먼저 정한다** (기존 것을 남길지, 이관할지) — P1 무손실

### 5.5 스킬을 수정하면 재배포가 필요하다

공용 층을 고치면 이미 이식한 모든 프로젝트에 다시 복사해야 한다. 대상은 §5.2 표에서 이식 완료(✅)인 것 전부다.

① 마스터(`.claude/skills/`)에서만 고친다 → ② `.agents/skills/` 로 복사 → ③ **`templates/` 를 갱신하고 두 파일을 바이트 동일로 맞춘다** → ④ **고친 스킬을 이름으로 지정해** 대상 프로젝트의 두 경로에 복사 → ⑤ **두 진입점 각각에서** `AI-SKILLS` 블록을 `templates/` 에서 통째 가져와 교체(§5.3) → ⑥ 해시로 **공용 층과 블록** 일치 확인 → ⑦ §5.2 표의 이식 상태 갱신

> **⑤는 두 파일에 각각 한다. 한쪽을 다른 쪽으로 복사하지 않는다.** 배포 대상에서 동일해야 하는 것은 **블록뿐**이고, 블록 밖은 도구별 규칙이라 서로 달라도 정상이다 (§5.3).
>
> **⑥의 대조 대상도 블록이다.** 파일 전체를 대조하면 정상 상태가 사고로 보고된다.

> **④ 는 이름 지정이고 ⑤ 는 통째 교체다. 헷갈리지 않는다.**
> **스킬 파일**은 배포 대상만 골라 복사한다 — 폴더를 통째로 복사하면 **자체 스킬이 딸려 나간다**(§5.2).
> **진입점 블록**은 전 프로젝트 동일하므로 `templates/` 에서 통째로 가져온다.

**③을 건너뛰면 ⑤가 성립하지 않는다.** 교체할 블록을 어디서 가져올지가 정해지지 않아, 배포하는 쪽이 즉석에서 문장을 조립하게 된다. **그 결과물은 어느 프로젝트에도 원본이 없는 사본이 된다.**

**`project-rules.md` 는 재배포 대상이 아니다.** 프로젝트마다 다른 유일한 파일이다.

### 5.6 이식 시 지키는 원칙

> 상세 이식 절차 문서는 **재작성 예정**이다. 그전까지 아래 두 가지는 반드시 지킨다.

- **P0 독단 금지** — 이슈가 생기면 멈추고 상의한다
- **P1 무손실** — 기존 룰은 이관 · 잔류 · 승인된 폐기 중 하나로 귀결. **제거 확인과 도착 확인은 별개다.** "원본에서 빠졌는가"만 보고 통과시키면 어디에도 안 들어간 채 증발한다

## 6. 문서 배치 규칙

**스킬 하나 = 폴더 하나 = 문서 두 개.** `plan.md`(설계) · `review.md`(검토). **그 이상 늘리지 않는다.**

```
docs/skills/<스킬명>/
├─ plan.md      ← 설계 · 담당 범위 · 결정 이력 · 미결정
└─ review.md    ← 교차 검증. 회차를 절로 쌓는다
```

**루트에 공통 문서를 두지 않는다.** 여러 스킬에 걸친 내용이 생기면 그것은 **개발 방식**이므로 **이 스킬로 올린다.** `docs/skills/` 아래에는 스킬 폴더만 있다.

| 성격 | 위치 |
|---|---|
| 스킬 설계 · 검토 | `docs/skills/<스킬명>/` |
| 개발 이력 | `docs/develop-history/YYYY-MM-DD-<슬러그>.md` |
| **작업 기록 · 열린 보류 현황** | **`docs/work-log/`** — 형식은 `work-log` 스킬 |
| 절차 · 분류표 · 인수인계 | `docs/YYYY-MM-DD-<슬러그>.md` |
| **팀 공유 공지 양식** | **`docs/team-notice-format.md`** — 살아있는 문서라 날짜를 붙이지 않는다. **공지 본문은 `tmp/` 에 쓰고 붙여넣은 뒤 지운다** |
| 살아있는 규칙 — 스킬 개발·배포 절차 | **이 스킬** |
| 살아있는 규칙 — 로드 의무 · 파국 방지 룰 · 저장소 배경 | 진입점 (`CLAUDE.md` · `AGENTS.md`) |
| 스킬 내용 | `.claude/skills/` + `.agents/skills/` |

**이 저장소에는 `docs/plan/` 을 두지 않는다.** 여기서 만드는 것은 스킬이고, 스킬 계획은 위 표대로 `docs/skills/<스킬명>/plan.md` 다. `document-convention` 의 `docs/plan/` 규칙은 **배포 대상 프로젝트에 적용된다** — 그쪽은 게임 기능을 만들기 전에 쓰는 계획이라 대상이 다르다 (§4.1 「분리」 판정). **폴더가 없다고 만들지 않는다.**

> **`docs/work-log/` 는 반대다 — 이 저장소에도 둔다.** `docs/plan/` 과 갈리는 이유는 **대상이 갈리느냐**다. 계획 문서는 *게임 기능*을 만들기 전에 쓰는 것이라 여기엔 대상이 없지만, **작업 기록은 스킬을 만드는 작업에도 그대로 해당한다.**
>
> **그리고 여기 없으면 파이프라인 ③ 테스트를 할 수 없다** — 스킬이 가리키는 파일이 저장소에 없기 때문이다. ⑤(프로젝트 재테스트)로 대체되지 않는다. 둘이 보는 것이 다르다 (§3).

**`docs/skills/` 아래에는 날짜를 붙이지 않는다.** 둘 다 살아있는 문서이고 폴더가 이미 구분자다. 추적은 문서 안의 표가 한다 — `plan.md` 는 변경 이력, `review.md` 는 회차. **검토를 2차·3차 받아도 파일을 늘리지 않고 절로 쌓되, 아래 수명 규칙을 지킨다.**

### 6.1 두 문서의 수명 ★

**둘의 성격이 다르다.**

| | 담는 것 | 회차가 끝나면 |
|---|---|---|
| **`plan.md`** | **결정과 근거** | **남는다.** 이게 「왜」다 |
| **`review.md`** | Claude·Codex 의 **왕복 과정** | **소진된다.** 판정이 끝나면 왕복 자체는 값이 없다 |

#### `plan.md` — 두 절만 남긴다

```
## 결정 이력   ← 무엇을 왜 · 버린 대안 · 뒤집힌 결정
## 미결정      ← 아직 안 정한 것과 판단 시점
```

**각 행은 개발 이력으로 링크한다.** 상세 경위는 거기 있으므로 **plan 은 색인 역할**이다. 그래야 다시 커지지 않는다.

나머지 — 담당 범위 표 · 절차 초안 · 형식과 예시 · 이관 대상 표 — 는 **SKILL 에 있거나 끝난 일**이므로 버린다 (§3.5).

#### `review.md` — 비운다. 지우지 않는다

**파일은 남긴다.** 다음 회차가 같은 자리를 쓴다. 지우면 *"이 스킬은 검토를 안 받았나"* 와 구분되지 않는다 — `document-convention` 이 보류 표에 `| 없음 | — | — |` 을 남기는 것과 같은 이유다.

비운 뒤 남기는 것:

```markdown
---
id: REVIEW:<스킬명>
title: <스킬명> — 교차 검증
date: YYYY-MM-DD
status: 비어 있음 — 다음 회차 대기
---

# `<스킬명>` 교차 검증

**이전 회차 판정은 [`plan.md`](./plan.md) 의 결정 이력으로 흡수됐다** (YYYY-MM-DD 비움).

진행 방식과 고정 질문은 `skill-pipeline` §3.2 에 있다. 여기에 복제하지 않는다.

## 회차

없음. 다음 검토가 시작되면 여기에 절로 쌓는다.
```

**비우는 조건은 하나다 — 판정이 plan 결정 이력에 들어갔는가.** 안 들어갔으면 **못 비운다.** 흡수 없이 비우면 근거가 통째로 날아간다.

#### 크기 상한

⑥에서 비우므로 정상 흐름에서는 안 커진다. 다만 **한 회차 안에서 라운드를 여러 번 돌면** 커진다.

> **`review.md` 가 60KB 를 넘으면 앞 라운드를 접는다.** 판정 결과만 남기고 왕복 과정을 버린다 — 그 결론은 이미 SKILL 에 반영돼 있다.

**사람의 판단이 아니라 숫자가 발동시킨다.** *"이제 좀 큰가"* 를 매번 판정하면 안 하게 된다.

> **왜 상한이 필요한가** — 로드된 문서는 **그 세션 남은 턴 전부에 다시 실린다.** 110KB 문서를 한 번 읽으면 약 3만 토큰이 매 턴 따라붙는다. 진입점을 12KB 로 줄여놓고 설계 문서가 110KB 면 **줄일 곳을 잘못 본 것이다** (2026-08-25 실측).

그 외 문서는 날짜 접두어를 쓴다. 한 문서가 특정 프로젝트 전용이면 슬러그에 프로젝트명을 넣는다 (예: `project-a-handover`).

**폴더명은 점으로 시작하지 않는다.** 옵시디언이 dotfolder 를 인덱싱하지 않아 문서가 보이지 않는다 (2026-08-21 실측).
