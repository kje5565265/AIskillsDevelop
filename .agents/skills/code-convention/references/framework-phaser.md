# Phaser 층 (L3)

Phaser 기반 웹 게임에서만 성립하는 룰. Unity 층의 대응 개념과 구조가 거의 같다 — 생명주기 대칭 / 매 프레임 할당 / 파괴된 객체 참조.

---

## §1. 로직과 렌더의 분리

**Phaser 를 모르는 채로 테스트할 수 있는 계층을 유지한다.**

| 계층 | 담당 | Phaser 의존 |
|---|---|---|
| core (모델) | 상태 전이, 점수, 난이도, 타이머 계산 | **없어야 함** |
| game (씬·렌더) | Scene 생명주기, 입력, 그리기, 사운드 | 있음 |
| config | 밸런스 수치, 상수 | 없음 |

- **core 에서 `Phaser.*` 를 import 하지 않는다.** 한 번 새면 그 계층 전체가 테스트 불가가 된다.
- 렌더러는 모델을 **읽기만** 한다. 렌더러가 게임 상태를 바꾸면 상태 소유자가 둘이 된다 (`SKILL.md` Part A 4축 분해 — 표시 소유자와 상태 소유자의 분리).
- 새 기능을 넣을 때 **"이건 core 인가 game 인가"를 먼저 정한다.** 정하지 않고 Scene 안에 쓰기 시작하면 거의 항상 Scene 이 비대해진다.

## §2. Scene 생명주기 대칭

`init` → `preload` → `create` → `update`(매 프레임) → `shutdown` → `destroy`

**Scene 은 재시작된다.** `create` 는 재시작마다 다시 불리고, `shutdown` 은 그때마다 정리 기회다. 짝을 맞추지 않으면 재시작할수록 리스너·타이머가 누적된다.

| 등록 | 해제 |
|---|---|
| `create` 에서 이벤트 구독 | `shutdown` 에서 `off` |
| `create` 에서 타이머·트윈 시작 | `shutdown` 에서 `remove` / `stop` |
| 전역(`window` / `document`) 리스너 | `shutdown` 에서 반드시 해제 — Scene 파괴로 자동 정리되지 않는다 |

```ts
create() {
  this.events.once('shutdown', this.onShutdown, this)
  window.addEventListener('resize', this.onResize)
}
private onShutdown() {
  window.removeEventListener('resize', this.onResize)
  this.tweens.killAll()
  this.time.removeAllEvents()
}
```

- **모듈 스코프 변수에 게임 상태를 두지 않는다.** Scene 이 재시작돼도 살아남아 이전 판의 상태가 새 판에 새어든다.
- `scene.restart()` 로 초기화를 대신하지 않는다. 무엇이 리셋되고 무엇이 남는지 불명확해진다.

## §3. 파괴된 GameObject

- `destroy()` 한 GameObject 의 참조를 계속 들고 있지 않는다. 이후 접근은 런타임 에러이거나 조용한 오동작이다.
- 파괴 여부는 `obj.active` / `obj.scene` 으로 확인한다. **`obj != null` 은 파괴를 잡지 못한다** — 참조는 살아있다.
- 파괴 시점이 콜백보다 먼저일 수 있다. 트윈·타이머 콜백 안에서 대상이 아직 유효한지 확인한다.
- 정리 순서를 스스로 관리하지 말고, 가능하면 **컨테이너·그룹에 넣어 한꺼번에** 파괴한다.

## §4. update 루프

- **`update(time, delta)` 의 `delta` 를 쓴다.** 프레임 수를 세거나 고정값을 더하면 기기·리프레시레이트마다 게임 속도가 달라진다.
- **update 안에서 할당하지 않는다** — 객체 리터럴, 배열 `map`/`filter`, 스프레드, 인라인 화살표 함수, 문자열 조립. 브라우저 GC 스파이크가 그대로 프레임 드랍이다 (`lang-typescript.md` §8).
- **매 프레임 조회를 캐시한다** — `this.children.getByName()`, `getChildren()` 순회, DOM 조회.
- 매 프레임 필요 없는 로직은 `this.time.addEvent` 주기 실행으로 내린다.
- update 가 길어지면 **분리 신호**다. Scene 이 상태 머신·스폰·점수·연출을 다 들고 있으면 `SKILL.md` Part A 원칙 2 적용 대상.

## §5. 오브젝트 재사용

- 탄환·적처럼 빈번히 생성·파괴되는 객체는 **그룹 풀**로 재사용한다.
- **풀에 반환할 때 상태를 전부 리셋**한다 — 속도, 회전, 알파, 스케일, 붙어 있던 트윈·타이머, 커스텀 데이터. 남으면 다음 대여자에게 새어간다.
- 리셋 책임은 풀이 아니라 **대상 객체**가 갖는다.

## §6. 에셋과 캐시

- `preload` 에서 로드하고, 키를 문자열 리터럴로 흩뿌리지 않는다 — 상수로 모은다.
- **같은 키로 두 번 로드하지 않는다.** Phaser 는 무시하거나 덮어쓰며, 어느 쪽이든 의도가 아니다.
- Scene 이 파괴돼도 텍스처·오디오는 **전역 캐시에 남는다.** 메모리를 신경 써야 하면 명시적으로 제거한다.
- 큰 에셋은 초기 로드에 넣지 않는다. 첫 화면 로딩 시간이 곧 이탈률이다.

## §7. 입력

- 입력 핸들러 등록도 §2 대칭 규칙을 따른다. `create` 에서 등록했으면 `shutdown` 에서 해제한다.
- **입력 콜백에서 게임 로직을 직접 실행하지 않는다.** 의도(intent)로 변환해 모델에 넘긴다 — 그래야 리플레이·테스트·다른 입력 소스가 가능해진다.
- 터치와 마우스를 따로 처리하지 않는다. 포인터 이벤트로 통일한다.

## §8. 빌드·환경

- 개발 전용 코드는 번들러 환경 플래그(`import.meta.env.DEV` 등)로 감싼다. **출시 번들에 디버그 경로가 남지 않게** 한다.
- 조건이 정적이어야 tree-shaking 이 동작한다. 런타임 변수로 분기하면 코드가 그대로 남는다.
- `strict` 를 끄거나 타입 에러를 무시한 채 빌드하지 않는다. `noEmit` + 타입 체크를 빌드 파이프라인에 둔다.
