# code-convention

프로젝트의 코드 컨벤션 단일 진실원. **설계 원칙**(무엇을 어디에 두는가)과 **변경 안전 절차**(기존 코드를 어떻게 건드리는가)를 다룬다.

- **Part A (사전형)** — 새 코드를 작성할 때 처음부터 구조를 잡는 원칙
- **Part B (사후형)** — 기존 코드를 수정할 때의 변경 안전 절차
- **Part C** — A와 B가 충돌할 때의 발동 시점 룰
- **Part D** — 테스트 로그를 심고 지우는 절차

언어·프레임워크·프로젝트 고유 룰은 본 문서에 없다. `references/` 하위 레퍼런스가 담당하며, **본 문서를 적용하기 전에 반드시 아래 §0 절차로 로드한다.**

## §0. 레퍼런스 로드 (필수 — 원칙 적용 전에 먼저 수행)

본 문서(L1)는 언어·엔진 무관한 설계 원칙만 담는다. 실제 코드를 쓰려면 언어(L2)·프레임워크(L3)·프로젝트(L4) 층이 필요하다.

### 발동 기준 — 「무게」가 아니라 「대상」

**저장소의 소스·데이터 파일을 편집하기 전에 로드한다. 편집 분량·난이도는 기준이 아니다.**

| 포함 | 제외 |
|---|---|
| 소스 파일(`.cs` / `.ts` / `.cpp` 등) 편집 — **주석 · 오타 · 로그 한 줄도 포함** | `.md` 문서 편집 → **`document-convention` 소관** |
| 데이터 파일(CSV / xlsx / 테이블) 편집 | 읽기 · 질문 · 조사만 하는 경우 |
| 프리팹 · 에셋 편집 | 대화만 |

> **오른쪽 칸의 `.md` 는 "규칙이 없다"가 아니라 "다른 스킬이 맡는다"다.** `document-convention` 이 같은 방식으로 — **무게가 아니라 대상으로** — 발동한다. 사양서·README 도 `.md` 이므로 그쪽 소관이다.
>
> **코드와 문서를 같이 만지면 둘 다 로드한다.** 세션당 한 번씩이라 비용이 늘지 않는다.

**"가벼운 수정이라 생략해도 되겠다"는 판단을 하지 않는다.** 그 판단 자체가 이 절차의 실패 지점이다.

> **실제 사례** — 주석을 다는 작업에서 에이전트가 "가벼운 수정"으로 보고 본 스킬을 건너뛴 적이 있다. 그 결과 Part B **§1(주석 오신뢰 방지)** 과 **§2(금지 항목에 "주석 어투 다듬기" 명시)** 가 무시됐다. **주석 작업은 이 스킬의 사정권 밖이 아니라, 오히려 두 절이 직접 규율하는 대상이다.**

**비용 오해 차단** — 스킬은 **세션당 한 번만** 로드되고 이후 컨텍스트에 남는다. 가벼운 작업에서 로드해도 총비용이 늘지 않으며, 뒤에 코드 작업이 이어지면 어차피 필요했던 로드다.

### 절차

1. **감지** — `references/_detection.md` 를 Read 해 감지 신호표와 감지 명령을 로드한다.
   - **한 번의 명령**으로 전 신호를 일괄 판정한다. 신호별로 탐색을 반복하지 않는다.
   - 결과를 `_detection.md` §3 형식의 **경로별 판정 표**로 정리해 답변에 남긴다. 파일로 저장하지 않는다 — 이 판정은 현재 세션 컨텍스트에서만 유지한다.

2. **해당 층 Read** — 작업 대상이 정해졌는지에 따라 갈린다.

   | 상황 | 처리 |
   |---|---|
   | 작업 대상 파일·경로가 **정해짐** | 그 경로가 속하는 행의 층을 **즉시 Read** |
   | 아직 **안 정해짐** (일반 논의 · 질문 · 계획 단계) | 판정 표만 유지하고 층 Read 는 보류. 전역 행(`*`)의 층만 읽는다 |

   **보류했을 때의 의무** — 첫 코드 작업 대상이 정해지는 순간, 그 경로가 속하는 행의 층을 **반드시 먼저 Read 한다.** 층을 읽지 않은 채로 코드를 작성·수정하지 않는다.
   **이 Read 는 사용자에게 묻지 않고 바로 수행한다** — 읽기 전용이라 확인받을 이유가 없고, 매번 묻는 것이 절차를 무겁게 만든다.
   *감지만 해놓고 정작 룰은 로드하지 않는 것이 이 절차의 가장 흔한 실패 지점이다.*

   감지는 됐는데 해당 레퍼런스 파일이 없으면 그 층은 건너뛴다(미작성).

3. **세션 중 재판정 (중요)** — 스킬은 세션당 한 번 로드되고 판정 결과가 컨텍스트에 남는다. 그래서 아래 상황에서는 **판정을 다시 해야 한다.** 이미 내린 판정을 그대로 쓰지 않는다.
   - 작업 대상 파일이 **기존 판정 표의 어느 행에도 속하지 않는 경로**일 때 → 그 경로만 추가 감지해 표에 행을 추가한다
   - 새 서브프로젝트·모듈이 추가되었을 때 (예: Unity 전용이던 레포에 .NET 서버 프로젝트가 붙음) → 그 경로를 감지해 편입한다
   - 판정 근거였던 파일이 사라졌을 때 → 전체 재감지

   재판정 시에도 **해당 경로만** 감지한다. 전체 재감지는 근거가 깨졌을 때만.

### 층 우선순위

충돌 시 **더 구체적인 층이 이긴다.**

```
project (L4)  >  platform (L3.5)  >  framework (L3)  >  lang (L2)  >  본 문서 (L1)
```

**platform 층은 framework 와 직교한다.** 같은 Unity 프로젝트라도 Android · iOS · WebGL 중 실제 타깃만 로드하며, 여러 타깃이면 **여러 platform 층이 함께** 적용된다. 플랫폼끼리 충돌하는 룰은 원칙적으로 없다 — 각자 자기 `#if` 분기 안에서만 유효하기 때문이다.

같은 층에서 판정 표의 경로가 겹치면 **더 좁은 경로**가 이긴다.

> **레퍼런스 파일에는 경로 정보가 없다.** frontmatter 에는 `layer` 만 둔다. 어느 경로에 적용되는지는 파일이 아니라 **§0 감지가 정한다** — 파일에 경로를 박아두면 감지 결과와 어긋나 오도한다.

> **예외** — 본 문서 **Part B(변경 안전 절차)** 는 어떤 층도 무효화할 수 없다. 프레임워크나 프로젝트 사정으로 면제되는 성질의 절차가 아니다.

### 하지 말 것

- 레퍼런스를 읽지 않고 Part A/B만 적용하기 — 원칙만 있고 판정 기준이 없어 추상적인 잔소리가 된다.
- 감지하지 않고 "아마 Unity겠지" 로 추정하기.
- 세션 초반 판정을 근거 없이 계속 재사용하기 — 3번 재판정 조건을 매 작업마다 확인한다.
- 판정 결과를 파일로 저장하기 — 틀린 판정이 고착되고, 레퍼런스는 읽기 전용이어야 한다.
- 레퍼런스 내용을 본 문서에 복제하기 — 단일 진실원이 깨진다.

## Part A — 코드 작성 베이스라인 (사전형)

### 원칙 1. 다형성 + 의존 역전

**룰**: 발신자는 수신자의 구체 자식 타입 대신 **공통 부모 또는 인터페이스**에 의존한다. 자식이 늘어나면 분기 코드를 늘리는 게 아니라, 자식이 부모 메서드를 override 한다.

**위반 신호**

- 같은 함수/블록 안에서 자식A로의 캐스팅과 자식B로의 캐스팅이 함께 나온다
- `if (x is TypeA) ... else if (x is TypeB)` 패턴으로 타입별 분기
- 한 함수가 자식 타입별로 다른 처리를 한다

**해결 절차**

1. 공통 부모 또는 인터페이스를 찾는다
2. 부모에 virtual 메서드를 추가한다 — **의미 있는 신호 이름**으로 (`OnAttackWindowOpened` 처럼, `HandleTypeA` 가 아니라)
3. 자식이 각자 override 한다

**계약 유지(Liskov)**: override 할 때 부모의 계약(사이드이펙트 / 예외 조건 / 반환값 의미)을 유지한다. 부모 의도와 다른 동작이면 override 가 아니라 별도 메서드다.

### 원칙 2. 책임 경계 + 합성 우선

**룰**: 한 클래스는 **한 도메인의 책임만** 갖는다. 새 책임이 추가되면 새 클래스로 분리한다. 분리 방식은 상속보다 **합성**을 우선한다.

#### 4축 분해 — 기능 설계 시 다음 4개 역할을 먼저 식별한다

| 축 | 질문 |
|---|---|
| 1. 신호 발신자 | 누가 트리거하는가 |
| 2. 신호 수신자 | 누가 받는가 |
| 3. 상태 소유자 | 상태 플래그/태그의 Add·Remove 책임은 누구에게 있는가 |
| 4. 표시 소유자 | 이펙트·UI·사운드 책임은 누구에게 있는가 |

이 4개가 한 클래스에 뭉쳐 있으면 분리 대상이다.

**위반 신호**

- 주체(캐릭터·플레이어·엔티티) 본체에 이펙트/UI/타이머 코드가 직접 들어간다
- 발신자가 수신자의 상태 플래그를 직접 Add/Remove 한다
- 한 클래스가 도메인 2개 이상을 알아야 동작한다

**해결**

- 표시·이펙트·타이머 → 전용 컴포넌트/클래스로 분리
- 상태 Add/Remove → **상태를 겪는 주체** 또는 그 주체의 전용 컴포넌트가 소유
- 발신자는 **신호만** 보내고, 수신자가 정책을 결정한다

#### 재사용 공용 레이어 책임 경계 — 자가검증 5항목

여러 도메인에서 재사용되거나 부착되는 레이어(베이스 클래스 / 공용 컴포넌트 / 인터페이스 구현부 / 공유 서비스·매니저 / 유틸리티·정적 헬퍼 / 공통 이벤트 핸들러)는 **자기 책임 밖의 구체 타입과 내부 정책에 직접 접근하지 않는다.**

1. 이 접근이 파일명·주석·사양에 드러난 **1차 책임**인가?
2. 다른 도메인에서 호출·부착될 때 무의미한 부작용을 만들지 않는가?
3. 새 상태 플래그를 세팅했다면 **제거 경로까지** 확인했는가?
4. 형제 자식 클래스 양측(예: 플레이어/적)에 영향이 있으면 **양측 구현을 대조**했는가?
5. 시스템 A의 입력을 시스템 B의 출력으로 변환하는 코드라면, **변환 책임을 가진 전용 위치**에 있는가?

**예외 기준** — 아래를 모두 만족하면 구체 타입 접근을 허용한다.
- 파일이 이름·주석·사양·부착 대상 기준으로 특정 도메인 전용이다
- 구체 타입 접근이 그 파일의 1차 책임 수행에 필요하다
- 재사용 공용 레이어에 도메인별 정책을 숨겨 넣는 형태가 아니다

> 어떤 카테고리가 "재사용 공용 레이어"에 해당하는지의 **구체 목록은 framework 층**에 있다.

### 원칙 3. 인터페이스 슬림

**룰**: 인터페이스는 클라이언트가 **실제로 쓰는 메서드만** 포함한다. 일부 구현체에만 의미 있는 메서드는 별도 인터페이스로 분리한다.

**위반 신호 (자기 고백형)**

- 인터페이스에 빈 기본 구현(`{}`)이 달려 있다
- 주석에 "특정 자식에서만 override" 라고 적혀 있다
- 메서드 수가 20개를 넘는다

**해결**

- 도메인별로 작은 인터페이스로 분리한다
- 구현체가 implement 하는 인터페이스 목록 = **그 구현체의 능력 명세**가 되게 한다

**핫패스 예외**: 매 프레임 호출되는 인터페이스는 호출 비용 회피를 위해 통합 인터페이스 + 빈 메서드를 허용할 수 있다. 단 **면제 사유를 주석에 명시**한다.

### 적용 제외 영역

다음 영역에서는 의도적으로 룰을 깨도 된다. **단 면제 적용 시 주석에 사유를 명시한다** (예: `// 핫패스 — 의존 역전 면제, 직접 호출`).

- 데이터 지향 / 캐시 친화 핫패스
- 매 프레임 호출 경로 — 가상 호출 비용 회피
- 렌더링·물리처럼 본질적으로 두꺼운 인터페이스
- 성능 패턴(오브젝트 풀 / 플라이웨이트)

> 프로젝트별 구체 면제 대상은 framework·project 층에서 정의한다.

## Part B — 코드 수정 안전 절차 (사후형)

**이 절차는 어떤 층도 무효화할 수 없다.**

### §1. 주석 오신뢰 방지

**원칙**: 코드 분석·버그 판단 시 **주석 문구에만 근거해 결론을 내리지 않는다.** 반드시 실제 함수 본문과 **호출부(하위 소비자)** 까지 따라가 실제 동작을 확인한 후 판단한다. 주석은 과거 시점에 작성되어 현재 구현과 어긋나 있을 수 있다.

**절차**

1. 함수 본문을 읽는다
2. 반환값·출력 파라미터를 실제로 소비하는 호출부를 **전수 추적**한다
3. 호출부에서 그 값을 어떻게 해석하는지 확인한다
4. 주석과 실제 동작이 어긋나면 **주석을 수정**하고, 주석을 근거로 코드를 바꾸려던 계획은 **폐기**한다

> 주석을 믿고 부호를 뒤집었다가 없던 버그를 만드는 사고가 이 절차가 막는 대표 유형이다.

### §2. 외과적 변경 (Surgical Changes)

**원칙**: 모든 코드 수정은 **사용자 요청에 직결되는 라인만** 변경한다. 작업 중인 파일이라도 인접 코드를 "겸사겸사" 다듬지 않는다.

| | |
|---|---|
| **금지** | 인접 코드 스타일 보정 / 안 쓰는 듯 보이는 변수 제거 / 주석 어투 다듬기 / 포매팅 통일 / 자발적 리팩터링 |
| **허용** | 본인 수정으로 **새로 생긴** 미사용 import·변수·함수 정리 (orphan cleanup 한정) |
| **기존 죽은 코드 발견 시** | 삭제하지 말고 한 줄 보고만. 사용자가 명시 요청하면 그때 제거 |
| **스타일 충돌 시** | 본인이라면 다르게 짤 부분이라도 같은 파일 안에서는 **기존 스타일**을 따른다 |

**자가검증**: "내가 바꾼 라인 한 줄 한 줄이 사용자가 요청한 작업과 직결되는가?" 한 줄이라도 아니면 그 변경은 폐기하거나 별도 작업으로 분리한다.

**목적**: diff 검토 시 의도하지 않은 변경이 섞이면 검증 비용이 오르고 변경 의도 추적이 어려워진다.

### §3. 조건문 대칭성 체크 (보호·상쇄 로직 추가 시)

**원칙**: 새 조건문으로 보호·상쇄 로직을 감쌀 때, **조건이 false인 분기를 타는 대상이 원래 문제를 여전히 받는지** 반드시 확인한다. `원인의 적용 범위 ⊇ 보호의 적용 범위` 가 되면 안 된다. 부작용이 모두에게 적용된다면 보호도 모두에게 적용돼야 한다.

**절차**

1. 보호가 상쇄하려는 **"원인"** 을 명시한다
2. 원인의 적용 범위를 나열한다
3. 조건문 false 분기를 타는 대상을 나열한다
4. (3)이 (2)에 노출되면 **조건문 설계 자체가 잘못**이다 — 조건을 제거하거나 범위를 재조정한다

> 보호를 특정 대상에만 걸었는데 부작용은 전체에 적용되는 잠복 버그가 이 절차가 막는 대표 유형이다. 다른 기능이 도입되는 순간 크리티컬 증상으로 터진다.

### §4. 영향 분석 (시스템 변경·도입 시)

**원칙**: 기존 시스템을 변경하거나 새 시스템을 도입할 때, **구현 전에 영향 범위를 분석**한다. 내부 로직만 구현하고 기존 연결점을 누락하면 잘 되던 기능이 고장난다. 전투·데이터·UI·네트워크 등 **모든 시스템 변경에 공통 적용**한다.

**분석 절차**

1. **참조 전수 검색** — 변경되는 변수·플래그·상수·이벤트를 사용하는 모든 파일을 검색한다
2. **콜백/이벤트 경로 추적** — 관여하는 콜백 체인을 **양방향**으로 추적한다
3. **형제 클래스 양측 확인** — 부모의 가상 함수를 자식 한쪽에만 추가·수정하지 않았는지 대조한다. 양측에 mirror 본문이 있으면 1:1 비교한다
4. **상태 생명주기 검증** — 플래그의 **Add 경로와 Remove 경로를 매칭**해 누락·누적 가능성을 확인한다

**계획에 포함할 항목**

- 변경되는 변수·플래그 목록
- 참조 파일:함수 목록 (검색 결과)
- 각 참조 지점에서 필요한 수정 사항
- **기존 동작 회귀 테스트 체크리스트** (변경 시스템에 인접한 기능들)

### §5. 사양서에서 "집행 정책"을 "구조"로 오인하지 말 것

**원칙**: 데이터 구조(테이블 컬럼 / 구조체 필드 / 인터페이스)의 **표현력**과, 현재 시점의 **집행 정책**(실제로 매핑한 값 / 적용 범위 / 이번 버전 한정 결정)을 사양서에서 **분리해 명시**한다. 둘이 합쳐 표현되면 미래에 정책을 확장할 때 "구조도 같이 바꿔야 하나?" 하는 잘못된 작업을 유발한다.

| | 정의 |
|---|---|
| **구조** | 이 컬럼/필드/인터페이스가 **표현 가능한 모든 경우의 수** |
| **정책** | 현재 디자인 결정으로 그중 **일부만 채우거나 한정한 매핑** |

**판단 체크리스트**

1. 표현이 "X만 컬럼이 있다 / X만 비용을 부과한다" 처럼 읽히는가? → 구조와 정책이 뭉쳐진 위험 표현
2. "X의 값을 Y로 갱신하면 정책 변경 가능, 코드 변경 불필요" 가 사양서에서 즉시 추론되는가? → 분리 OK
3. 미래 확장 시 "어디만 바꾸면 되는가?" 가 사양서로 답해지는가? → 분리 OK

**절차**: 구조 정의 절을 먼저 쓰고("전 행위자 / 전 행동에 적용 가능" 같은 표현력 명시), 정책 매핑 절을 별도로 쓴다("이번 버전 결정 / 미사용 행 = 0 명시"). 두 절을 상호 참조로 연결한다 — "정책 확장 시 본 절만 갱신, 구조 변경 불필요".

### §6. 외과적 변경은 최소 라인 수가 아니다

**원칙**: 외과적 변경의 기준은 **① 요청에 직접 필요한가** 와 **② 올바른 책임 경계 안에 있는가** 두 축이다. 잘못된 파일에 몇 줄 끼워 넣는 것보다, **올바른 위치에 필요한 최소 구조를 추가하는 쪽이 더 외과적이다.**

**자가검증**

1. 바꾼 라인이 사용자 요청에 직접 필요한가?
2. 바꾼 라인이 **이 파일의 책임 범위 안**에 있는가?
3. 둘 중 하나라도 아니면 폐기하거나 별도 작업으로 분리한다.

§2의 "최소 라인" 자가검증과 Part A 원칙 2의 책임 경계 룰을 함께 적용한 형태다. 라인 수만 줄이려다 잘못된 위치에 끼워 넣는 안티패턴을 차단한다.

## Part D — 테스트 로그 (심기부터 지우기까지)

**심는 것도 지우는 것도 소스 파일 편집이다.** 그래서 한 덩어리로 이 스킬에 있다. `session-routine` 은 **언제 지우나**(마무리 1단계)만 정한다.

### §D1. 상위 맥락 — Log-First

**추측으로 고치지 않는다.** 로그 제거는 독립 작업이 아니라 디버깅 루프의 마지막 단계다.

```
추측 수정 금지
  → 의심 경로 분기점에 로그를 먼저 심는다
  → 실행, 사용자 테스트 요청
  → 로그로 실제 실행 경로 식별
  → 원인 특정 후 수정
  → 마무리에서 로그 제거
```

한 번 추측 수정이 실패하면 **즉시 로그 방식으로 전환**한다.

### §D2. 심기 전에 어느 쪽인지 정한다

로그를 심어달라는 요청을 받으면 **심기 전에** 판정한다. 물을 문장은 하나면 된다.

> 원인을 찾으면 없어질 로그인가요, 계속 보실 로그인가요?

| | 마커 | 마무리에서 |
|---|---|---|
| **임시 진단 로그** | **붙인다** | 제거된다 |
| **남길 로그** | 안 붙인다 | 그대로 둔다 |

**애매하면 임시다.** 되돌리는 비용이 비대칭이기 때문이다.

> **마커를 안 붙이면 아무도 안 지운다.** 붙였다가 남기기로 하면 떼면 되지만(§D6), 안 붙였다가 나중에 찾으려면 못 찾는다.

### §D3. 마커는 2중이다 ★

목적이 다른 마커가 **둘** 필요하다. 하나만 있으면 반쪽이다.

| 마커 | 위치 | 목적 |
|---|---|---|
| **`[AITESTLOG_<컨텐츠명>]`** | **로그 문자열 안** | **런타임 출력 필터링** — 수천 줄에서 이번에 심은 것만 골라 본다 |
| **`// TODO: AITESTLOG_<컨텐츠명> — 제거 예정 (조건)`** | 주석 | 소스에서 찾아 제거 |

첫 번째가 빠지면 *"로그를 AI 가 읽는다"* 는 목적이 성립하지 않는다. 두 번째가 빠지면 **지울 때 못 찾는다.**

**접두어와 접미가 하는 일이 다르다.**

| | 하는 일 |
|---|---|
| `AITESTLOG_` **고정** | **전수 검색.** 마무리에서 남은 것을 하나도 빠뜨리지 않는다 |
| `_<컨텐츠명>` **가변** | **선택 필터 · 선택 제거.** 그 시스템 것만 골라 보고, *"인벤토리 것만 지워줘"* 가 된다 |

**컨텐츠명 규칙 셋**

- **지금 하는 작업의 이름**을 쓴다 — 파일명·클래스명이 아니라 시스템·기능 이름. `Inventory` · `BossPhase` · `WaveSpawn`
- **영문, 언더스코어 없이.** 구분자가 `_` 하나여야 접두어가 깨끗하게 잘린다
- **한 작업에서 여러 파일에 심어도 같은 이름을 쓴다.** 파일마다 다르면 선택 제거가 무의미해진다

> **전제의 한계** — *"에이전트가 심으니 누락이 없다"* 는 **에이전트가 새로 심는 로그에만** 성립한다. 붙여넣은 코드·이전 세션의 수동 로그·인스펙터 옵션·서드파티 logger 는 마커가 없다. 그런 것은 §D5 의 **목록 제시 → 확인** 경로로 처리한다.

> **릴리스 검증** — `AITESTLOG_` 가 릴리스 산출물에 남아 있으면 **실패로 판정한다.** 사용자에게 노출되는 문자열이다.

### §D4. 형식

**라인** — 주석은 줄 **위**가 아니라 줄 **끝**에 붙인다. 제거가 한 줄 삭제로 끝난다.

```csharp
Debug.Log($"[AITESTLOG_Inventory] 슬롯 병합 진입: {slotId}, 수량 {count}");   // TODO: AITESTLOG_Inventory — 제거 예정 (병합 버그 수정 후)
```

**블록** — 치트키·강제 스폰·조건 우회처럼 **로그가 아닌 테스트용 코드**가 대상이다. 로그 한 줄만 지우면 **빈 껍데기가 남는** 문제를 막는다.

```csharp
// [AITESTLOG_Inventory-BEGIN] 슬롯 강제 채우기 — 제거 예정 (병합 버그 수정 후)
if (Input.GetKeyDown(KeyCode.F9)) { FillSlots(); }
// [AITESTLOG_Inventory-END]
```

**두 형식 모두 `AITESTLOG_` 한 조각으로 찾힌다.** 로그 API 표기는 언어마다 다르므로 해당 층(L2·L3)을 따른다.

> 마커를 **파일에** 남기는 이유는 컨텍스트가 날아가도 기록이 남기 때문이다. 긴 세션은 중간에 요약이 일어나 *"어디에 로그를 심었는지"* 를 잊는다. 이전 세션에서 못 지운 로그도 다음 마무리에서 같이 걸린다.

### §D5. 제거 절차

1. `AITESTLOG_` 를 찾는다 — **검색 범위는 깃이 추적하는 파일**이다. 빌드 캐시·중간 산출물을 훑지 않는다
2. **삭제 범위를 먼저 보고한다** — 파일별 줄 범위. **미리보기 없이 삭제하지 않는다**
3. 라인 마커는 해당 줄 삭제 · 블록 마커는 블록 통째 삭제
4. 마커 없는 의심 로그는 **목록만 제시하고 확인받는다** (규약 도입 이전 로그)
5. 사용자가 *"이건 남겨줘"* 하면 §D6 으로 간다

**블록 삭제 안전 규칙 ★**

블록 삭제는 강력해서 잘못되면 정상 코드가 같이 사라진다.

- **`END` 없는 `BEGIN` 은 삭제하지 않는다.** 보고만 하고 사용자 판단을 받는다
- **중첩(`BEGIN` 안의 `BEGIN`)은 삭제하지 않는다.** 규약 위반이므로 보고한다
- 한 파일에 블록이 여러 개면 **각각의 범위를 따로 계산**하고 전부 보고한다
- 삭제 후 실제 삭제 범위를 확인한다

> 이 규칙은 **진입점 문서의 「먼저 지킬 것」 절이 원본**이다. 이 스킬이 로드되지 않아도 지켜져야 하므로 그쪽에 있으며, 여기서는 절차 맥락에서 다시 짚는 것이다. **문구가 어긋나면 진입점 쪽이 맞다.**

**마커 없는 로그 탐색 (보조)**

규약 도입 이전 로그를 잡으려면 로그 API 자체를 훑는다. **한 진입점이 전부가 아니다** — 경고·에러 계열, 커스텀 logger, wrapper 도 있다. 프로젝트가 쓰는 진입점 목록은 해당 층(L3·L4)이 갖는다.

**이 탐색 결과는 자동 삭제하지 않는다 — 목록 제시 후 확인이다.**

**찌꺼기는 함께 정리한다.** 로그 한 줄을 지우면 **그 로그만 쓰던 변수나 import 가 남는다.** 그건 로그의 일부이므로 같이 없앤다 — Part B §2 가 *"본인 수정으로 새로 생긴 미사용 심볼 정리"* 를 허용한다.

**다만 두 가지는 건드리지 않는다.**

- 로그와 **무관한** 인접 코드 — 정리·스타일 보정·자발적 리팩터 금지 (Part B §2)
- 디버그 출력과 **같은 블록에 있는 정상 로직** — 함께 계산하던 상태 갱신·반환값까지 지우면 **게임 동작이 바뀐다**

### §D6. 이미 심은 것을 남기기로 할 때

사용자가 *"이건 남겨줘"* 하는 순간이 **상주 전환**이다.

1. **마커를 뗀다** — 로그 문자열의 `[AITESTLOG_...]` 와 `// TODO:` 주석 양쪽
2. **그 로그가 앞으로 출시 빌드에도 출력된다는 것을 알린다**

> **빌드 가드는 아직 이 스킬의 범위가 아니다.** 개발/테스트 빌드 구분과 치트 가드는 별도 작업으로 계획돼 있다. 그전까지는 **남기기로 한 로그가 그대로 나간다는 사실을 알리는 것**까지가 이 절의 몫이다. 없는 절차를 가리키지 않는다.
