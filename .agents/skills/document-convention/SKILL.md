# document-convention

저장소의 **마크다운 문서를 어디에 어떻게 쓰는가**의 단일 진실원.

- **§1 위치와 명명** — 어느 폴더에, 어떤 파일명으로
- **§2 링크** — 문서끼리 어떻게 가리키나
- **§3 개발 이력** — 개발이 끝난 뒤 무엇을 남기나
- **§4 계획 문서** — 개발을 시작하기 전에 무엇을 쓰나
- **§5 검증** — 문서를 고친 뒤 무엇을 확인하나

---

## §0. 발동 기준 — 「무게」가 아니라 「대상」

**저장소의 `.md` 문서를 작성·수정하기 전에 로드한다. 편집 분량·난이도는 기준이 아니다.**

| 포함 | 제외 |
|---|---|
| `.md` 문서 **작성** — 개발 이력 · 계획 · 사양서 · README 등 | 소스·데이터 파일 편집 → **`code-convention`** |
| `.md` 문서 **수정** — **오탈자 한 글자 · 표현 다듬기 · 한 줄 추가도 포함** | 읽기 · 질문 · 조사만 하는 경우 |
| 문서를 **옮기거나 지우거나 이름 변경** | 대화만 |
| **위치 · 파일명 · slug** 결정 | |
| **링크 · 인용 키** 작성·수정 | |

**"가벼운 수정이라 생략해도 되겠다"는 판단을 하지 않는다.** 그 판단 자체가 이 절차의 실패 지점이다.

> **왜 오탈자까지 포함하나** — *"이건 구조를 안 건드리는 편집이다"* 는 **편집을 해봐야 알 수 있다.** 오타를 고치러 들어갔다가 링크를 건드리게 되고, 한 줄 다듬다가 절을 추가하게 된다. 시작 시점에 판정할 수 없는 것을 기준으로 삼으면, 그 판단이 곧 실패 지점이 된다.
>
> **`.md` 를 건드리는가** — 이건 확장자로 판정되는 **사실**이다. `code-convention` 이 "소스 파일"로 판정하는 것과 같은 축이며, 두 스킬이 같은 방식으로 갈려야 헷갈리지 않는다.

**비용 오해 차단** — 스킬은 **세션당 한 번만** 로드되고 이후 컨텍스트에 남는다. 가벼운 작업에서 로드해도 총비용이 늘지 않으며, 뒤에 문서 작업이 이어지면 어차피 필요했던 로드다.

| 이 스킬 | 다른 스킬 |
|---|---|
| 문서 위치 · 파일명 · slug | 소스·데이터 파일 편집 → `code-convention` |
| 문서 간 링크 · 인용 키 | **언제** 문서를 쓰는가 → `session-routine` |
| 개발 이력 · 계획 문서 **형식** | 문서를 **언제** 쓰고 **언제** 보류를 닫나 → `session-routine` |
| 문서 검증에서 **무엇을 확인하나** | 검증 **실행 시점** → `session-routine` |
| | 문서를 커밋하는 절차 → `git-procedure` |

**두 스킬은 파일 종류로만 갈린다.** 소스·데이터 파일이면 `code-convention`, `.md` 면 이 스킬이다. 사양서·README 도 `.md` 이므로 여기 속한다.

**코드와 문서를 같이 만지면 둘 다 로드한다.** 세션당 한 번만 로드되므로 비용이 늘지 않는다.

**문서 언어(한국어/영어)는 이 스킬이 정하지 않는다.** 프로젝트 운영 문서에서 정한다. `code-convention` 의 `project-rules.md` 를 암묵적 출처로 쓰지 않는다 — 그건 코드 스킬의 레퍼런스다.

## §1. 위치와 명명

**성격이 둘로 갈린다 — 기록 문서와 현황판.**

| 성격 | 위치 | 언제 | |
|---|---|---|---|
| **기록 — 계획** | `docs/plan/YYYY-MM-DD-<slug>.md` | 개발 **시작 전** | |
| **기록 — 개발 이력** | `docs/develop-history/YYYY-MM-DD-<slug>.md` | 개발 **완료 후** | |
| **현황판 — 작업 로그** | `docs/work-log/` | 수시 · 마무리루틴 | **형식과 갱신 규칙은 `work-log` 스킬** |

### 기록 문서 — 작업 하나 = 문서 하나

**기존 문서에 누적하지 않고 매번 새로 만든다.**

> 쓰는 시점에 *"기존 문서에 합칠까?"* 를 판단하면 실패 지점이 늘어난다. 그 판단은 나중에 여러 건을 함께 놓고 볼 때가 훨씬 정확하다.
>
> **다만 병합·정리를 어느 스킬도 맡지 않는다.** 사용자가 원할 때 하는 일이지 루틴으로 굳힐 성질이 아니다. **여기서 정하는 것은 「쓸 때 합치지 않는다」까지이고, 나중에 합칠지 말지는 규칙이 아니라 그때의 판단이다.**

### 현황판 — 한 파일에 누적한다

**`docs/work-log/` 는 위 규칙의 대상이 아니다.** 한 파일에 계속 쌓는 것이 그 문서의 본질이다.

**예외가 아니라 대상이 다른 것이다.** 기록 문서는 *"그때 무슨 일이 있었나"* 를 남기므로 건마다 파일이 갈리고, 현황판은 *"지금 어디까지 와 있나"* 를 보여주므로 한 곳에 모여야 한다.

> **`docs/work-log/` 를 만지면 `work-log` 스킬이 원본이다.** 줄 형식 · 갱신 · 보류 해소 · 아카이브 전부 그쪽에 있다. **이 스킬이 정하는 것은 위치와 링크 문법까지다.**
>
> 이 포인터가 필요한 이유는, `docs/work-log/` 도 `.md` 라 **이 스킬이 확정적으로 함께 뜨기 때문**이다. 포인터가 없으면 위 표를 보고 **`docs/develop-history/` 에 새 파일을 만들게 된다** — 하려던 것과 정반대다.

### 폴더명 규칙

- **소문자 · 숫자 · 하이픈만.** 파일 slug 과 같은 규칙이다. 두 단어 이상이면 하이픈으로 잇는다 — `develophistory` 가 아니라 **`develop-history`**
- **대문자를 쓰지 않는다.** Windows·macOS 는 파일명 대소문자를 구분하지 않지만 **Linux 는 구분한다.** 나중에 이름의 대소문자만 바꾸면 git 이 변경을 못 잡거나, Linux 쪽에서 두 폴더가 동시에 존재하는 상태가 된다. WSL 을 경유하는 도구에서도 같은 문제가 난다
- **점으로 시작하지 않는다.** 옵시디언이 dotfolder 를 인덱싱하지 않아 문서가 통째로 안 보인다

**폴더가 없으면 만든다.** 각 폴더에는 `README.md` 가 있어야 한다 — 빈 폴더는 git 에 올라가지 않으므로 README 가 폴더를 남기는 역할을 겸한다. README 에는 **그 폴더가 무엇을 담는 곳인지**만 적고 규칙 본문을 복제하지 않는다. 규칙의 단일 진실원은 이 스킬이다.

> 프로젝트에 **이미 비슷한 이력 문서가 있으면** 덮어쓰거나 무시하지 말고 **관계를 먼저 확인한다.** 기존 것을 그대로 두고 앞으로만 이 규약을 쓸지, 이관할지는 사용자 판단이다.

### slug

파일명의 날짜 뒤 부분이 곧 **인용 키**다. 별도 레지스트리를 두지 않는다.

- **2~4 단어, 30자 이내** kebab-case
- **영문 소문자 · 숫자 · 하이픈만.** 한글 slug 금지 — 파일명은 동작하지만 셸로 텍스트 처리할 때 인코딩 사고가 난다
- 짧되 **의미가 드러나게** — `combo-reset` `enemy-guard-brace`. `fix-1` 같은 무의미명 금지
- 불용어·군더더기 접미 제거 — `and` `the` `of` `for`, 그리고 의미를 좁히지 못하는 `-fix` `-system` `-update`
- 한 문서가 여러 주제를 다뤄도 **대표 주제 하나만** slug 으로 쓴다. 전체 범위는 `title` 과 본문에 적는다

| 나쁜 예 | 좋은 예 |
|---|---|
| `attack-guard-bidirectional-cancel-and-combo-stale-window-fix` (9 단어) | slug `attack-guard-cancel` · title `어택↔가드 양방향 캔슬 + 콤보 stale window 수정` |
| `enemy-downed-getup-flow-stabilization` | `enemy-getup-flow` |

> **4 단어로도 안 좁혀지면 문서가 한 주제가 아니라는 신호다.** 범위를 쪼개 둘로 나눈다.

**유니크 범위** — **같은 네임스페이스 안에서** 유니크하다. `DH:` 끼리, `PLAN:` 끼리 안 겹치면 된다.

- **`PLAN:` 과 `DH:` 는 같은 slug 을 공유하는 것이 정상이다.** 계획(`PLAN:character-dash`) → 개발 → 이력(`DH:character-dash`) 으로 이어지면 짝이 한눈에 보인다
- 충돌은 우연적이라 드물고, 겹치면 **머지에서 파일명 충돌로 드러난다** → 더 구체적인 slug 으로 분기
- 같은 날 같은 slug 이 불가피하면 `-2` · `-3` 접미

### 인용 키

`DH:<slug>` / `PLAN:<slug>`. **번호는 쓰지 않는다.**

> 번호는 "중앙 발급 카운터 × 분산 작업" 구조라 분기에서 충돌이 필연이고, 재번호하면 참조가 깨진다. slug 은 불변이라 참조가 안 깨진다.

## §2. 문서 간 링크

- **표준 마크다운 링크만 쓴다** — `[표시텍스트](./상대경로.md)`
- **`[[wiki-link]]` 금지** — 옵시디언 전용 문법이라 VS Code·GitHub 에서 클릭이 안 된다
- **섹션 앵커(`#heading`) 금지** — 옵시디언과 GitHub 의 슬러그 생성 규칙이 달라 한쪽에서 깨진다

**형식** — 링크 텍스트는 **인용 키**, 링크 대상은 **실제 파일 경로**다.

```markdown
<!-- O -->  콤보 리셋 전이 race 는 [DH:combo-reset](./2026-06-18-combo-reset.md) 참조
<!-- X -->  [[2026-06-18-combo-reset]]
<!-- X -->  DH103 참조
```

slug 이 파일명 본문이라 `*-combo-reset.md` glob 이나 `combo-reset` grep 으로 파일이 바로 잡힌다. 매핑 테이블이 필요 없다.

### 절을 가리켜야 할 때

앵커를 금지했으므로 **절 번호가 앵커를 대신한다.**

> **모든 문서에 절 번호를 붙이라는 뜻이 아니다.** 짧은 문서는 번호 없이 쓴다. 아래는 **절을 참조할 일이 있어 번호를 붙인 문서**에만 적용된다.

- **한번 붙인 절 번호는 재배열하지 않는다.** `§3` 은 개정돼도 `§3` 이다. 절을 추가할 때는 뒤에 붙이거나 `§3.1` 로 파생시킨다
- 절을 가리킬 때는 **번호를 링크 텍스트에 포함**한다 — `[DH:combo-reset §4](./2026-06-18-combo-reset.md)`. 클릭하면 문서가 열리고 절은 `Ctrl+F` 로 찾는다

## §3. 개발 이력 문서

**개발이 끝난 뒤** `docs/develop-history/` 에 남긴다.

```markdown
---
id: DH:<slug>
title: <제목>
date: YYYY-MM-DD
---

# <제목>

| 날짜 | 작성자 | 내용 |
|------|--------|------|
| YYYY-MM-DD | <git user> | 최초 작성 |

## 한 일
- 행위 + 의미

## 판단과 근거
- 왜 그렇게 했나. 대안을 버린 이유

## 검증
- 무엇으로 확인했는가 (명령 · 기준 · 결과)

## 보류 — 나중에 할 것
| 항목 | 왜 미뤘나 | 재개 조건 |
|---|---|---|
| 없음 | — | — |

## 남은 것 / 다음 스텝
```

### 각 절에 무엇을 쓰나

**`## 한 일`** — **행위와 의미**만 쓴다. 어떤 파일을 몇 줄 고쳤는지는 **쓰지 않는다.** diff 에 이미 있다.

**`## 판단과 근거`** — 결과뿐 아니라 **버린 대안과 그 이유**를 함께 적는다. 근거가 없으면 다음 사람이 같은 논의를 반복한다.

**`## 검증`** — 확인한 것만 적는다. **확인하지 못한 것은 여기 적지 말고 `## 보류` 로 내린다.**

**`## 보류`** — 이 포맷의 핵심이다. **"나중에 하자"가 여기 적히지 않으면 증발한다.**

- **왜 미뤘는지와 어떤 조건이면 재개하는지를 함께** 적는다. 조건이 없으면 나중에 판단할 근거가 없다
- **보류가 없으면 `| 없음 | — | — |` 행을 남긴다.** 절을 지우거나 헤더만 두지 않는다 — 읽는 쪽이 "보류 없음"과 "절을 안 썼음"을 구분하지 못한다
- **보류 항목을 하나라도 추가하면 `| 없음 | — | — |` 행은 삭제한다.** 둘이 함께 남으면 "없음"과 "있음"이 동시에 표기된다
- 표는 **사람과 에이전트가 읽는 것**이지 기계 파싱 대상이 아니다. 셀 안에 자연어를 자유롭게 쓴다

#### 처리한 보류는 취소선으로 닫는다 ★

**항목에 취소선을 긋고, 「재개 조건」 칸을 해소 기록으로 바꾼다.**

```markdown
| ~~Project_A 스킬 권한 2건 누락~~ | 배포 대상 저장소를 고치는 일이라 범위 밖이었다 | ✅ **해소 (2026-08-25)** — [DH:session-routine](./2026-08-25-session-routine.md) |
| 진입점 §0 자체의 다이어트 | §0 은 더 줄일 여지가 있다 | 예산이 다시 빡빡해질 때 |
```

- **「왜 미뤘나」에는 취소선을 긋지 않는다.** 그게 기록이고, 취소선까지 치면 읽을 수 없다
- **「재개 조건」은 해소되면 무의미하다** — 이미 재개해서 끝냈기 때문이다. 그 자리에 **날짜와 해소한 문서 링크**를 넣는다. 보류를 적은 문서와 해소한 문서가 다른 경우가 많다
- **행을 지우지 않는다.** 지우면 *"왜 없어졌는지"* 를 알 수 없다. 상태를 갱신하는 것과 기록을 없애는 것은 다르다
- **칸을 늘리지 않는다.** 상태 칸을 추가하면 기존 문서와 칸 수가 어긋나고, 맞추려면 과거 기록을 전부 고쳐야 한다
- **행이 전부 취소선이 돼도 `| 없음 | — | — |` 을 다시 넣지 않는다.** 취소선 행이 있다는 것 자체가 "보류가 있었다"를 말한다

> **왜 이 규칙이 필요한가** — 개발 이력은 **그때의 판단을 남기는 불변 기록**이다. 행을 지우면 *"왜 없어졌는지"* 를 알 수 없고, **상태를 갱신하는 것과 기록을 없애는 것은 다르다.**
>
> **처리한 항목이 브리핑에 계속 뜨는 것을 막는 역할은 `docs/work-log/` 가 맡는다.** 열린 보류의 **현황**은 그쪽에 있고, 여기 보류 표는 **당시 기록**이다. 둘은 대상이 다르다 (§1 「현황판」).
>
> **언제 닫는가는 `session-routine` 소관이다** (마무리 4단계). 이 절은 *어떤 형식으로* 닫는지만 정한다.

**변경 이력 표** — 문서를 고칠 때마다 행을 추가한다. **작성자 칸은 세션 컨텍스트의 `Git user:` 값을 그대로 쓴다.** 예시를 따라 쓰지 않는다.

### 제외한 것도 적는다

기획·사양에 있지만 **이번 개발에서 뺀 항목과 그 사유**를 함께 기록한다. 사유에는 *"왜 지금 안 하는지"* 와 *"어떤 조건이 충족되면 하는지"* 를 넣는다.

> 예 — `보스 전용 무적 처리: 현재 보스 적이 없어 대상 없음 → 보스전 기획 확정 후 구현`

## §4. 계획 문서

**개발을 시작하기 전에** `docs/plan/` 에 쓴다.

**`작업 → 검증` 형식은 실행 계획에만 적용한다.**

```
1. [작업] → 검증: [확인 명령/기준]
```

- **각 단계마다 검증 방법을 명시**한다. 검증이 붙는 형식이라 **검증 없는 완료 주장**이 구조적으로 막힌다
- **비싼 검증은 마지막에 통합**한다 (패키징 빌드 30분+, 풀 플레이 테스트 5분+)

**절차를 지시하지 않는 문서는 자유 서술이다** — 리뷰 · 브리핑 · 회고 · 설계 설명 · 사양서 · 개발 이력. 이들에 단계별 검증을 요구하면 형식만 남고 내용이 빈다.

### 질문 우선

- 사용자가 명시하지 않은 가정이 계획에 **1건 이상** 들어가면 **질문으로 분리**한다. 0건이면 면제
- 1줄 수정 · 오타 · 로그 추가 · 명시된 컴파일 에러 수정 같은 **자명한 작업은 질문 면제**
- **답을 알면서 승인만 받으려는 안전빵 질문은 하지 않는다**

## §5. 문서 검증 — 무엇을 확인하나

문서를 고친 뒤 확인할 것은 넷이다.

| 확인 | 왜 |
|---|---|
| **갱신 누락된 참조** | 경로·이름을 바꾸면 다른 문서가 옛 값을 가리킨다 |
| **상대 링크 유효성** | 링크 대상 파일이 실제로 존재하는가 |
| **stale 경로** | 지운 문서를 아직 가리키는 곳이 있는가 |
| **slug 중복** | 인용 키에 날짜가 없으므로 slug 이 겹치면 참조가 애매해진다 (§1) |

**명령은 고정하지 않는다.** `rg` 가 없는 환경이 있고, PowerShell 과 Bash 의 정규식 이스케이프가 다르다.

```bash
# 예시 (Git Bash). 환경에 맞게 바꾼다
rg "옮긴-경로|바뀐-이름"
rg -o "\]\(\./[^)]+\)" docs
```

> **명령을 고정하지 않는 것이 확인을 면제한다는 뜻은 아니다.** 그 환경에서 **쓸 수 있는 도구로 반드시 확인한다.** 확인하지 못했으면 확인했다고 쓰지 않는다.

**검증을 언제 실행하는지는 `session-routine` 소관이다.** 본 절은 *무엇을 확인하는가*만 정한다.

## 하지 말 것

- **파일·줄 수를 이력 본문에 나열하기** — diff 에 있다
- **`[[wiki-link]]` · 섹션 앵커 사용** — 도구 한쪽에서 깨진다
- **인용에 번호 쓰기** — 재번호 시 참조가 깨진다
- **`## 보류` 절 삭제** — 보류가 없어도 `| 없음 | — | — |` 를 남긴다
- **확인하지 않은 것을 `## 검증` 에 적기** — 보류로 내린다
- **기존 문서에 누적하기** — 작업마다 새 문서다
- **처리한 보류를 행째로 지우기** — 취소선으로 닫고 해소 기록을 남긴다 (§3)
- **`docs/work-log/` 를 여기 규칙으로 판정하기** — 위치와 링크 문법만 이 스킬이고, 나머지는 `work-log` 스킬이다 (§1)

> **`docs/work-log/` 의 `## 열린 보류` 는 위 첫 항목의 대상이 아니다.** 거기서는 처리한 보류의 **줄을 지우는 것이 맞다** — 현황판이라 열린 것만 남긴다. 기록은 개발 이력에 취소선으로 영구히 남는다.
>
> **단 무조건 허용이 아니다.** **개발 이력의 취소선 갱신이 성공한 뒤에만** 지운다. 순서를 뒤집으면 *"줄만 지우고 취소선을 안 함"* 이 되는데, 그 실패는 **증상이 없어 영원히 발견되지 않는다.** 조건은 `work-log` §3.2 가 원본이다.
