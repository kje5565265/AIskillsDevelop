# session-routine

하루의 **시작과 끝**에 도는 절차를 지휘한다. **규약은 갖지 않고 다른 스킬을 호출한다.**

- **§0 발동 기준** — 언제 뜨나, 애매하면 어떻게 하나
- **§1 아침루틴** — 받고, 무엇이 바뀌었는지 알리고, 지난 기록을 올린다
- **§2 마무리루틴** — 디버그를 걷어내고, 올리고, 기록한다
- **§3 완료 정의** — 중간 상태를 정확히 남긴다
- **§4 테스트 로그** — 언제 지우나 (절차는 `code-convention`)

> **규약을 요약해서 옮기지 않는다.** 문서 형식은 `document-convention`, 깃 절차는 `git-procedure` 가 원본이다. **"해당 스킬을 읽고 계속한다"고만 지시하고, 그 내용을 여기서 다시 쓰지 않는다.** 요약하면 원본이 바뀔 때 이쪽이 조용히 낡는다.

---

## §0. 발동 기준 — 「사용자 발화」

**다른 스킬과 축이 다르다.** `code-convention`·`document-convention` 은 **건드리는 파일**로, `git-procedure` 는 **실행하는 명령**으로 발동한다. 이 스킬은 **사용자가 그렇게 말했을 때만** 뜬다.

**발화가 없으면 뜨지 않는다. 그것이 의도다.** 파일이나 명령으로 발동하면 아무 작업에나 루틴이 끼어든다.

| 루틴 | 발화 |
|---|---|
| **아침** | *"시작루틴 하자"* · *"아침루틴"* · *"이어서 하자"* |
| **마무리** | *"마무리루틴 하자"* · *"오늘 마무리"* · *"정리하고 올리자"* |

**줄여 말한 것도 잡는다** — *"마무리"* · *"정리하자"* · *"이어서"*.

**단순 질문은 트리거가 아니다.** *"어제 뭐 했지"* 는 **질문이지 루틴 실행 지시가 아니다.** 물어봤을 뿐인데 원격에서 받아오면 안 된다. 이런 발화는 그냥 답하면 된다.

**작업 기록만 남기는 발화도 루틴이 아니다.** *"오늘 작업 남겨줘"* · *"작업 기록해줘"* · *"어디까지 했는지 남겨줘"* 는 **`work-log` 만 뜨면 된다.** 어휘가 마무리 발화와 겹치지만(*"오늘 마무리"* ↔ *"오늘 작업 남겨줘"*), **하려는 일이 다르다** — 로그 한 줄이지 로그 제거·올리기·이력 작성이 아니다.

> **이 한 줄이 없으면 §0.1 의 되묻기가 매번 걸린다.** 작업 기록은 **수시로, 마찰 없이** 남기는 것이 설계 의도인데, 하루에 몇 번씩 *"어떤 마무리를 말씀하신 건가요?"* 를 받으면 **§0.1 이 스스로 경고한 대로 확인을 생략하는 쪽으로 흐른다.**

### §0.1 애매하면 실행 전에 묻는다

발화가 잡혔는데 **어느 루틴인지, 어디까지 하라는 것인지 애매할 수 있다. 추측해서 실행하지 않는다.**

1. 저장 안 한 변경과 최근 대화 맥락을 보고 **먼저 판단해본다**
2. 그래도 애매하면 **선택지를 제시하고 확인받는다**

```
"마무리하자"
  → 저장 안 한 변경에 코드 수정이 있다
  → "어떤 마무리를 말씀하신 건가요?
       ① 마무리루틴 전체 (로그 제거 → 올리기 → 이력 작성)
       ② 지금 것만 저장하고 올리기"
```

**이미 명확한 지시는 되묻지 않는다.** *"마무리루틴 하자"* 는 애매하지 않다. 되묻는 마찰이 반복되면 다음엔 확인을 생략하는 쪽으로 흐른다.

### §0.2 다른 스킬과 함께 뜬다

마무리 발화에는 깃 신호가 섞이는 일이 많다 (*"정리하고 올리자"*). **여러 스킬이 동시에 해당하면 모두 로드한다.** 깃 쪽만 뜨고 이 절차가 빠지면 로그 제거와 기록이 통째로 스킵된다.

## §1. 아침루틴

**하는 일은 둘이다** — ① 내가 없는 사이 뭐가 바뀌었는지 알리고, ② 지난 작업 기록을 올린다.

```
1. 받아올 것이 내 작업과 겹치는지 본다   ← 게이트
2. 받는다                               → git-procedure
3. 새로 들어온 것 정리해서 보고
4. docs/work-log/work-log.md + 개발 이력 최신 1건을 읽는다
5. 보류 수집 → 기록 상태 → 브리핑 → 다음 작업 제안
```

> **1~3 과 4~5 는 독립이다.** 받기는 깃 상태를 타지만 **작업 로그 읽기와 브리핑은 깃과 무관하다. 게이트에 걸려 받기를 멈춰도 4·5 는 진행한다.** 게이트마다 루틴이 통째로 죽으면 사용자가 게이트를 우회하게 된다.

### 1단계 — 겹치는지 본다

**`git-procedure` 의 받기 전용 흐름을 그대로 탄다.** 겹침 판정 · 합칠 수 있을 때의 확인 · 중단 문구가 전부 거기 있다.

**여기에 요약해서 옮기지 않는다.** 아침이라서 필요한 게 아니라 **커밋 단계를 건너뛰는 모든 받기에 필요한 것**이라, 원본은 그쪽이다. 아침루틴만 특별한 게이트를 갖는 형태가 되면 *"받아줘"* 라고만 한 사람은 보호받지 못한다.

**아침루틴이 여기에 더하는 것은 하나뿐이다.**

> **받기가 중단돼도 브리핑은 진행한다.** 받기와 브리핑은 별개이고, 겹쳤다고 오늘 할 일까지 못 보게 만들 이유가 없다.

```
오늘 할 일 브리핑은 아래에 이어서 드립니다.
```

### 2·3단계 — 받고, 무엇이 들어왔는지 말한다

받기는 `git-procedure` 의 **받기 전용 흐름**을 탄다 — 커밋·푸시를 하지 않는다.

**비교 기준을 git 이 남기는 표시에 맡기지 않는다.** ★

```
① 받기 전에 현재 위치를 기억해둔다
② 받는다
③ 위치가 그대로면  → "새로 들어온 것 없습니다" 로 끝낸다
   움직였으면      → ①에서 기억한 값과 지금을 비교한다
```

> git 은 「받기 직전 위치」 표시(`ORIG_HEAD`)를 **실제로 뭔가 받았을 때만** 갱신한다. **받을 게 없는 날에는 지난번 값이 그대로 남아**, 그 표시를 쓰면 **어제 받은 것과 그 뒤 내가 만든 커밋까지 「오늘 새로 들어온 것」으로 보고**하게 된다.

보고할 때는:

- 파일 목록을 그대로 붙이지 않는다. **무엇이 바뀌었는지를 말로** 옮긴다
- 자동으로 합쳐진 에셋이 있으면 `git-procedure` 의 **조용한 머지 보고**를 따라 함께 알린다

### 4단계 — 작업 로그와 개발 이력 최신 1건을 읽는다

**둘을 읽는다. 개발 이력을 여러 건 훑지 않는다.**

| 읽는 것 | 무엇을 얻나 |
|---|---|
| `docs/work-log/work-log.md` | 최근 작업 · **열린 보류 전부** |
| **개발 이력 최신 1건** | `## 남은 것 / 다음 스텝` · 어제 판단의 근거 · **작업 로그 갱신 누락 탐지** |

> **왜 개발 이력을 1건은 읽나** — 「추가 정보」가 아니라 **교차 검증** 때문이다. 작업 로그 갱신이 누락돼도 개발 이력을 읽으면 드러난다. 그리고 **보류와 「다음 스텝」은 다른 것**이다 — 보류는 *"미룬 것"*, 다음 스텝은 *"이어서 할 것"* 이고, 5단계 선택지의 재료가 둘 다다. 작업 로그만 읽으면 **「어제 하던 것 이어서」가 브리핑에서 사라진다.**
>
> **왜 10건이 아닌가** — 개발 이력이 200건을 넘으면 최근 10건이 **약 16K 토큰**이고, 그것이 **그 세션의 모든 턴에 프리픽스로 다시 실린다.** 보류는 이제 작업 로그에 모여 있으므로 여러 건을 읽을 이유가 없다.

- 더 펼쳐야 하면 작업 로그의 링크를 따라간다. **한 번에 최대 3건.** 색인을 만들어놓고 결국 여러 건을 여는 것이 이 구조의 실패 방식이다
- **검색은 깃이 추적하는 파일만 대상으로 한다.** 빌드 캐시·중간 산출물을 훑지 않는다

### 5단계 — 보류와 기록 상태를 모아 브리핑한다

**4단계에서 읽은 내용에서 뽑는다.** 문서를 이미 읽었으므로 필요한 것이 전부 들어와 있다.

> **셸 검색으로 대체하지 않는다.** 저장소 문서는 **한글이고 BOM 이 없어**, PowerShell 5.1 로 검색하면 시스템 기본 인코딩으로 읽혀 **에러 없이 「0건」이 나온다.** 보류가 있는데 *"보류 없음"* 으로 브리핑되고 아무도 눈치채지 못한다. 문서가 늘어 무거워져도 **셸 검색으로 갈아타지 않는다.**

#### 기록 상태 — 세 겹으로 본다

**기준일은 「어제」가 아니라 `## 최근 작업` 최상단 줄의 날짜다** (= 마지막으로 일한 날).

> 「어제」로 잡으면 **월요일 아침마다 *"개발 이력 미작성"* 오탐**이 난다 — 어제가 일요일이니 당연히 `✅` 가 없다. **오탐이 반복되면 브리핑이 무시되고, 그 순간 세 겹이 동시에 죽는다.**

| 겹 | 검사 | 어긋나면 |
|---|---|---|
| ① | 그 날짜에 **`✅` 줄이 하나도 없다** | 개발 이력 미작성. 브리핑에 올린다 |
| ② | 그 날짜의 **`develop-history/` 파일명 집합** ↔ 작업 로그 그 날짜 줄의 **`✅` 링크 집합** | **개발 이력은 있는데 `✅` 없음** → 마무리 줄 누락. 지금 추가할지 묻는다<br>**`✅` 링크가 가리키는 파일이 없음** → 더 심각. **멈춰서 확인** |
| ③ | 개발 이력 최신 1건의 보류 표에 **취소선 없는 행**이 있는데 작업 로그 `## 열린 보류` 에 대응 줄이 없다 | **이관 누락.** 브리핑에 올린다 |

**셋 다 비용이 0 이다.** ①③은 이미 읽은 내용이고, ②는 **디렉터리 목록만 읽는다** — 파일명에 날짜가 있고 slug 이 ASCII 라(`document-convention` §1) 내용을 열지 않고 대조되며 인코딩 사고도 없다.

> **②가 「최신 1건」이 아니라 「집합」인 이유** — 최신 1건은 마무리루틴이 직후에 `✅` 를 붙인 것이라 **거의 항상 통과한다.** 하루에 여러 건을 썼을 때의 누락을 잡으려는 것인데, 1건만 보면 **정확히 그 경우를 비껴간다.**

```
최근 작업
- 09-09  인벤토리 정렬 수정                       DH:inventory-sort-fix
- 09-09  정렬 비교 함수 동점 처리 추가

기록 상태
- 09-09 개발 이력 2건 중 1건이 작업 로그에 없습니다 — 설정 화면 레이아웃 정리

보류 중인 것 2건
- [06-14] framework-dotnet 보강 — 재개 조건: 실제 .NET 코드를 볼 수 있을 때  (3개월 열림)
- [09-04] 시즌 리셋 처리 — 재개 조건: 시즌 기획 확정 후

먼저 진행할까요?  ① dotnet 보강  ② 시즌 리셋  ③ 새 작업
```

**「기록 상태」 줄은 이상이 없어도 자리를 비우지 않는다** — *"기록 상태 이상 없음"* 을 적는다. **출력 자리가 없으면 검사가 조용히 스킵된다.** 2단계 재검사에서 이미 쓴 논리다.

**게이트 강도 = 소프트.** 브리핑하고 제안까지 하되, 사용자가 다른 걸 시키면 그대로 따른다.

## §2. 마무리루틴

```
0. 완료 검증                     ← 증거 확보
1. 테스트 로그 제거               → code-convention
2. 작업물 재검사                  ← 필수
3. 작업물 깃 작업                 → git-procedure
4. 개발 이력 작성 + 보류 갱신      → document-convention
4.5 문서 재검사                   ← 필수
5. 문서 깃 작업                   → git-procedure
```

**개발 이력은 작업물을 올린 뒤에 쓴다.** 문서에 *"마무리했다"* 고 먼저 써놓고 정작 결과물을 올리다 막히면 **기록이 거짓이 된다.**

**로그 제거는 사용자가 따로 지시하지 않아도 한다.** 마무리 발화를 받으면 **먼저 알리고 지운다.**

> 이 작업은 완료됐으니 방금 심은 테스트 로그를 삭제하겠습니다.

### 0단계 — 완료 검증

**「검증」을 둘로 나눈다. 에이전트가 할 수 있는 것과 없는 것이 다르다.** ★

| 무엇을 확인 | 누가 | 못 했을 때 |
|---|---|---|
| **컴파일이 통과하는가** | **에이전트** — 엔진 재컴파일·콘솔 확인 또는 IDE 빌드 | **여기서 멈춘다.** 실제로 할 수 있으므로 정당한 게이트다 |
| **의도대로 동작하는가** | **사용자** — 실행해보고 확인 | **멈추지 않는다.** `## 보류` 에 *"동작 확인 미실시"* 를 남기고 진행. 사용자가 확인했다면 **출처를 밝혀** 기록 |
| 문서·스킬만 바꿨을 때 | 에이전트 | 실행 검증 불필요. `document-convention` 의 문서 검증 항목을 확인 |

> **못 하는 것을 요구하면 매번 멈추고, 그러면 우회 해석이 자리잡는다** — *"컴파일 에러가 없으니 확인된 걸로 본다"* 같은 것이. **그게 §3 이 막으려는 거짓 기록이다.** 지킬 수 있는 선으로 낮추는 것이 목적을 지키는 길이다.

**검증 명령을 여기서 고정하지 않는다.** 무엇을 확인하는가는 `document-convention` 이 정하고, **언제 확인하는가만** 이 절차가 정한다.

스킬을 고쳤으면 **마스터와 복사본의 일치 확인**도 이 단계에서 한다.

### 2단계 · 4.5단계 — 재검사 (필수)

**변경 목록을 다시 실행하고 그 출력을 답변에 남긴다. 기억으로 대체하지 않는다.**

> *"다시 확인한다"* 로만 하면 방금 본 것을 또 보라는 말이라 *"직전에 확인했다"* 로 넘어간다. **출력을 남기면 안 돌린 것이 드러나므로 실제로 돌린다.**

- **2단계** — 변경 목록 + `AITESTLOG_` 잔존 여부
- **4.5단계** — 변경 목록 + `document-convention` 의 문서 검증 항목

### 4단계 — 개발 이력 · 보류 · 작업 로그 갱신

문서 작성은 `document-convention` 을, 작업 로그의 줄 형식은 `work-log` 를 따른다. 여기서는 **시점과 순서**만 정한다.

**이어지는 작업이면 기존 문서를 이어 쓴다.** 10일에 시작해 11일에 끝난 작업은 **한 작업이므로 문서도 하나**다.

#### 내부 순서를 고정한다 ★

```
① 개발 이력 작성
② 보류 해소   — 취소선 갱신 → 성공 후 작업 로그 줄 삭제
③ 새 보류 올리기 — 개발 이력 보류 표에 적은 것을 작업 로그에도 한 줄
④ 마무리 줄 추가 — 작업 로그에 ✅ + 개발 이력 링크
⑤ 아카이브 검사 — 20KB 초과면 오늘 줄만 남기고 옮긴다
```

**순서가 없으면 ⑤가 먼저 돌다가 아직 정리 안 된 보류 줄을 함께 옮길 수 있다.** ②가 앞이고 ⑤가 마지막이면 *"열린 보류는 이미 정리됐고 이제 안 건드린다"* 가 자연스럽다.

**②의 순서는 뒤집지 않는다.** 두 동작 중 하나만 되는 경우가 **비대칭**이기 때문이다 — 「취소선만 하고 줄을 안 지움」은 다음 아침 브리핑에 떠서 발견되지만, **「줄만 지우고 취소선을 안 함」은 증상이 없어 영원히 발견되지 않는다.** 상세와 멱등 처리는 `work-log` §3.2 가 원본이다.

#### 처리한 보류를 그 자리에서 완료로 갱신한다 ★

- 이번 작업이 **과거 문서의 보류를 처리했으면**, 그 문서를 열어 해당 항목을 닫고 변경 이력에 한 줄 남긴다. **닫는 형식은 `document-convention` §3 의 취소선 규칙**이다
- 별개 작업이라 새 문서를 썼더라도 **원래 보류가 적혀 있던 문서를 갱신한다**
- **개발 이력의 취소선은 기록을 남기는 것이고, 작업 로그의 줄 삭제는 현황을 반영하는 것이다.** 둘 다 한다

> **「지난 문서를 고쳐 쓰지 않는다」와 구분한다.** 그건 **이미 쓴 내용을 바꾸지 말라**는 뜻이다. **보류의 상태를 갱신하는 것은 기록을 바꾸는 것이 아니라 현재 상태를 반영하는 것**이다.

> **작업 로그 갱신이 끝나야 4단계가 끝난 것이다.** ②~⑤ 중 하나라도 빠지면 다음 아침 브리핑이 틀린 채로 정상처럼 나온다.

### 각 단계의 게이트

| 단계 | 게이트 |
|---|---|
| 0 검증 | **컴파일이 안 통과하면 중단.** 동작 확인은 못 해도 중단하지 않고 보류로 |
| 1 로그 제거 | `code-convention` Part D 의 게이트를 그대로 따른다 — 마커 없는 의심 항목은 **목록만 제시하고 확인**, 블록 삭제는 **범위 미리보기 후** |
| 2 재검사 | 누락 발견 시 1로 되돌아감. **출력을 남기지 않았으면 안 한 것으로 본다** |
| 3 작업물 깃 | `git-procedure` 의 멈춤 조건을 따른다. 실패하면 개발 이력을 쓰지 않는다. **단 애매하게 끝난 올리기는 실패로 보지 않는다** (§3) |
| 4 문서 작성 | 작업물 올리기가 성공했을 때만. **보류 갱신과 작업 로그 갱신을 함께 한다** — 내부 순서 ①~⑤ 를 지킨다 |
| 4.5 재검사 | 누락 발견 시 4로 되돌아감 |
| 5 문서 깃 | `git-procedure` 의 멈춤 조건을 따른다 |

## §3. 완료 정의 — 중간 상태를 정확히 남긴다

**"완료"의 기준은 사용자가 요청한 범위다.**

| 상황 | 개발 이력에 무엇을 쓰나 |
|---|---|
| 요청 범위 전부 완료 | `## 검증` 에 결과 |
| 사용자가 **"커밋만"** 을 명시 | *"로컬 저장 완료 (올리기는 요청 범위 밖)"* — **정상 종료다** |
| 올리려다 **막힘** | *"로컬 저장 완료 / 원격 반영 보류"* + `## 보류` 에 재개 조건 |
| 검증 일부만 됨 | `## 보류` 에 *"검증 못 한 것 + 이유"* |

**"막힘"과 "요청 범위 밖"을 구분하는 것이 핵심이다.** 둘 다 원격에 안 올라간 상태지만, 전자는 다음 날 이어서 할 일이고 후자는 정상 종료다. **구분하지 않으면 아침 브리핑이 거짓이 된다.**

**작업물 올리기가 막히면 개발 이력을 쓰지 않는다.** 작업이 끝났다고 말할 근거가 없다.

### 애매하게 끝난 올리기를 실패로 판정하지 않는다 ★

대용량 파일이 섞인 첫 올리기는 **수 분이 걸리는데 도구 기본 제한은 2분**이라, **시간 초과가 「실패」로 보인다.** 오판하면 실제로는 올라갔는데 *"막힘"* 으로 분류되어 **개발 이력을 아예 안 쓰게 된다.**

> **불명확하게 끝난 올리기는 실패로 판정하지 않는다.** `git-procedure` 대로 **원격 상태를 다시 확인한 뒤** 판정한다.

### 문서 올리기만 막힌 경우

**개발 이력은 드물다.** 매번 새 파일이라 충돌 여지가 거의 없다. 별도 규칙을 두지 않고 평문으로 보고하되, **작업물은 이미 올라갔다는 사실을 분명히 한다.**

> **`docs/work-log/work-log.md` 는 다르다. 거의 항상 충돌한다.** ★
>
> **단일 파일 · 매일 · 최상단 추가**라 위 전제(*"파일이 매번 다르다"*)가 성립하지 않는다. 둘 이상이 같은 날 쓰면 같은 구간을 건드린다.
>
> **양쪽 줄을 모두 살리고 시각 순으로 정렬만 한다.** 한쪽을 버리지 않는다 — 갱신이 없는 구조라 **두 줄이 서로 배타적일 수가 없고, 둘 다 사실이다.** 상세는 `work-log` §5.

> 오늘 작업한 내용은 모두 올라갔습니다. **기록 문서만 아직 올리지 못했습니다.**

## §4. 테스트 로그 — 시점만 정한다

**마무리 1단계에서 제거한다.** 그것이 이 스킬이 정하는 전부다.

**마커 형식 · 심는 규칙 · 제거 절차 · 블록 삭제 안전 규칙은 전부 `code-convention` Part D 가 원본이다.** 로그를 심는 것도 지우는 것도 **소스 파일 편집**이므로 그쪽 소관이며, 그 스킬은 로그를 만지는 순간 함께 뜬다.

**여기에 요약해서 옮기지 않는다.** 마커 형식은 바뀔 수 있고, 사본이 있으면 조용히 낡는다.

**로그 제거는 사용자가 따로 지시하지 않아도 한다.** 마무리 발화를 받으면 먼저 알리고 지운다 (§2).

## §5. 보고

**모든 사용자 대면 문구는 평문으로 쓴다.** 깃 용어를 그대로 노출하지 않는다 — 원본은 `git-procedure` 다.

- 파일은 **경로 대신 이름과 종류**로 — `Assets/Prefabs/Player.prefab` → *"Player 프리팹"*
- **다음에 무엇이 필요한지 한 줄로 끝맺는다.** 상태만 알리면 사용자가 무엇을 해야 할지 모른다

## 하지 말 것

- **추측해서 루틴을 실행하기** — 애매하면 선택지를 내고 확인받는다 (§0.1)
- **단순 질문에 받기까지 실행하기** — *"어제 뭐 했지"* 는 답만 한다
- **임의로 저장하거나 치워두기** — 사용자의 명시 지시까지 대기한다
- **중단 문구에 「보관·되돌리기」를 선택지로 내밀기** — 금지된 조작을 AI 가 먼저 권하지 않는다
- **검증하지 못한 것을 완료로 쓰기** — 확인 못 한 것은 보류로 내린다
- **재검사를 기억으로 대체하기** — 출력을 답변에 남긴다
- **다른 스킬의 명령·규약을 여기에 복제하기** — 원본이 바뀌면 조용히 낡는다

> 위 항목 중 **「임의로 저장하거나 치워두기」는 이 저장소 진입점 문서의 안전망 절이 원본**이다. 이 스킬이 로드되지 않아도 지켜져야 하므로 그쪽에 있으며, 여기서는 절차 맥락에서 다시 짚는 것이다. **문구가 어긋나면 진입점 쪽이 맞다.**
