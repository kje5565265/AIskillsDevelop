# project-report

추적 중인 여러 프로젝트의 **새 커밋을 모아, 개발을 모르는 사람(대표 등)도 읽을 수 있는 현황 보고서(HTML 파일 하나)** 로 만든다. 주 독자이자 검수자는 **스킬을 부른 사람**이고, 대표는 그 사람이 공유한 것을 본다.

> ⚠️ **AI_Develop 전용이다. 실 프로젝트에 배포되지 않는다.** 설계와 근거는 `docs/skills/project-report/plan.md` — 여기에 복제하지 않는다.

> **어느 조직에서든 쓴다.** 스킬에는 조직 정보가 없다. **추적할 프로젝트는 PC 마다 로컬 설정에 등록한다** — `~/.project-report/config.json`, 저장소에 커밋하지 않는다 (§3).

- **§0 언제 · 무엇을** — 부르는 말과 경계
- **§1 절차** — 수집 → 보고서 → 기준점
- **§2 보고서 쓰는 법** — 대표가 읽는다
- **§3 등록과 설정** — 추적할 프로젝트 · 대응표

---

## §0. 언제 · 무엇을

| 말 | 동작 |
|---|---|
| `/project-report` · *"프로젝트 현황 보고해줘"* | **지난 보고 이후**를 새로 보고한다 |
| *"<프로젝트> 현황 보고해줘"* (등록한 별칭도 된다) | **그 프로젝트만** 보고하고 그 기준점만 옮긴다 |
| *"다시 해줘"* | **마지막 보고의 범위를 그대로** 다시 만든다. 기준점은 움직이지 않는다 |
| *"이름 넣어서 보고해줘"* | 작업자 이름을 넣는다. **기본은 넣지 않는다** |
| *"○○ 빼줘"* · *"이 문장 고쳐줘"* | 같은 보고서 파일을 고친다. 기준점은 움직이지 않는다 |
| *"이 저장소도 추적해줘"* · *"○○ 빼줘(추적에서)"* · *"추적 목록 보여줘"* | 로컬 설정에 등록 · 해제 · 조회한다 (§3) |

**경계**

- **「작업기록」이 들어가도** 보고 · 대표 · 현황, 또는 등록한 프로젝트 이름(설정의 `name` · `aliases`)과 함께 나오면 이 스킬이다. 이 저장소의 `docs/work-log/` 에 적는 일이 아니다
- **「올려줘」가 메신저 게시를 뜻하면** 보고서만 만든다. **커밋 · 푸시 · 게시를 하지 않는다** — 공유는 부른 사람이 검수한 뒤 직접 한다
- **작업 저장소(사람이 개발하는 클론)는 읽지도 받지도 않는다.** 기록은 설정의 `baseDir` 아래 `mirrors/` 의 보고 전용 복제본에서만 읽는다. **pull 은 어디서도 하지 않는다**

## §1. 절차

**git 출력을 셸로 읽지 않는다.** 수집은 이 스킬 폴더의 `scripts/collect.mjs` 가 한다 — git 출력을 UTF-8 로 직접 받아 파일로 떨군다. PowerShell 5.1 을 거치면 한글 커밋 메시지가 깨지고, 깨진 글자를 해석하면 지어낸 보고가 된다.

```
⓪ 설정 확인  node <스킬 폴더>/scripts/collect.mjs list
             설정이 없거나 프로젝트가 0개면 멈추고 §3 으로 등록을 안내한다
① 수집      node <스킬 폴더>/scripts/collect.mjs report [--project <key>]
            (다시 해줘 → redo [--project <key>])
② 읽기      출력된 요약본(.md)을 네이티브 Read 로 읽는다. 전체 JSON 은 근거 확인이 필요할 때만
③ 보고서    references/report-template.html 을 채워
            <baseDir>/reports/<YYYY-MM-DD-HHmm>.html 로 저장한다 (다시 해줘면 파일명 끝에 -redo)
④ 기준점    node <스킬 폴더>/scripts/collect.mjs commit <①의 수집 JSON>
            ← report 일 때만. redo · 고쳐 다시 만들기에서는 하지 않는다
⑤ 알림      채팅에는 「한눈에」 요약과 보고서 파일 위치만 낸다
```

- **보고서는 HTML 파일 하나다.** 파일 하나로 어디서든 열린다(스타일이 파일 안에 있다). 공유도 이 파일을 그대로 보낸다
- **④는 ③이 끝난 뒤에만 한다.** 중간에 실패하면 기준점이 그대로라 다음 요청이 같은 범위를 다시 본다
- **fetch 가 실패한 프로젝트**는 요약본에 `! fetch 실패` 로 나온다 — 보고서에 *"최신 아님 — ○월 ○일 ○시 기준"* 을 적는다. 계정 문제(`auth`)면 부른 사람에게 알린다
- **요약본에 `!` 로 시작하는 줄**(기준점 손상 · 사라진 브랜치)은 전부 보고서에 반영한다 — 손상은 머리에 *"이전 보고와 겹칠 수 있음"*, 합쳐지지 않고 사라진 브랜치는 주의 신호로
- 프로젝트를 고를 때는 설정의 `key` · `name` · 별칭을 쓴다 — `list` 로 확인한다

## §2. 보고서 쓰는 법 — 대표가 읽는다

**원칙: 무엇이 바뀌었고, 그게 왜 중요한지를 개발 용어 없이.**

### 구성 — 첫 화면에 판단할 것이 다 보이게

```
기간 · 고정 문구 「아래는 개발 진행 내용이며 출시 여부와는 별개입니다.」
한눈에           프로젝트마다 한 줄
확인해 보실 것   ← 한눈에 바로 아래. 끝에 두면 끝까지 읽어야 보인다
프로젝트마다     핵심 → (버전별 반영 표) → 그 밖
근거와 확인할 점  ← 맨 아래. 검수용
```

- **프로젝트는 설정의 `name` 으로 쓴다**(보통 실제 폴더 이름). 별칭(`aliases`)은 부르는 말을 알아듣는 데만 쓰고 보고서에는 쓰지 않는다
- **이번 범위에 커밋이 없는 라인은 쓰지 않는다.** 프로젝트 전체가 변동 없으면 「한눈에」에 *"변동 없음"* 한 줄
- **본문에 브랜치 원래 이름을 쓰지 않는다** — 필요하면 쉬운 이름(설정의 `platform`), 원래 이름은 「근거와 확인할 점」에만

### 프로젝트 — 핵심과 그 밖

- **핵심은 2~3개.** 굵은 한 문장 + 아래 작은 글씨로 구체 내용. 고르는 기준은 대표에게 중요한 순서 — 수익(유료 상품 · 광고 · 결제) · 새 콘텐츠 · 큰 화면 개편 · 이용자가 겪는 문제 해결 · 진행 중인 큰 조정
- **그 밖은 분류별 한 줄.** `밸런스` · `버그 수정` · `화면` · `수익` · `안정성` · `출시 준비` 로 나누고 짧은 항목을 ` · ` 로 잇는다. 커밋 하나 = 한 줄이 아니다
- **빼는 것** — 기록 · 문서 정리 커밋, 개발 도구(편집기 연동 · 개발용 계정 제어 · 측정용 기록 등). 본문에 *"기록 정리"* 줄도 쓰지 않는다. 뺀 것은 「근거와 확인할 점」에 한 줄로 남긴다
- **라인 = 출시 라인이다.** 대표는 *"이 플랫폼 버전에 무엇이 들어갔나"* 를 본다
- **플랫폼 라인이 둘 이상인 프로젝트는 핵심 아래에 「버전별 반영」 표**를 둔다 — 항목 한 줄에 라인마다 `●`(이번 기간 반영) · `—`(없음). 요약본의 **「플랫폼 대조」** 에서 옮긴다. 같은 작업인지는 스크립트가 **머리말 뗀 제목이 완전히 같은 것만** 묶은 결과다 — 비슷한 문구를 AI 가 추가로 묶지 않는다. 사소한 항목은 표에서 빼고 그 밖으로 보낸다
- **플랫폼으로 판정되지 않는 브랜치가 여럿이고 내용이 거의 같으면** 하나로 합쳐 쓰고, 브랜치 사이의 차이는 「근거와 확인할 점」에 적는다. 내용이 다르면 쉬운 이름으로 절을 나눈다
- 커밋 머리말(설정의 `prefix` — 예: `and -` · `ios -`)은 떼고 쓴다

### 문장

- **쉬운 문장.** 쓰지 않는다 — 커밋 번호 · 파일명 · 깃 용어 · 개발 약어(그대로 옮기지 말고 풀어 쓴다)
- **작업 건수를 쓰지 않는다** — 커밋 입자가 프로젝트마다 달라 성과 비교로 읽힌다
- **사람 이름을 쓰지 않는다** — 요청받았을 때만

### 구체 내용과 의미 — 추측을 표시한다

- **커밋 제목 · 본문에 근거가 있을 때만** 의미를 덧붙인다. 없으면 생략한다
- 근거가 약하면 **`(추정)`** 을 붙인다. 표시가 없으면 검수하는 사람이 어느 줄이 추측인지 거를 수 없다
- 커밋에 없는 효과 · 의도 · 수익 영향을 **단정하지 않는다**

### 확인해 보실 것

- **되돌림** — 같은 범위에 조정과 되돌림이 둘 다 있으면 *"조정했다가 원래대로"* 한 줄. **지난 보고 항목을 되돌린 것**이면 *"지난 보고의 ○○ 취소"*
- 세이브 · 결제 · 서버 · 계정 관련 변경
- 합쳐지지 않고 사라진 브랜치 · fetch 실패 · 판독 불가 커밋

### 근거와 확인할 점 (보고서 맨 아래)

부른 사람이 검수할 때 보는 칸이다. 보고서와 한 파일에 둔다 — 따로 떼지 않는다.

- 추정이 들어간 항목 · 근거가 약한 항목의 **근거 커밋 제목**
- 대응표에 없는 브랜치 — 요약본의 *"대응표에 없음"*
- 하나로 합쳐 쓴 브랜치들의 차이
- 뺀 것 — 기록 · 문서 정리 커밋, 개발 도구
- 기록이 다시 정리된 라인(요약본 범위 `rewritten` · `lost-base`)

## §3. 등록과 설정 — PC 마다 로컬에

**추적할 프로젝트는 스킬이 아니라 이 PC 의 설정 파일에 있다.**

| | 위치 |
|---|---|
| 설정 | `~/.project-report/config.json` — 환경 변수 `PROJECT_REPORT_HOME` 으로 폴더를 바꿀 수 있다 |
| 기준점 · 복제본 · 보고서 | 설정의 `baseDir` (기본은 설정과 같은 폴더) |
| 예시 | 이 스킬 폴더의 `config.example.json` — 형식 참고용. 실제로 읽지 않는다 |

**설정 파일과 `baseDir` 은 어느 저장소에도 커밋하지 않는다.** 조직의 저장소 주소와 프로젝트 이름이 들어 있다.

### 등록 명령

```
node <스킬 폴더>/scripts/collect.mjs init [--base-dir <경로>]
node <스킬 폴더>/scripts/collect.mjs add --url <저장소 주소> [--key k] [--name N] [--alias a,b] [--exclude "wip/*"]
node <스킬 폴더>/scripts/collect.mjs map <key> <브랜치> --platform <이름> [--prefix "<머리말>"]
node <스킬 폴더>/scripts/collect.mjs unmap <key> <브랜치>
node <스킬 폴더>/scripts/collect.mjs remove <key>
node <스킬 폴더>/scripts/collect.mjs list
```

- **설정 파일을 손으로 고치지 않고 위 명령을 쓴다.** 명령이 형식 · 중복 · key 규칙을 검사한다
- **`add` 는 등록 전에 이 PC 의 계정으로 저장소가 읽히는지 확인한다.** 안 읽히면 등록하지 않는다 — 계정 문제면 부른 사람에게 알리고 멈춘다. 확인을 건너뛰는 `--no-check` 는 부른 사람이 원할 때만 쓴다
- **이름 · key 를 정하지 않으면** 주소의 저장소 이름을 쓴다. 별칭은 부른 사람이 실제로 부르는 이름을 묻고 넣는다
- **브랜치가 출시 라인(플랫폼)으로 나뉘는 프로젝트**는 `map` 으로 표시한다. 어느 브랜치가 어느 플랫폼인지 **추측하지 않고 묻는다** — 틀리면 대표에게 틀린 출시 정보가 간다. 처음 보고에서 *"대응표에 없음"* 으로 나온 브랜치를 보여 주고 물어도 된다
- **`remove` 는 추적 목록에서만 뺀다.** 복제본과 기준점은 남는다 — 지울지는 부른 사람이 정한다
- 다른 설정값(`firstReportDays` · `newBranchDays` · `fetchTimeoutSec` · `bodyMaxChars` · `docPathPatterns`)은 기본값으로 충분하다. 바꿔 달라고 하면 설정 파일의 그 값만 고친다

### 기록 파일

- `state.json` 이 깨지면 스크립트가 첫 보고처럼 처리하고, 기준점을 옮길 때 깨진 파일을 `state.corrupt-<시각>.json` 으로 남긴다. **직접 지우지 않는다**

## 하지 말 것

- **작업 저장소에서 fetch · pull** — 보고 전용 복제본만 쓴다 (§0)
- **메신저에 직접 게시** — 부른 사람이 검수하고 공유한다 (§0)
- **셸로 git 출력 읽기** — 스크립트가 UTF-8 로 받는다 (§1)
- **redo · 수정 때 기준점 옮기기** — ④는 report 에서만 (§1)
- **플랫폼 라인 사이 중복 합치기 · 건수 · 사람 이름 · 근거 없는 의미 단정 · 기록 커밋과 개발 도구를 본문에 쓰기** (§2)
- **로컬 설정 · 기록 파일을 저장소에 커밋하기 · 브랜치 → 플랫폼을 추측해서 등록하기** (§3)
