# git-procedure

**커밋 → 페치 → 풀 → 푸시**를 안전하게 수행하는 절차의 단일 진실원.

- **§0 발동 기준** — 언제 이 절차를 타나
- **§1 절차** — 여섯 단계와 멈춤 조건, **받기 전용 흐름**
- **§2 에셋** — 충돌 시 인계, 조용한 머지 보고
- **§3 커밋 메시지 전달** — 셸 함정과 `-F` 단일 경로
- **§4 커밋 메시지 규약** — 무엇을 어떻게 쓰나, 머지·문서 전용 커밋의 예외
- **§5 보고** — 깃 용어를 쓰지 않는다

> **읽는 사람이 누구인지 AI 는 모른다.** 프로그래머도 쓰고, 깃을 직접 쓰기 어려운 기획·디자인 직군도 쓴다. 같은 저장소를 함께 쓰므로 **지금 누가 타이핑하는지 판정할 수 없다.**
>
> **그래서 낮은 쪽에 맞춘다.** 비대칭이라 방향이 하나뿐이다 — 프로그래머 기준으로 짜면 **기획·디자인 쪽에서 사고가 나지만**, 낮은 쪽에 맞추면 프로그래머는 **같은 절차를 더 잘 쓸 뿐 잃는 것이 없다.**
>
> **결과를 스스로 검증할 수 없는 사람을 대신해** 깃을 만진다고 생각하고 움직인다.

## §0. 발동 기준 — 「크기」가 아니라 「실행하는 명령」

**`git commit` · `git pull` · `git push` 중 하나라도 실행하면 이 스킬을 로드한다.** 한 글자 수정의 커밋도, 문서 한 줄의 푸시도 같다.

**"이번엔 가벼우니 짧게 가겠다"는 판단을 하지 않는다. 그 판단 자체가 이 절차의 실패 지점이다.**

**흐름은 사용자가 무엇을 지시했는지로 갈린다.** 로드는 언제나 하고, 어느 단계를 도는지가 달라진다.

| 지시 | 흐름 |
|---|---|
| 커밋·올리기 (또는 *"깃작업 해줘"*) | **§1 전체** — ⓪~⑥ |
| **받기만** (*"받아줘"* · *"풀 좀"*) | **§1.5 받기 전용** — ③④⑤ |
| **깃 지시가 없다** (*"이식하자"* · *"고쳐줘"*) | **아무것도 돌지 않는다.** 작업만 끝내고 **묻는다** (§0.1) |

**시키지 않은 단계를 채워 넣지 않는다.** 받기만 지시받고 커밋·푸시까지 하면 **자동 커밋 금지를 절차가 어기게 된다.**

> **비용 오해 차단** — 스킬은 세션당 한 번만 로드되고 이후 컨텍스트에 남는다. 가벼운 작업에서 읽어도 총비용이 늘지 않는다.

**다른 스킬과 발동 축이 다르다.** `code-convention` · `document-convention` 은 **어떤 파일을 건드리는가**로 갈리지만, 이 스킬은 **어떤 명령을 실행하는가**로 갈린다. 파일을 안 건드려도 커밋하면 이 절차다.

### 확인은 절차 시작 전 1회

**사용자의 명시적 커밋·푸시 지시가 곧 그 확인이다.** *"깃작업 해줘"* 라고 이미 말한 사용자에게 *"진행할까요?"* 를 되묻지 않는다 — 순수한 왕복 비용이고, 그 마찰이 반복되면 다음엔 확인을 생략하는 쪽으로 흐른다.

지시가 없는데 절차가 필요해 보일 때만 묻는다. 그때의 질문은 *"커밋할까요?"* 다.

### §0.1 그 지시가 이번 작업의 것인가 ★

**「깃 지시가 있었는가」는 세션이 아니라 「지금 이 작업」 단위로 판정한다.**

- **앞선 작업의 승인은 다음 작업으로 넘어가지 않는다.** 앞서 *"깃작업까지 해줘"* 를 들었어도, **다른 작업을 지시받았으면 그 작업에는 깃 지시가 없는 것**이다
- 지시에 **커밋·푸시·올리기·깃작업이 없으면 절차를 시작하지 않는다.** 작업만 끝내고 **묻는다**
- **작업 완료가 커밋 조건이 아니다.** *"다 됐으니 올린다"* 는 자동 커밋이다

> **작업 지시는 깃 지시를 포함하지 않는다.** *"이식하자"* · *"고쳐줘"* · *"문서 써줘"* 는 전부 작업 지시이며, **끝까지 해내라는 뜻이지 올리라는 뜻이 아니다.**

**검수가 커밋보다 먼저다.** ★

이식·수정의 결과는 **사용자가 검수한 뒤에** 올라간다. AI 가 테스트를 통과시켰다는 것은 **검수가 끝났다는 뜻이 아니다** — 통과 판정을 내린 것도 AI 이기 때문이다.

> **그래서 「전부 통과했으니 물어볼 것이 없다」가 성립하지 않는다.** 오히려 그때가 물어야 할 시점이다. 검수 없이 올리면 **사용자가 결과를 보기 전에 원격에 박힌다.**

**§1.5 와 같은 축의 룰이다.** 그쪽은 *"받기만 지시받고 커밋·푸시까지 하지 않는다"* 로 **덜 시킨 것을 더 하는 것**을 막고, 이 절은 **아예 안 시킨 것을 하는 것**을 막는다.

## §1. 절차

```
⓪ 현재 셸 확인 — 어느 셸로 진행하는지 한 줄로 밝힌다
① git add <경로 명시> + git commit -F <메시지 파일>
② git log -1 --format=%B          ← 메시지 저장 검증 (§3)
③ git fetch
④ git pull --no-rebase --no-edit  ← 충돌 시 §2 로 중단
⑤ 머지된 에셋 보고 (§2.3)
⑥ git push
```

**커밋이 첫 단계인 이유** — 내 작업을 먼저 봉인해야 pull 이 실패해도 잃는 것이 없다.

- **`git add -A` 금지.** 변경 파일을 경로로 명시한다
- **`--no-rebase` 를 붙인다.** 사용자 홈 `.gitconfig` 에 `pull.rebase=true` 가 있으면 rebase 로 도는데, **금지된 동작을 설정이 대신 일으킨다**
- **`--no-edit`** — 머지 커밋 메시지는 기본값을 그대로 둔다 (§4.5)
- **브랜치·remote 이름은 어디에도 적어두지 않고 물어본다.** `git branch --show-current` · `git remote`. 적어두면 바뀌었을 때 안 따라간다. **확인한 그 브랜치로만 푸시한다**

### §1.1 멈춤은 두 종류다

| 종류 | 조건 |
|---|---|
| **게이트 멈춤** | 충돌 발생(§2) · 커밋 메시지 검증 실패(§3) |
| **명령 실패 멈춤** | git 명령이 **0 이 아닌 코드로 끝나면 언제나.** 인증 실패 · 원격 거부 · 업스트림 없음 · LFS 실패 · 훅 거부 |

**둘 다 확인이 아니라 보고하고 대기다.** 조건표에 없다는 이유로 진행하지 않고, **다음 단계를 시도해 우회하지 않는다.** pull 이 실패했는데 push 로 넘어가면 원격 이력을 모르는 채 밀어 올리게 된다.

### §1.2 잔여 변경

`add -A` 를 금지하므로 **① 이후에도 커밋 안 된 변경이 반드시 남는다.** Unity 에서는 상시 상태다 — `.csproj` 재생성, 에디터가 건드리는 `ProjectSettings`, 임포트로 갱신되는 `.meta`.

- ① 뒤에 `git status` 로 확인하고 **남은 것이 있으면 목록을 보고한다**
- 겹치는 파일이 있으면 ④ 가 *"Your local changes would be overwritten"* 로 실패한다 → 명령 실패 멈춤
- **`git stash` 는 사용자가 지시했을 때만 쓴다.** 잔여 변경을 통째로 치우는 비가역 조작이다

### §1.3 push 가 거부되면

③~⑥ 사이에 남이 푸시하면 거부된다. **흔한 일이고 사고가 아니다.**

> **③ → ④ → ⑤ → ⑥ 을 한 번 더 돈다.** 이미 승인된 절차의 재시도이므로 **확인을 다시 받지 않는다.**

이 경로가 없으면 되묻고 멈추거나(마찰) **강제 푸시를 집게 된다**(금지).

### §1.4 LFS 는 오래 걸린다

Unity + LFS 저장소의 첫 push 는 수 분이 걸리는데 셸 도구 기본 타임아웃은 대개 2분이다. **타임아웃은 0 이 아닌 종료 코드로 보여 「push 실패」로 오인된다.**

- ⑥ 은 **긴 타임아웃 또는 백그라운드**로 돌린다
- 불명확하게 끝나면 **`git fetch` 후 원격 상태를 다시 보고** 판정한다. 오판하면 사용자에게 거짓을 보고하게 된다

### §1.5 받기 전용 흐름 ★

**사용자가 받기만 지시하면 ①커밋과 ⑥푸시를 건너뛴다.**

```
③ git fetch → ④ git pull --no-rebase --no-edit → ⑤ 머지된 에셋 보고
```

*"최신거 받아줘"* · *"풀 좀"* · 하루 시작 루틴의 받기 단계가 여기 해당한다. **시키지 않은 커밋과 푸시를 하지 않는다** — 자동 커밋 금지가 절차보다 위에 있다.

**단계를 빼는 것이 아니라 안전장치가 빠지는 것이다.** ★

①이 첫 단계인 이유는 **내 작업을 먼저 봉인해 ④풀을 안전하게 만드는 것**이었다. ①을 건너뛰면 **봉인 안 된 작업 위로 받게 된다.** 그래서 뺀 자리를 아래 게이트가 메운다.

#### 받기 전에 겹치는지 본다

**판정 축은 「저장 안 한 변경이 있는가」가 아니라 「받아올 파일과 내가 고친 파일이 겹치는가」다.**

```
받아올 파일 목록  ∩  내가 고친 파일 목록

교집합 없음   → 그대로 받는다
교집합 있음
   ├ 에셋(§2.1)이 하나라도 있으면     → 중단
   ├ 같은 줄을 건드렸으면 (덮어써야)  → 중단
   └ 줄이 안 겹치면 (합칠 수 있으면)  → 확인을 받고 진행
```

**에셋은 줄 판정을 하지 않는다.** 프리팹·씬·`.meta`·데이터 자산이 겹치면 **줄이 안 겹쳐도 중단**한다. §2.1 이 *"충돌이든, 충돌 없이 양쪽이 같은 파일을 건드렸든 항상 사용자에게 넘긴다"* 로 이미 정했고, 여기서 다르게 판정하면 2중 조건이 된다.

**저장 안 한 변경이 있다는 것만으로 막지 않는다.** 엔진이 만드는 설정 파일 하나 때문에 **매일 아침 받기가 잠긴다.** 그러면 사용자가 매번 우회하게 되고, 게이트가 있는 것보다 나빠진다.

> **이 게이트의 값어치는 「막아주는 것」이 아니라 「먼저, 알아듣게 알려주는 것」이다.** 겹친 채로 받으면 git 이 알아서 거부하므로 작업은 안 날아간다. **진짜 위험은 §2.3 의 조용한 머지** — 같은 에셋을 서로 다른 줄에서 고치면 **충돌로 안 잡히고 조용히 합쳐진다.** 에러도 거부도 없어서 조심할 대상 자체가 안 보인다. 그래서 **받기 전에** 본다.

#### 합칠 수 있을 때 — 확인을 받는다

미커밋 변경을 그대로 둔 채 받는 방법은 git 에 없다. **실체는 「잠시 치워두고 → 받고 → 되돌려놓기」이며, 이는 진입점 문서가 금지한 조작이다.** §1.2 의 *"사용자가 지시했을 때만"* 이 그 예외 경로이므로, **무슨 일이 일어나는지 드러내고 묻는다.**

> 작업 중인 내용을 **잠시 치워두고 받은 뒤 다시 되돌려놓습니다.** 되돌릴 때 같은 줄을 건드린 게 있으면 멈추고 알려드립니다. 진행할까요?

- **승인 없이 실행하지 않는다.** *"합칠 수 있으니 진행했습니다"* 는 금지다
- **판정은 미리 한다.** 해보고 충돌이 나면 사용자 작업 파일에 충돌 표시가 박힌다

#### 중단할 때 — 막다른 길로 끝내지 않는다

```
지금 작업 중인 파일 중 2개가 받아올 내용과 겹칩니다.
 — Player 프리팹 · 전투 설정 파일

프리팹은 자동으로 합쳐지면 연결이 조용히 끊어질 수 있어 받지 않고 멈췄습니다.
어떻게 할지 알려주세요.

  ① 지금 작업을 마무리하고 받는다
  ② 지금 것을 별도 가지에 담아두고 받는다   ← 작업은 그대로 남습니다
  ③ 나중에 받는다
```

- 겹치는 파일을 **이름과 종류**로 알린다. 경로를 그대로 붙이지 않는다 (§5)
- **②는 ①커밋의 변형이다.** 별도 가지에 봉인하면 받기 전용이 포기했던 안전이 되돌아온다. 아무것도 지우거나 되돌리지 않으므로 금지 조작이 아니다
- **②를 AI 가 먼저 실행하지 않는다.** 가지가 생기면 나중에 합치는 일이 따라오고, 그건 사용자 판단이다
- **「보관할지·되돌릴지」는 선택지로 내밀지 않는다.** 그건 지우는 조작이고, **AI 가 먼저 권하면 위험 조작이 일상이 된다.** ②를 넣는 것과 다르다 — **지우느냐 아니냐가 기준이다**

#### 공통

- **임의로 저장하지 않는다.** 자동 커밋 금지다
- **임의로 치워두지 않는다**
- 이 상태에서 ⓪~⑥ 전체 흐름을 대신 실행하지 않는다. 사용자가 남은 작업을 마무리하라고 지시하면 그때 전체 절차로 전환한다

> **§1.2 를 이 흐름에 적용할 때** — 그 절은 *"① 이후에도 커밋 안 된 변경이 남는다"* 로 시작하는데, **여기서는 ①이 안 돈다.** 잔여 변경은 「남는 것」이 아니라 **처음부터 있는 것**이고, 그래서 더 위험하다. 위 게이트가 그것을 먼저 본다.

## §2. 에셋 — 충돌은 사용자가, 조용한 머지는 보고한다

### §2.1 AI 는 에셋 충돌을 해결하지 않는다

머지 도구가 성공했든 실패했든, 머지 드라이버가 설정돼 있든 없든 마찬가지다.

| 종류 | 예 | 처리 |
|---|---|---|
| **코드·텍스트** | `.cs` `.ts` `.md` `.json`(일반) | AI 가 해결 |
| **컴파일 경계** | `.asmdef` `.asmref` | AI 해결 가능. 해결 후 **reference · define constraints · 플랫폼 include/exclude 확인** |
| **Unity YAML** | `.prefab` `.unity` `.asset` `.anim` `.controller` `.mat` `.spriteatlasv2` 등 | **사용자** |
| **전역·의존성** | `ProjectSettings/**` · `Packages/**` | **사용자** |
| **LFS 바이너리 · `.meta`** | `.fbx` `.psd` `.png` `.wav` / **모든 `.meta`** | **사용자** |

**판정 축은 형식이 아니라 의미다.** *"텍스트면 AI 가 해결"* 은 틀렸다 — `ProjectSettings/*.asset` 은 YAML 이라 문법상 머지가 성공해도 프로젝트 전역 설정이 바뀐다. **전역 설정 · 참조 관계 · 데이터 자산이면 넘긴다.**

**`.gitattributes` 로 넓히되 좁히지 않는다.**

```bash
git check-attr merge filter -- <경로>
```

`merge=unityyamlmerge` 면 Unity YAML, `filter=lfs` 면 LFS 바이너리다. **선언에 없어도 위 표에 있으면 에셋으로 본다** — 새 Unity 버전이 새 확장자를 만들면 선언이 뒤처지는데, 그때 덜 보수적으로 판정되면 안 된다.

- **`.gitattributes` 를 눈으로 읽지 않는다.** `[attr]` 매크로 전개 · 후행 규칙 우선 · 하위 디렉터리 파일 · `core.ignorecase` 를 전부 놓친다. `check-attr` 이 그것을 다 반영한다
- **확장자 매칭은 대소문자를 무시한다.** `core.ignorecase` 는 로컬 설정이라 **같은 저장소가 개발자 Windows 와 CI 리눅스에서 다르게 분류된다.** 우리 판정이 거기 의존하면 안 된다

### §2.2 인계 — 「판단하지 않는다」와 「실행하지 않는다」는 다르다

**AI 는 어느 쪽을 살릴지 정하지 않는다. 그러나 사용자가 정하면 그 지시를 실행한다.**

둘을 붙여놓으면 인계가 *"깃 클라이언트에서 해결하세요"* 로 끝난다. **직접 해결할 수 있는 사람에겐 그것도 답이지만, 그럴 수 없는 사람에게는 막다른 길이다.** 누가 읽는지 모르므로 **양쪽 다 이어갈 수 있는 형태로** 낸다.

```
같은 파일을 두 분이 함께 수정하셔서 자동으로 합칠 수 없습니다.

- Assets/Prefabs/Player.prefab   (프리팹)
- Assets/Art/Boss.fbx            (3D 모델 파일)

각 파일을 어떻게 할지 알려주세요.
  ① 제 작업을 살린다        ② 상대 작업을 살린다
  ③ 둘 다 살려야 한다 / 판단이 어렵다  → 직접 확인이 필요합니다

말씀해주시면 그대로 처리하고 푸시까지 이어서 진행하겠습니다.
```

- **①·② 를 고르면 AI 가 실행한다.** 선택은 사용자 판단이므로 원칙이 지켜지고, 실행은 AI 가 하니 인계가 실제로 끝난다
- **③ 이면 멈춘다.** 둘 다 필요한 병합은 파일을 열어봐야 하고 그건 AI 가 할 일이 아니다
- **파일 종류를 평문으로 덧붙인다** — `LFS 바이너리` 가 아니라 `3D 모델 파일`, `GUID` 가 아니라 `연결 정보`
- 사용자가 직접 해결하고 **"해결됐어"** 라고 하면 **확인 없이 ⑤ 부터 이어간다**
- **스스로 `--ours` / `--theirs` 를 고르지 않는다.** 선택 자체가 사용자 판단 영역이다

### §2.3 조용한 머지는 막지 않고 보고한다

**충돌로 잡히면 이미 안전하다** — git 이 멈추고 사람이 본다. 실제 사고는 반대쪽에서 난다.

```
양쪽이 같은 .prefab 을 서로 다른 줄에서 수정
  → 충돌로 안 잡히고 조용히 합쳐짐
  → 참조가 어긋나 있는데 아무도 모름
```

Unity YAML 머지 드라이버는 **선언만 있고 실제 등록이 안 된 경우가 흔하다**(`.gitattributes` 에 `merge=unityyamlmerge` 는 있는데 `git config` 에 `merge.unityyamlmerge.cmd` 가 없는 상태). 그러면 git 은 **기본 텍스트 머지로 조용히 떨어진다.**

**이걸 pull 전에 막으려 하지 않는다.** ⑤ 에서 결과를 보고한다.

```bash
git -c core.quotepath=false diff --name-only ORIG_HEAD HEAD
```

이 목록에 §2.1 의 에셋이 있으면 덧붙인다.

```
※ 아래 파일이 양쪽 작업을 합치면서 자동으로 병합됐습니다.
  Unity 에서 열어 확인하시길 권합니다.
   - Player 프리팹
```

사고를 100% 막지는 못하지만 **모르고 지나가는 것은 막는다.**

## §3. 커밋 메시지 전달 — 셸 함정

Bash 와 PowerShell 은 여러 줄 문자열 문법이 다르다. **틀리면 메시지가 조용히 깨진 채 커밋된다.**

| 셸 | 문법 |
|---|---|
| Bash (Git Bash) | heredoc — `git commit -F - <<'EOF'` … `EOF` |
| PowerShell | here-string — `git commit -m @'` … `'@` (닫는 `'@` 는 0 컬럼) |

**함정 1 — Bash 에서 PowerShell here-string 사용.** Bash 는 리터럴로 넘겨 첫 줄이 `@` 가 되고, git 이 빈 줄 전까지를 제목으로 합쳐 최종 제목이 **`@ 의도한제목`** 으로 오염된다. **에러 없이 커밋이 성공해 알아채기 어렵다.**

**함정 2 — PowerShell 이 네이티브 명령 인수를 시스템 ANSI 로 인코딩.** 문법이 맞아도 한글이 cp949 로 도착하고 git 은 UTF-8 을 가정해 저장한다 → **깨진 메시지가 원격에 올라간다.**

### §3.1 그래서 셸 분기를 없앤다

**위 표는 배경 지식이다. 실제 지시는 하나뿐이다.**

```
1. 메시지를 UTF-8(BOM 없음) 파일로 쓴다   ← 네이티브 파일 도구 사용
2. git commit -F <파일>
3. git -c core.quotepath=false log -1 --format=%B  로 검증
4. 메시지 파일을 지운다
```

- **두 함정이 동시에 닫힌다.** 셸 문자열 문법을 아예 쓰지 않기 때문이다
- **메시지 파일은 저장소 밖 임시 경로에 쓴다.** 워킹트리에 쓰면 §1.2 의 잔여 변경에 섞인다
- **② 검증은 `-m` 단일 행이어도 실행한다.** 오염 여부를 사전에 판단하지 않는다
- 제목이 `@` 로 시작하거나 한글이 깨졌으면 **즉시 amend.** 이미 푸시됐으면 **고치지 말고 보고한다**

> **PowerShell 로 검증 출력을 읽을 때 주의** — PS 5.1 은 git 출력을 콘솔 코드페이지로 디코딩한다. 인코딩이 맞지 않으면 **멀쩡한 커밋이 깨져 보여 정상 커밋을 amend 하게 된다.** 미심쩍으면 Git Bash 에서 다시 본다.

## §4. 커밋 메시지 규약

**사용자는 메시지를 쓰지 않는다. AI 가 전부 쓴다.**

### §4.1 커밋 직전 5줄 체크리스트

1. **제목** = `{대상} {결과형 동사}` 한 줄, **한글 40자 이내**. 절차 카운트·추상 표현·작업 메타 금지
2. **본문** = 점 목록 기본. 배경 산문 단락 금지
3. **파일·필드·줄 수 나열 금지** — diff 에 이미 있다
4. **약식 기호 금지** — `→` `↔` `vs` 는 자연어로
5. **자가 검증** — 맥락 없는 팀원 / 2주 뒤 본인이 추적 가능한가 · **이 세션에서만 통하는 용어·영어가 남아 있지 않은가**

**언어는 한국어.** 컬럼은 제목 80 · 본문 100이며 **한글은 2컬럼**이므로 제목은 한글 40자다.

### §4.2 외부 독자 친화 룰

AI 가 쓰는 커밋 메시지는 **세션 컨텍스트를 그대로 토해내는 경향**이 있어, 맥락 없는 팀원이 읽지 못한다.

| # | 룰 | 요지 |
|---|---|---|
| 1 | **제목은 결과 중심 한 줄** | `{대상} {결과형 동사}`. **「대상」은 기능·시스템 이름이지 파일명이 아니다**(룰 5).<br>O `보스 텔레그래프 가드 미발동 이슈 수정` / X `보스 BT 정확도 보강 (3 cycles)` |
| 2 | **본문은 점 목록** | **금지** — 배경 산문 단락(맥락은 PR·이슈 트래커에서).<br>**허용** — 점 목록만으로 본문을 채워도 된다. 한 줄 안에 행위 + 인과가 녹는 표현은 권장 |
| 3 | **세션 로컬 약어 금지** | 임시 지칭(`dp-1`)·절차 약어(`sub-X`)는 풀어쓴다. 문서를 지칭하면 실제 파일명 |
| 4 | **풀리는 영어는 한국어로** | `bullet` → 점 목록, `revert` → 되돌리기. 고유명사·API·표준 약어는 유지 |
| 5 | **파일·필드·줄 수 나열 금지** | 본문은 **"무엇을 했다"**(행위 + 의미)만.<br>O `LockOn 컴포넌트가 회전 변경 뒤 내부 기준값을 동기화하도록 보정`<br>X `LockOnComponent.cs 의 CachedYaw 수정, PlayerController.cs 12줄 변경` |
| 6 | **표현 자연성** | 약식 기호 금지 · 점 목록은 주제별로 묶어 배치.<br>X `(settings.json, Kanban 사양 2건)` — 괄호로 디테일 packing 금지<br>**적용 범위는 커밋 메시지 본문에 한정한다. 문서는 `document-convention` 소관** |
| 7 | **사소한 부수 변경 제외** | 로그 제거·주석 정리·들여쓰기는 본문에 줄을 추가하지 않는다. **단 그것이 작업 의도 자체면 포함** |
| 8 | **자가 검증 3항목** | 2주 뒤 추적 가능한가 · 맥락 없는 팀원이 이해 가능한가 · 본인만 아는 용어가 없는가 |

### §4.3 완성 예시

**단순 커밋** — 제목 + 평평한 점 목록. 번호 섹션을 쓰지 않는다.

```text
공격자 리코일 좌우 교대 구현

- 연속 패리·가드당함 시 좌우 리코일 방향을 번갈아 적용
- 마지막 적용 방향을 기억해 다음 피격에서 반대 방향 선택
```

**다주제 커밋** — 주제별 번호 그룹핑. **번호 하위 점 목록에도 룰 5 가 그대로 적용된다.**

```text
적 기상 흐름 안정화 및 사양서 갱신

1. 기상 중 피격 처리
   - 기상 모션 진행 중 피격되면 다운으로 되돌리지 않고 경직만 적용
   - 무적 구간이 기상 종료까지 이어지도록 정리
2. 사양서
   - 기상 상태 전이 규칙을 현재 구현에 맞게 정정
```

WIP 중간 저장처럼 임시 성격이 강한 커밋은 **제목만** 허용한다.

### §4.4 무엇을 문서로 남기는가는 이 스킬 소관이 아니다

커밋 메시지와 개발 이력 문서는 **대상이 다르다.** 「파일·줄 수 나열 금지」가 양쪽에 있지만 각자 자기 대상에 대한 규칙이다. 문서 쪽은 `document-convention` 이 원본이다.

### §4.5 머지 커밋에는 §4 를 적용하지 않는다

④ pull 이 만드는 `Merge branch 'x' of ...` 는 위 룰을 전부 위반한다.

> **머지 커밋의 기본 메시지는 그대로 둔다.** §4 는 **내가 작성하는 커밋**에만 적용되고, **② 검증도 머지 커밋에는 하지 않는다.**

### §4.6 문서만 올리는 커밋 ★

개발 이력·설계 문서만 올리는 커밋은 **§4.1 의 「작업 메타 제목 금지」에서 면제된다.**

**산출물이 문서일 때는 *"무슨 기록을 남겼는가"* 가 작업 메타가 아니라 내용 그 자체이기 때문이다.** 코드 커밋에서 *"3차 리팩터"* 가 금지인 것은 그것이 **결과가 아니라 과정**을 말해서인데, 문서 커밋에서 *"개발 이력 추가"* 는 **결과 그 자체**다.

**면제되는 것은 그 한 줄뿐이다.** 나머지는 그대로 적용한다 — 제목 한글 40자 · 본문 점 목록 · **파일명 나열 금지** · 세션 로컬 약어 금지.

```text
세션 루틴 스킬 개발 이력 추가         ← O   무엇에 대한 기록인지 드러난다
받기 전용 흐름 설계 문서 정리         ← O

디벨롭 히스토리 업데이트              ← X   무엇에 대한 기록인지 없다
문서 수정                             ← X   같은 이유
docs/develop-history 3개 파일 수정    ← X   파일 나열 (룰 5)
```

> **왜 규약이 필요한가** — 하루 마무리 절차의 마지막 단계가 **문서만 올리는 커밋**이다. 매일 도는 절차라, 규약이 없으면 **위반 커밋이 가장 빠르게 쌓이는 자리**가 된다.

## §5. 보고는 평문으로 — 깃 용어를 쓰지 않는다

**모든 사용자 대면 문구에 적용된다. 상대가 프로그래머로 보여도 예외를 두지 않는다** — 누가 읽는지 판정할 수 없고, 판정하려 드는 순간 세션마다 답이 갈린다. 프로그래머가 평문 보고로 잃는 것은 없다.

| 쓰지 않는다 | 대신 |
|---|---|
| `untracked 파일이 3개 있습니다` | *"아직 저장하지 않은 변경이 3건 있습니다"* |
| `non-fast-forward 로 거부됨` | *"제가 작업하는 사이 다른 분이 먼저 올리셨습니다. 받아서 합친 뒤 다시 올리겠습니다"* |
| `merge commit 이 생성됨` | *"양쪽 작업을 합쳤습니다"* |
| `LFS 전송 타임아웃` | *"용량이 큰 파일이라 업로드가 오래 걸립니다"* |
| `.meta GUID 충돌` | *"파일 연결 정보가 어긋났습니다"* |

- **커밋 해시·브랜치명·명령어를 보고 본문에 넣지 않는다.** 사용자가 그걸로 할 수 있는 일이 없다
- **파일은 전체 경로 대신 이름과 종류로** — `Assets/Prefabs/Player.prefab` → *"Player 프리팹"*
- **다음에 무엇이 필요한지 한 줄로 끝맺는다.** 상태만 알리면 사용자가 무엇을 해야 할지 모른다

> **예외 — 에러 원문은 그대로 붙인다.** 명령 실패 멈춤(§1.1) 때는 평문 설명 뒤에 원문을 덧붙인다. 사용자가 프로그래머에게 전달할 수 있어야 한다.

## 하지 말 것

- **자동 커밋** — 사용자의 명시 지시까지 대기한다
- **작업 지시를 깃 지시로 읽기** — *"이식하자"* 에는 커밋이 없다. **앞선 작업의 승인도 넘어오지 않는다** (§0.1)
- **검수 전에 올리기** — 테스트를 통과시킨 것도 AI 다. 통과가 검수를 대신하지 않는다 (§0.1)
- **`git add -A`** — 변경 파일을 경로로 명시한다
- **rebase pull** — merge 방식으로 한다
- **이력·작업을 지우는 조작** — 강제 푸시 · `reset --hard` · `checkout`/`restore` 로 되돌리기 · `clean -fd` · `stash` · 푸시된 커밋 amend. **필요해 보이면 실행하지 말고 보고한다**
- **에셋 충돌을 AI 가 해결** — 사용자가 고른 뒤에 실행하는 것과는 다르다 (§2.2)
- **받기만 지시받고 커밋·푸시까지 하기** — 시키지 않은 단계를 채워 넣지 않는다 (§1.5)
- **겹침을 안 보고 받기** — 받기 전용은 ①의 봉인이 없으므로 게이트가 그 자리를 메운다 (§1.5)
- **"가벼우니 절차를 줄이자"는 판단** (§0)
- **보고에 깃 용어 쓰기** (§5)

> 위 항목 중 **자동 커밋 · `git add -A` · rebase pull · 이력·작업을 지우는 조작 · 에셋 충돌**은 **이 저장소 진입점 문서의 안전망 절**이 원본이다. 이 스킬이 로드되지 않아도 지켜져야 하므로 그쪽에 있으며, 여기서는 절차 맥락에서 다시 짚는 것이다. **문구가 어긋나면 진입점 쪽이 맞다.**
