# 팀 공유 공지 양식

**스킬을 만들거나 배포한 뒤 팀에 알리는 슬랙 공지의 양식**이다. 살아있는 문서이며 날짜 접두어를 붙이지 않는다.

| 날짜 | 작성자 | 내용 |
|------|--------|------|
| 2026-09-09 | hans | 최초 작성 — `session-routine` 공지를 기준으로 굳혔다 |

> **초안은 `tmp/` 에 쓴다.** 붙여넣고 나면 지운다. 공지 본문을 저장소에 남기지 않는다 — 내용은 개발 이력에 이미 있고, 두 곳에 있으면 어긋난다.

---

## §1. 왜 양식이 필요한가

**공지를 쓸 때마다 형태가 달라지면 팀이 매번 새로 읽는 법을 배워야 한다.** 그리고 규칙 설명으로 흐르기 쉽다 — 만든 사람은 규칙을 알지만 **읽는 사람은 「내가 뭘 해야 하나」만 알고 싶다.**

**이 양식의 중심은 실제 대화 예시다.** 규칙을 설명하지 않고 **"이렇게 말하면 이렇게 답한다"** 를 보여준다.

---

## §2. 골격

```
🌤️ <스킬 이름> — <프로젝트> 적용 완료

<한 문장. 이 스킬이 무엇을 해주는가>

■ 한 줄 요약
■ 왜 만들었나          ← 문제. 없으면 생략
■ 무엇이 생겼나         ← 구조. 없으면 생략
■ 실제로 어떻게 답하나   ← 본체
■ 멈추는 경우           ← 게이트가 있으면
■ 알아두실 것           ← 번호 목록
■ 검증
■ 같이 고친 것          ← 있으면
■ 팀에서 해주실 것       ← 번호 목록 + 각 항목에 → 효과
■ 확인 부탁드립니다      ← 사람 판단이 필요한 것이 있으면
```

**`■ 실제로 어떻게 답하나` 와 `■ 팀에서 해주실 것` 은 빼지 않는다.** 앞은 이해를, 뒤는 행동을 만든다. 나머지는 상황에 따라 뺀다.

---

## §3. 각 절의 규칙

### 제목과 도입

- **이모지 하나 + 스킬 이름 + 적용 대상.** 이모지는 제목과 §2 의 구조 도식에만 쓴다
- 도입은 **한 문장.** 무엇을 해주는지만

### `■ 한 줄 요약`

**사용자가 하는 말과 그 결과를 붙여 쓴다.**

```
"작업 남겨줘" 한마디면 한 줄이 쌓이고,
다음 날 아침루틴이 그것만 읽고 브리핑합니다.
```

### `■ 실제로 어떻게 답하나` ★

**이 절이 본체다.** `Q.` 로 사용자 발화를, `→` 로 응답을 쓴다.

```
Q. "오늘 작업 남겨줘"
   → 작업 로그에 한 줄 추가했습니다.

      - 09-09 16:20  hans  정렬 비교 함수에 동점 처리 추가

   ※ 하루에 몇 번을 해도 됩니다
   ※ 이전 줄을 고치거나 합치지 않습니다
```

- **`※` 는 예시 바로 밑에.** 규칙을 따로 모으지 않는다 — 예시와 붙어 있어야 읽힌다
- **응답은 실제로 나온 것을 쓴다.** 테스트 출력이 있으면 그것을 옮기고, **그렇다고 밝힌다** (*"Project_A 에서 실제로 나온 브리핑입니다"*). 지어낸 예시는 실제 동작과 어긋날 수 있다
- 발화는 **2~4개.** 정면 · 축약 · 애매한 경우를 섞는다

### `■ 멈추는 경우`

**게이트가 있는 스킬에만 쓴다.** 형식은 위와 같고, **왜 멈추는지**를 `※` 에 적는다.

> **읽는 사람이 가장 불안해하는 지점이다** — *"AI 가 마음대로 하면 어쩌지."* 멈추는 장면을 보여주는 것이 설명보다 강하다.

### `■ 알아두실 것`

번호 목록. **각 항목은 제목 한 줄 + 설명 두세 줄.**

**「하지 마세요」가 아니라 「이렇게 됩니다」로 쓴다.** 금지는 지켜지지 않고, 결과는 기억된다.

### `■ 검증`

- 무엇을 몇 번 돌렸는지 한두 줄
- **테스트가 실제로 잡은 것 하나**를 덧붙인다. 통과했다는 말보다 **무엇이 걸렸는지**가 신뢰를 만든다

### `■ 팀에서 해주실 것` ★

번호 목록. **각 항목은 「할 일 → 그래서 뭐가 좋아지나」 두 줄.**

```
1. 작업하다 아무 때나 "작업 남겨줘" 한마디
   → 기억에 의존하지 않게 됩니다. 나중에 몰아 적으면 시각도 내용도 부정확해집니다
```

**효과를 안 적으면 지시로 읽히고, 지시는 안 지켜진다.**

### `■ 확인 부탁드립니다`

**사람이 판단해야 할 것**만. 우리가 할 수 있는 일은 여기 넣지 않는다.

## §4. 표기

| | |
|---|---|
| **말투** | 존댓말. 팀 전체가 읽는다 |
| **볼드 · 백틱** | **쓰지 않는다.** 슬랙에서 반쯤만 렌더돼 지저분해진다. 강조는 줄바꿈과 들여쓰기로 |
| **파일 경로** | 그대로 쓴다 — `docs/work-log/work-log.md` |
| **표** | 쓰지 않는다. 슬랙이 마크다운 표를 렌더하지 않는다. **들여쓴 목록으로 푼다** |
| **이모지** | 제목과 구조 도식에만. 본문에 흩뿌리지 않는다 |
| **체크 표시** | `✅` 대신 `[완료]`. 복사 과정에서 깨질 수 있다 |
| **들여쓰기** | 응답 예시는 6칸, `·` 항목은 7칸, `※` 는 3칸 |

**전문 용어를 풀어 쓴다.** 읽는 사람이 프로그래머가 아닐 수 있다 — `git-procedure` §5 와 같은 이유다.

| 쓰지 않는다 | 대신 |
|---|---|
| 토큰 · 컨텍스트 | 읽는 양 · 세션 내내 다시 실려 간다 |
| frontmatter · YAML 파싱 실패 | 머리말 문법 오류로 파일을 읽지 못한다 |
| 미러 · 해시 불일치 | 두 파일이 서로 다르다 |

> **숫자는 그대로 쓴다.** *"16,000 토큰"* 은 남긴다 — 크기 감각을 주는 유일한 수단이고, 앞뒤 문장이 뜻을 설명해준다.

---

## §5. 하지 말 것

- **규칙 나열로 시작하기** — 예시가 먼저다
- **지어낸 응답 예시** — 실제 출력을 쓰고, 지어냈으면 그렇다고 적는다
- **「팀에서 해주실 것」 생략** — 읽고 나서 뭘 할지 모르면 공지가 소용없다
- **효과 없는 지시** — *"이렇게 해주세요"* 만 있고 이유가 없으면 안 지켜진다
- **공지 본문을 저장소에 남기기** — `tmp/` 에 쓰고 붙여넣은 뒤 지운다
- **볼드 · 백틱 · 표 사용** — 슬랙에서 깨진다
