# `skill-pipeline` 설계

이 저장소에서 **스킬을 만들고 배포하는 절차**의 단일 진실원.

> ⚠️ **이 스킬은 AI_Develop 전용이며 실 프로젝트에 배포되지 않는다.** 다른 스킬들과 성격이 반대다 — 나머지는 배포되기 위해 만들고, 이것은 **배포하는 쪽이 쓰는 도구**다.

## 왜 만드나

**진입점이 커져서 코덱스가 뒤를 못 읽는다.** 실측으로 확인됐다 (2026-08-25).

```
AI_Develop AGENTS.md   36,486 bytes
Codex 예산             32,768 bytes
초과                    3,718 bytes  → 뒤 10% 가 잘림
```

잘리는 구간이 **재배포 절차 · 이식 원칙 · 문서 배치**다. 즉 **코덱스에게 배포를 맡기면 절차를 모르는 채로 한다.** 어제 실제로 그런 사고가 났다 — 배포 블록이 기준 문서에서 안 나오고 손으로 조립됐다.

**원인은 우리가 만든 규칙을 이 저장소에서만 안 지킨 것이다.** [`CLAUDE.md`](../../../CLAUDE.md) §1.1 에 이렇게 써놓고도,

> 규칙을 한 파일에 쌓으면 **매 세션 전부 상주**한다 — 비용은 드는데 정작 그 작업을 하는 순간엔 attention 이 흐려진다

**스킬 개발 절차 자체를 스킬로 만들지 않고 진입점에 쌓았다.** 그 세 절이 전체의 **64%** 다.

## 담당 범위

| 담당한다 | 담당하지 않는다 |
|---|---|
| 스킬 개발 파이프라인 6단계와 각 단계의 게이트 | 스킬 **본문에 무엇을 쓰나** → 각 스킬 자신 |
| 스킬 이름 · `description` · 마스터 단일 진실원 규칙 | 커밋·푸시 절차 → `git-procedure` |
| 교차 검증과 고정 테스트 방법 | 개발 이력·계획 문서 형식 → `document-convention` |
| 실 프로젝트 이식·재배포 절차 | 소스 편집 규칙 → `code-convention` |
| **스킬 산출물 문서**(설계·검토)의 위치와 명명 | 하루 루틴 → `session-routine` |

### 기존 스킬과의 충돌 검사

| 겹침 | 판정 | 근거 |
|---|---|---|
| `document-convention` 의 문서 위치·명명 | **분리** | 그쪽은 **작업 단위 문서**(개발 이력·계획)를, 이 스킬은 **스킬 산출물 문서**(`docs/skills/<스킬명>/`)를 담당한다. **규칙이 정반대라 한쪽에 두면 2중 조건이 된다** — 그쪽은 날짜 접두어를 쓰고, 이쪽은 폴더가 구분자라 날짜를 안 붙인다. 실제로 `document-convention` SKILL.md 는 스킬 설계 문서를 **전혀 다루지 않는다** |
| 진입점 §0.2 의 **미러 수정 · 배포 범위 · 설계 판정** | **포인터** | 셋 다 **파국 방지 룰**이라 진입점이 원본이다. 이 스킬은 절차 맥락에서 다시 짚되, **문구가 어긋나면 진입점 쪽이 맞다** |
| `git-procedure` — 배포 후 커밋 | **포인터** | 이식은 파일 복사와 블록 교체까지다. **커밋·푸시는 그쪽이 원본** |
| `session-routine` — 마무리의 스킬 미러 확인 | **분리** | 그쪽은 **언제 확인하나**(마무리 0단계), 이 스킬은 **무엇을 어떻게 맞추나**(②미러링) |

> **`document-convention` 쪽 갱신이 필요하다.** 그 스킬의 설계 문서 충돌 검사 표가 *"그 선언은 저장소 진입점 문서에 있다"* 고 가리키는데, §6 이 이 스킬로 오면 **가리키는 곳이 바뀐다.**

## 배포되지 않는 스킬 — 3층으로 박는다 ★

**자체 스킬과 배포 스킬이 같은 폴더에 섞인다.** 지금 재배포 절차는 *"대상 프로젝트에 스킬 양쪽 재복사"* 라, **그대로 두면 이 스킬이 딸려간다.**

| 층 | 무엇 | 성격 |
|---|---|---|
| **①** | `SKILL.md` 맨 위 배너 — *"AI_Develop 전용, 실 프로젝트에 배포되지 않는다"* | 사람이 읽는 것 |
| **②** | **배포 대상 스킬 목록**을 진입점에 두고, 재배포는 **그 목록만** 복사한다 | **절차가 걸러내는 것** |
| **③** | 진입점 저장소 구조 표에서 `.claude/skills/` 를 **배포용 / 자체용**으로 갈라 표기 | 구조로 보이는 것 |

**②가 실질 안전장치다.** ①은 안 읽으면 그만이고, ③은 표시일 뿐이다. **목록에 없으면 복사되지 않는다**가 유일하게 기계적인 보장이다.

## 결정 이력

| # | 결정 | 근거 |
|---|---|---|
| 1 | **스킬 하나로 합친다** (제작 + 배포를 나누지 않음) | 나누면 *"파이프라인 → ④이식 단계 → 배포 스킬 로드"* 에 **재량이 한 번 더** 생긴다. **로드 실패가 곧 절차 미준수**이고, 어제 그 사고가 실제로 났다. 진입점 미러 전환 때 포인터를 버린 것과 같은 논리 — **다리를 놓으면 그 다리를 건너는 것도 재량이 된다** |
| 2 | 이름은 **`skill-pipeline`** | 우리 문서가 이미 「스킬 개발 파이프라인 6단계」라 부르고 **이식이 그 안의 ④단계**다. 이름에서 담당 범위가 그대로 연상된다 |
| 3 | §6 문서 배치도 **함께 옮긴다** | 내용이 대부분 **스킬 설계 문서를 어디 두나**다. 파이프라인 ①의 산출물 규칙이라 같은 자리다 |
| 4 | §0·§1·§2 는 **진입점에 남긴다** | §0 은 스킬이 안 떴을 때도 지켜야 하는 것이고, §1·§2 는 **이 저장소가 뭐 하는 곳인지**라 배경이다. 스킬로 내리면 배경을 알려면 스킬을 로드해야 한다 |
| 5 | **배포 대상 목록**으로 걸러낸다 | 배너와 표기는 사람이 읽는 것이다. **목록에 없으면 복사되지 않는다**가 유일한 기계적 보장이다 |
| 6 | 크기(23KB+)를 **분할 근거로 삼지 않는다** | 스킬은 **필요할 때만 로드**된다. 상주 비용이 아니라 로드 시 1회 비용이며, `session-routine` 이 22KB 로 이미 돌고 있다 |
| 7 | ⑥ 마무리에 **세 문서 동기화** 게이트를 넣는다 (§3.5) | `plan`·`review`·`SKILL` 이 어긋난 채로 쌓였다. **방금 고친 세션이 무엇이 어긋났는지 가장 잘 안다.** 미루면 다음 세션이 낡은 plan 을 읽고 잘못된 전제로 시작한다 |
| 8 | **기준은 언제나 `SKILL.md`** | 에이전트가 런타임에 읽는 것은 그것 하나다. `plan`·`review` 는 그것을 만들기 위한 부속이므로, 어긋나면 부속을 고친다 |
| 9 | 정정은 **덮어쓰기가 아니라 표기**다 | *"X 로 정했다"* 를 Y 로 바꿔 쓰면 **뒤집혔다는 사실이 사라진다.** 그러면 다음 사람이 X 를 다시 제안하고 같은 논의를 반복한다 |
| 10 | **plan 을 `SKILL.md` 의 요약본으로 만들지 않는다** ★ | 같은 내용이 두 곳에 있으면 **다시 어긋난다.** `git-procedure` 의 절 번호가 7쌍 어긋난 원인이 정확히 이것이었다 — plan 이 SKILL 과 같은 절 구조를 가져서 **어긋날 번호가 생겼다.** 결정 이력만 있으면 어긋날 것 자체가 없다 |
| 11 | `review.md` 는 **비운다. 지우지 않는다** (§6.1) | 파일이 없으면 *"검토를 안 받았나"* 와 구분되지 않는다. `document-convention` 이 보류 표에 `\| 없음 \| — \| — \|` 을 남기는 것과 같은 이유다 |
| 12 | 비우는 조건은 **판정이 plan 결정 이력에 들어갔는가** 하나 | 흡수 없이 비우면 근거가 통째로 날아간다. **왕복 과정은 소진되지만 판정은 남아야** 한다 |
| 13 | `review.md` 에 **크기 상한 60KB** | 사람이 *"이제 좀 큰가"* 를 매번 판정하면 안 하게 된다. **숫자가 발동시켜야** 한다. 로드된 문서는 그 세션 남은 턴 전부에 다시 실리므로 110KB 는 턴당 3만 토큰이다 |

## 미결정

| # | 항목 | 판단 시점 |
|---|---|---|
| 1 | **교차 검증 미실시** | 이관이라 F1(2중 조건)만 실질적이고 그건 위 충돌 검사에서 판정했다. **생략이 정당하다는 뜻은 아니다** — 다음 회차에서 실측 결과와 함께 받는다 |
| 2 | `SKILL.md` 편집 때 **`document-convention` 이 함께 뜨지 않는다** | 실측으로 확인(③ 테스트 T3). **실질 손해가 없어 관찰만 한다.** 예외를 명시하면 판정이 늘어난다. 문제가 생기면 그때 라우팅 표에 예외를 넣는다 |
| 3 | **받는 쪽 안내가 없다** ★ | 배포는 우리가 하는 전제라 **직접 가져가려는 사람이 볼 문서가 없다.** Project_B 에서 작업자가 `templates/` 가 아니라 루트 문서를 긁어갔고, **다음 프로젝트에서 그대로 반복된다.** `templates/` 에 넣을지 별도 안내를 만들지 판단이 필요하다 (`DH:project-b-deploy`) |
| 4 | **「세션은 저장소 루트에서 연다」를 `templates/` 에 넣을지** | Project_B 진입점에만 넣었다. **중첩 구조가 아닌 프로젝트에는 불필요**한데 넣으면 전 프로젝트가 받는다. Project_C 가 모노레포라 그때 판단이 유력하다 |
| ~~5~~ | ~~**`git-procedure` · `session-routine` 의 `review.md` 가 §6.1 상한을 넘긴 채 방치돼 있다**~~ | ✅ **해소 (2026-09-09)** — **110KB · 92KB → 2.3KB · 2.0KB.** 판정은 각 `plan.md` 결정 이력과 개발 이력에 이미 있었고, 남아 있던 것은 **왕복 과정과 ③ 테스트 결과 중복**이었다. 회차 요약과 가장 값이 컸던 판정만 남기고 비웠다.<br>**비우면서 닫힌 이월 항목 넷** — `git-procedure` 훅 실사용 확인(직접 검증 5/5), `session-routine` 미결정 2·3·4(각 스킬에서 이미 확정돼 있었다).<br>**낡은 포인터도 함께 고쳤다** — `plan.md` 들이 *"지적 원문이 `review.md` 에 남아 있다"* 고 가리키고 있었다 |

> **구현하면서 정해진 것 둘**
>
> **배포 대상 목록 위치** — 진입점 §2 구조 표에 자체/배포로 갈라 표기하고, **행위 금지**(*"스킬 폴더를 통째로 복사하지 않는다"*)를 §0.2 안전망에 넣었다. 목록만으로는 대조를 요구하지만 **행위 금지는 통째 복사 자체를 막는다.** 상세 목록은 이 스킬 §5.2 에 둔다.
>
> **라우팅 행 문구** — *"스킬을 만들거나 실 프로젝트에 배포한다 — `.claude/skills/` · `.agents/skills/` · `templates/` 편집 포함"*. 파일 축과 발화 축을 한 행에 담았고, ③ 테스트에서 **양쪽 다 발동을 확인**했다.
