> 저장소 차원의 규칙(3층 배치 · 배포 경로 · 충돌 판정 · 파이프라인)은 [`CLAUDE.md`](../../../CLAUDE.md) 에 있다. 여기에 복제하지 않는다.

> **아침과 마무리를 한 스킬에 넣은 이유** — 절차는 다르지만 **서로 짝**이다. 마무리가 남긴 것을 다음 날 아침이 집어 든다. 스킬은 세션당 1회 로드라 나눠도 비용이 안 줄고, 아침에 로드한 것이 저녁 마무리까지 살아 있는 편이 낫다.

> **절 번호를 재배열하지 않는다.** 이 문서의 절 번호를 다른 문서와 개발 이력이 가리킨다. 절이 사라져도 뒤 번호를 당기지 않고, 새 절은 뒤에 붙인다.

## 담당 범위

| 담당한다 | 담당하지 않는다 |
|---|---|
| 아침루틴 절차 | 문서 **포맷** → `document-convention` |
| 마무리 절차와 순서 | 깃 절차 → `git-procedure` |
| 완료 정의 · 중간 상태 표현 | 코드 편집 규칙 → `code-convention` |
| 테스트 로그를 **언제 제거하나** (마무리 1단계) | 테스트 로그의 **마커·심기·제거 절차** → `code-convention` **Part D** |
| 문서 검증 **실행 시점** | 문서 검증에서 **무엇을 확인하나** → `document-convention` |
| 처리한 보류를 **완료로 갱신하는 시점** | 문서 **병합·정리** → **아무도 안 맡는다** (아래 판정) |

**규약을 요약 복제하지 않는다.** "해당 스킬을 읽고 계속한다"고만 지시한다 — 오케스트레이터가 규약을 요약하면 drift 가 생긴다.

### 기존 스킬과의 충돌 검사

| 겹침 | 판정 | 근거 |
|---|---|---|
| `document-convention` 의 문서 검증 — *"명령은 고정하지 않는다"* | **해소** | 이 문서가 검증 명령을 고정하고 있었다. **정반대 지시라 2중 조건이었고, 명령 고정을 철회**했다. 이 스킬은 **실행 시점만** 정한다 (2026-08-25) |

| `code-convention` Part B §2 — 외과적 변경 · 찌꺼기 정리 | **포인터** | 로그 제거는 소스 편집이다. **그쪽이 「본인 수정으로 새로 생긴 미사용 심볼 정리」를 허용**하므로, 로그를 지우며 생긴 찌꺼기는 그 기준으로 함께 정리한다. 판정의 원본은 그쪽이다 |
| `document-convention` 의 문서 **병합·정리** | **반려** | 그쪽이 *"병합·정리는 `session-routine` 소관"* 이라고 넘겼으나 **받지 않는다.** 병합·정리는 사용자가 원할 때 하는 일이지 규칙으로 굳힐 성질이 아니다. **넘긴 문장을 `document-convention` 에서 회수해야 한다** (§10) |
| Claude 내부 memory 기록 | **폐기** | 원래 이 스킬이 가져왔으나, Codex·Cursor 가 접근하지 못해 3종 공용이 아니다. 대체안이던 레포 인덱스도 함께 폐기했다 (§7 결정 8·9·10) |

## 0. 발동 기준 — 「사용자 발화」

**다른 세 스킬과 발동 축이 다르다.**

| 스킬 | 무엇으로 발동하나 |
|---|---|
| `code-convention` | 건드리는 **파일** |
| `document-convention` | 건드리는 **파일** |
| `git-procedure` | 실행하는 **명령** |
| **`session-routine`** | **사용자의 발화** |

**발화가 없으면 이 스킬은 뜨지 않는다. 그것이 의도다.** 파일이나 명령으로 발동하면 아무 작업에나 루틴이 끼어든다.

### 문장으로 부른다

원래 이런 스킬은 이름을 정확히 불러야 실행된다. **그 스킬을 평소 쓰는 말로도 부를 수 있게 만드는 것이 이 설계의 목적이다.**

| 루틴 | 발화 예 |
|---|---|
| 아침 | *"시작루틴 하자"* · *"아침루틴 시작하자"* · *"아침루틴 하자"* · *"이어서 하자"* |
| 마무리 | *"마무리루틴 하자"* · *"마무리 작업하자"* · *"오늘 마무리"* · *"정리하고 올리자"* |

**루틴 이름이 축이다.** 줄여 말한 것(*"마무리"* · *"정리하자"* · *"이어서"*)도 잡는다.

**단순 질문은 트리거가 아니다.** *"어제 뭐 했지"* 같은 말은 **루틴 실행 지시가 아니라 질문**이다. 트리거에 넣으면 물어보기만 했는데 원격에서 받아오게 된다. **이런 발화는 규칙으로 굳히지 않고 에이전트 판단에 맡긴다** — 규칙을 하나 줄이는 쪽이 맞다.

### 애매하면 실행 전에 묻는다 ★

발화가 잡혔는데 **어느 루틴인지, 어디까지 하라는 것인지 애매할 수 있다.** 그때는 추측해서 실행하지 않는다.

- 저장 안 한 변경과 최근 대화 맥락을 보고 **먼저 판단해본다**
- 그래도 애매하면 **선택지를 제시하고 확인받는다**

```
"마무리하자"
  → 저장 안 한 변경에 코드 수정이 있음
  → "어떤 마무리를 말씀하신 건가요?
       ① 마무리루틴 전체 (로그 제거 → 이력 작성 → 올리기)
       ② 지금 것만 저장하고 올리기"
```

**이미 명시적으로 지시받은 것을 되묻지 않는다.** *"마무리루틴 하자"* 는 애매하지 않다.

### 스킬은 하나, 이름도 하나

슬래시로 부르면 `/session-routine` 하나이고, **아침인지 마무리인지는 문장이 가른다.** 슬래시로도 갈라 부르고 싶으면 인자를 받는 방식(`/session-routine start`)이 되며, 그때도 스킬은 하나로 유지한다 — 둘로 쪼개면 목록 예산을 두 배로 쓴다 (§7 결정 1).

### 다른 스킬과 함께 뜬다

마무리 발화에는 깃 신호가 섞이는 일이 많다 (*"정리하고 올리자"*). 진입점 규칙이 이미 **여러 스킬이 동시에 해당하면 모두 로드한다**고 정하고 있으므로 새로 정할 것은 없다. **다만 실제로 둘 다 뜨는지는 고정 테스트 T4 가 본다.**

## 1. 아침루틴

**하는 일은 둘이다** — ① 내가 없는 사이 뭐가 바뀌었는지 알려주고, ② 지난 작업 기록을 머릿속에 올린다.

```
1. 받아올 것이 내 작업과 겹치는지 본다      ← 게이트
2. 받기                                    → git-procedure 의 pull 안전 규칙만
3. 새로 들어온 것 정리해서 보고
4. docs/develop-history/ 를 읽는다          ← 진실원
5. 보류 수집 → 브리핑 → 다음 작업 제안
```

**1~3 과 4~5 는 독립이다.** 받기는 깃 상태를 타지만 **개발 이력 읽기와 브리핑은 깃과 무관**하다. 그래서 **게이트에 걸려 받기를 멈춰도 4·5 는 진행한다.** 이게 없으면 게이트가 걸릴 때마다 루틴이 통째로 죽고, 몇 번 반복되면 사용자가 게이트를 우회하게 된다.

### 1단계 — 받아올 것이 내 작업과 겹치는지 본다 ★

**판정 축은 「저장 안 한 변경이 있는가」가 아니라 「받아올 파일과 내가 고친 파일이 겹치는가」다.**

```
git fetch
받아올 파일 목록  ∩  내가 고친 파일 목록

교집합 없음   → 그대로 받는다
교집합 있음
   ├ 에셋이 하나라도 있으면          → 중단
   ├ 같은 줄을 건드렸으면 (덮어써야)  → 중단
   └ 줄이 안 겹치면 (합칠 수 있으면)  → 확인을 받고 진행
```

**왜 dirty 자체가 아니라 겹침인가**

- **git 이 이미 막는다.** 겹치는 채로 받으면 git 이 거부하고 아무것도 바꾸지 않는다. **이 게이트의 값어치는 「막아주는 것」이 아니라 「먼저, 알아듣게 알려주는 것」이다**
- dirty 자체를 기준으로 삼으면 **유니티가 만든 설정 파일 하나 때문에 아침루틴이 통째로 잠긴다.** 실제로 배포 대상 프로젝트에 그런 파일이 2주 넘게 커밋되지 않은 채 남아 있었다 (2026-08-25 실측)

**에셋은 줄 판정을 하지 않는다.** `git-procedure` §2.1 이 *"충돌이든, 충돌 없이 양쪽이 같은 파일을 건드렸든 항상 사용자에게 넘긴다"* 로 이미 못박았다. 겹치는 파일이 프리팹·씬·`.meta`·데이터 자산이면 **줄이 안 겹쳐도 중단**이다.

**합칠 수 있을 때 — 확인을 받는다**

미커밋 변경을 그대로 둔 채 받는 방법은 git 에 없다. **실체는 「잠시 치워두고 → 받고 → 되돌려놓기」이며, 이는 진입점 §0.2 가 금지한 조작이다.** `git-procedure` §1.2 의 *"사용자가 지시했을 때만"* 이 그 예외 경로이므로, **확인 문구가 무슨 일이 일어나는지 드러내야 한다.**

> 작업 중인 내용을 **잠시 치워두고 받은 뒤 다시 되돌려놓습니다.** 되돌릴 때 같은 줄을 건드린 게 있으면 멈추고 알려드립니다. 진행할까요?

- **승인 없이 실행하지 않는다.** "합칠 수 있으니 진행했습니다" 는 금지다
- 판정은 **미리** 한다 — 해보고 충돌이 나면 사용자 작업 파일에 충돌 표시가 박힌다. 이 스킬은 그걸 스스로 풀 수 없는 사람을 전제한다

**중단할 때**

- 겹치는 파일을 **이름과 종류**로 알린다. 경로를 그대로 붙이지 않는다
- **「보관할지·되돌릴지」를 선택지로 내밀지 않는다.** 둘 다 진입점이 금지한 조작이고, **AI 가 먼저 권하면 위험 조작이 일상이 된다**
- 다음에 무엇을 하면 되는지 한 줄로 끝맺는다

> 지금 작업 중인 파일 중 2개가 받아올 내용과 겹칩니다.
> — Player 프리팹 · 전투 설정 파일
> 이 작업을 먼저 마무리하시면 이어서 받겠습니다. 오늘 할 일 브리핑은 아래에 이어서 드립니다.

**공통**

- 임의로 저장하지 않는다. 자동 커밋 금지다
- **임의로 치워두지도 않는다.** 되돌리기 어려운 조작이다
- 이 상태에서 `git-procedure` 의 전체 흐름(`commit → fetch → pull → push`)을 대신 실행하지 않는다. 사용자가 남은 작업을 마무리하라고 지시하면 **마무리루틴**으로 전환한다

### 2·3단계 — 받고, 무엇이 들어왔는지 말한다

받기 자체는 `git-procedure` 의 안전 규칙을 탄다. 단, 아침루틴은 **받기만 하는 흐름**이다.

**비교 기준을 git 이 남기는 표시에 맡기지 않는다.** ★

```
① 받기 전에 현재 위치를 기억해둔다
② 받는다
③ 위치가 그대로면  → "새로 들어온 것 없습니다" 로 끝낸다
   움직였으면      → ①에서 기억한 값과 지금을 비교한다
```

git 은 「받기 직전 위치」 표시(`ORIG_HEAD`)를 **실제로 뭔가 받았을 때만** 갱신한다. **받을 게 없는 날에는 지난번 값이 그대로 남아**, 그 표시를 그냥 쓰면 **어제 받은 것과 그 뒤 내가 만든 커밋까지 「오늘 새로 들어온 것」으로 보고**하게 된다. 주말 다음이나 혼자 작업한 다음 날마다 난다.

**명령은 여기에 적지 않는다.** 받기의 원본은 `git-procedure` 이고, 명령을 복사해두면 원본이 바뀔 때 이쪽 사본이 조용히 낡는다 — 이 문서가 담당 범위에서 스스로 금지한 것이다.

받은 뒤 **무엇이 추가·수정·삭제됐는지 정리해 보고한다.**

- 파일 목록을 그대로 붙이지 않는다. **무엇이 바뀌었는지를 말로** 옮긴다
- 자동으로 합쳐진 에셋이 있으면 `git-procedure` **`SKILL.md` §2.3** 대로 함께 알린다

> **절 번호는 `SKILL.md` 기준이다.** `git-procedure` 는 설계 문서와 `SKILL.md` 의 절 번호가 서로 다르다 (설계 §2.2 = `SKILL.md` §2.3). **에이전트가 런타임에 읽는 것은 `SKILL.md`** 이므로 그쪽을 가리킨다. 4회차까지 이 문서는 설계 문서 번호를 쓰다가 한 번 잘못 정정된 적이 있다.

### 4단계 — 개발 이력을 읽는다

**진실원은 `docs/develop-history/` 다.** 요약본을 따로 두지 않는다 (§7 결정 10).

- **기본은 최근 10건**이다. 파일명에 날짜가 있어 정렬만으로 순서가 나온다
- 최근 10건 안에 `## 보류` 항목이 있으면, 그 항목의 키워드로 과거 개발 이력을 추가 검색한다
- **검색은 깃이 추적하는 파일만 대상으로 한다.** 빌드 캐시·중간 산출물을 훑지 않는다
- 이미 이번 세션에서 읽은 문서를 다시 읽을지는 에이전트 재량이다. 아침루틴은 보통 **세션을 새로 여는 시점**에 돌아 컨텍스트가 비어 있다

### 5단계 — 보류를 모아 브리핑한다

**4단계에서 읽은 내용에서 보류를 뽑는다.** 문서를 이미 읽었으므로 그 안의 `## 보류` 절이 함께 들어와 있다.

> **셸 검색으로 대체하지 않는다.** 이 저장소의 문서는 **한글이고 BOM 이 없어**, PowerShell 5.1 로 검색하면 시스템 기본 인코딩으로 읽혀 **에러 없이 「0건」이 나온다.** 보류가 있는데 *"보류 없음"* 으로 브리핑되고 아무도 눈치채지 못한다. 문서가 늘어 전부 읽기가 무거워져도 **셸 검색으로 갈아타지 않는다** — 네이티브 파일 도구를 쓴다.

**마무리가 남긴 것을 아침이 집어 드는 연결이 이 설계의 이점이다.**

```
최근 작업

- 08-20  스킬 마스터 정리, docs 재작성 결정        DH:docs-reset
- 08-19  code-convention 배포                     DH:convention-deploy

보류 중인 것 2건
- framework-dotnet 보강 — 재개 조건: 실제 .NET 코드를 볼 수 있을 때
- 배포 플랜 문서 갱신 — 재개 조건: 스킬 3종 완성 후

먼저 진행할까요?  ① dotnet 보강  ② 플랜 갱신  ③ 새 작업
```

**게이트 강도 = 소프트.** 브리핑하고 제안까지 하되, 사용자가 다른 걸 시키면 그대로 따른다.

## 2. 마무리 루틴

**하는 일은 넷이다** — ① 심어둔 디버그를 걷어내고, ② 작업 결과물을 먼저 올리고, ③ 문제가 없을 때 오늘 한 일을 기록하고, ④ 기록 문서를 다시 올린다.

```
0. 작업물 완료 검증             ← 증거 확보
1. 테스트 로그 제거              → §4
2. 작업물 재검사                 ← 필수
3. 작업물 깃 작업                → git-procedure
4. 개발 이력 문서 작성           → document-convention
   + 처리한 보류를 완료로 갱신
4.5 문서 재검사                  ← 필수
5. 문서 깃 작업                  → git-procedure
```

**개발 이력은 작업물 깃 작업이 끝난 뒤에 쓴다.** 문서에 "마무리했다"고 먼저 써놓고 정작 작업 결과물을 올리다 막히면 기록이 거짓이 된다.

**로그 제거는 사용자가 따로 지시하지 않아도 한다.** 마무리 발화를 받으면 **먼저 알리고 지운다** — *"이 작업은 완료됐으니 방금 심은 테스트 로그를 삭제하겠습니다."* 사용자가 *"로그 지워"* 라고 말해야만 지우는 구조면, 잊는 순간 그대로 올라간다.

### 0단계 — 완료 검증

작업물을 올리기 전에 그것을 증명하는 확인을 **이번 세션에서** 실행한다.

**「검증」을 둘로 나눈다. 에이전트가 할 수 있는 것과 없는 것이 다르기 때문이다.** ★

| 무엇을 확인 | 누가 | 못 했을 때 |
|---|---|---|
| **컴파일이 통과하는가** | **에이전트** — 엔진 재컴파일·콘솔 확인 또는 IDE 빌드 | **여기서 멈춘다.** 실제로 할 수 있는 일이므로 정당한 게이트다 |
| **의도대로 동작하는가** | **사용자** — 실행해보고 확인 | 멈추지 않는다. `## 보류` 에 *"동작 확인 미실시"* 를 남기고 진행한다. 사용자가 확인했다고 하면 **출처를 밝혀** 기록한다 |
| **문서·스킬만 바꿨을 때** | 에이전트 | 실행 검증 불필요. `document-convention` 의 문서 검증 절이 정한 것을 확인한다 |

> **왜 「빌드·실행」이 아니라 「컴파일 통과」인가** — 에이전트는 게임 빌드를 돌릴 수 없다. 라이선스가 필요하고 수 분~수십 분이 걸려 도구 시간제한에 들어가지 않는다. **못 하는 것을 요구하면 코드를 만진 날마다 0단계에서 멈추고, 그게 반복되면 우회 해석이 자리잡는다** — *"컴파일 에러가 없으니 확인된 걸로 본다"* 같은 것이. **그게 바로 §3 이 막으려는 거짓 기록이다. 지킬 수 있는 선으로 낮추는 것이 목적을 지키는 길이다.**

**검증 명령을 이 문서에서 고정하지 않는다.** `document-convention` 이 *"명령은 고정하지 않는다 — `rg` 가 없는 환경이 있고 PowerShell 과 Bash 의 이스케이프가 다르다"* 고 정해두었다. **무엇을 확인하는가는 그쪽이 정하고, 언제 확인하는가만 여기서 정한다.**

스킬을 고쳤으면 **마스터와 복사본의 일치 확인**도 이 단계에서 한다.

**검증하지 못한 항목은 없던 일로 만들지 않는다.** 작업물 깃 작업 전이면 루틴을 멈추고 사용자에게 보고한다. 개발 이력 문서를 쓰는 4단계 이후에 발견한 문서 검증 미완료는 `## 보류` 절로 내린다.

### 순서가 고정인 이유

로그를 지우기 전에 저장하면 테스트 로그가 저장 대상에 들어간다. 반대로 개발 이력 문서를 먼저 쓰면, 작업 결과물을 올리다 충돌·인증·원격 거부로 막혔을 때 **"마무리했다"는 문서가 거짓**이 된다.

그래서 마무리는 두 번 저장한다.

1. **작업물 깃 작업** — 코드·데이터·스킬·문서 작업물 자체를 먼저 올린다
2. **문서 깃 작업** — 작업물 반영이 성공한 뒤 개발 이력 문서를 쓰고 다시 올린다

### 2단계 — 작업물 재검사 (필수)

로그를 제거하는 동안에도 파일이 바뀐다. **작업물 깃 단계 직전에 한 번 더 본다.**

- 변경 목록을 **다시 실행하고 그 출력을 답변에 남긴다**
- `AIDEBUG` 가 남아 있는지 **다시 찾고 그 결과를 남긴다.** 검색 범위는 깃이 추적하는 파일이다

> **"다시 확인한다"로만 적으면 안 한다.** 방금 본 것을 또 보라는 말이라 *"직전에 확인했다"* 로 넘어간다. **출력을 남기게 하면 안 돌린 것이 드러나므로 실제로 돌린다.**

### 4단계 — 개발 이력 문서와 보류 갱신

문서 작성은 `document-convention` 을 따른다. 여기서는 **시점**만 정한다.

**이어지는 작업이면 기존 문서를 이어 쓴다.** 10일에 시작해 11일에 끝난 작업은 **한 작업이므로 문서도 하나**다. `document-convention` 의 *"작업 하나 = 문서 하나"* 가 그대로 적용된다 — *"매번 새로 만든다"* 는 **작업이 다를 때** 얘기다.

**처리한 보류를 그 자리에서 완료로 갱신한다.** ★

- 이번 작업이 **과거 문서의 보류를 처리했으면**, 그 문서를 열어 해당 항목을 완료로 고치고 변경 이력에 한 줄 남긴다
- 별개 작업이라 새 문서를 썼더라도 **원래 보류가 적혀 있던 문서는 갱신한다.** 그 보류를 보고 시작했으므로 어디 있었는지 안다
- 안 하면 **이미 처리한 항목이 최근 10건 창 안에 있는 동안(약 2주) 매일 아침 브리핑에 뜬다.** 며칠이면 사용자가 브리핑을 안 보게 된다

> **「지난 문서를 고쳐 쓰지 않는다」와 구분한다.** 그 규칙은 **이미 쓴 내용을 나중에 바꾸지 말라**(기록 왜곡 방지)는 뜻이다. **보류의 상태를 갱신하는 것은 기록을 바꾸는 것이 아니라 현재 상태를 반영하는 것**이다.

### 4.5단계 — 문서 재검사 (필수)

개발 이력 문서를 쓴 뒤, 문서 깃 작업 직전에 한 번 더 본다.

- 변경 목록을 **다시 실행하고 그 출력을 답변에 남긴다**
- 문서 검증은 `document-convention` 이 정한 항목을 따른다

### 각 단계의 게이트

| 단계 | 게이트 |
|---|---|
| 0 검증 | **컴파일이 안 통과하면 중단.** 동작 확인은 못 해도 중단하지 않고 보류로 남긴다 |
| 1 로그 제거 | 마커 없는 의심 항목은 **목록만 제시하고 확인**. 블록 삭제는 **범위 미리보기 후** |
| 2 작업물 재검사 | 누락 발견 시 1로 되돌아감. **출력을 남기지 않았으면 안 한 것으로 본다** |
| 3 작업물 깃 | `git-procedure` 의 멈춤 조건을 그대로 따른다. 실패하면 개발 이력 문서를 쓰지 않는다. **다만 애매하게 끝난 올리기는 실패로 판정하지 않는다** (§3) |
| 4 문서 작성 | 작업물 깃 작업이 성공했을 때만. 처리한 보류 갱신을 함께 한다 |
| 4.5 문서 재검사 | 누락 발견 시 4로 되돌아감 |
| 5 문서 깃 | `git-procedure` 의 멈춤 조건을 그대로 따른다 |

## 3. 완료 정의 — 중간 상태를 정확히 남긴다 ★

"완료"의 기준은 **사용자가 요청한 범위**다. 푸시까지가 요청이면 푸시까지, 커밋까지가 요청이면 커밋까지다.

| 상황 | 개발 이력 처리 |
|---|---|
| 작업물 깃 작업 성공 + 문서 깃 작업 성공 | `## 검증` 에 결과. 정상 완료 |
| 사용자가 **"커밋만"** 을 명시 | "로컬 저장 완료 (올리기는 요청 범위 밖)" — **정상 종료다** |
| 작업물 깃 작업 중 **막힘**(충돌·인증·원격 거부 등) | 개발 이력 문서를 아직 쓰지 않는다. 작업이 마무리되지 않았기 때문이다 |
| 문서 깃 작업 중 **막힘** | 작업물은 반영 완료. 개발 이력 문서의 원격 반영만 보류 상태로 보고한다 |
| 검증 일부만 됨 | 작업물 깃 작업 전에 멈추고, 완료로 취급하지 않는다 |

**"막힘"과 "요청 범위 밖"을 구분하는 것이 핵심이다.** 둘 다 원격에 안 올라간 상태지만, 전자는 다음 날 이어서 해야 할 일이고 후자는 정상 종료다. 구분하지 않으면 아침 브리핑이 거짓이 된다.

**작업물 깃 작업이 막힌 경우에는 개발 이력 문서를 쓰지 않는다.** 작업이 끝났다고 말할 근거가 없기 때문이다.

### 애매하게 끝난 올리기를 실패로 판정하지 않는다 ★

`git-procedure` 가 이미 경고한 상황이다 — **대용량 파일이 섞인 첫 올리기는 수 분이 걸리는데 도구 기본 제한은 2분**이라, **시간 초과가 「실패」로 보인다.**

여기서 오판하면 손해가 크다. 실제로는 올라갔는데 *"막힘"* 으로 분류되어 **개발 이력 문서를 아예 안 쓰게 된다.**

> **불명확하게 끝난 올리기는 실패로 판정하지 않는다.** `git-procedure` 대로 **원격 상태를 다시 확인한 뒤** 판정한다.

### 문서 올리기만 막힌 경우

**드문 경우다.** 개발 이력은 `날짜-이름.md` 로 매번 새 파일이 만들어져 충돌이 날 여지가 거의 없고, 한 프로젝트를 동시에 만지는 인원도 한두 명이다.

그래서 **별도 규칙을 두지 않는다.** 막히면 평문으로 보고하되, **작업물은 이미 올라갔다는 사실을 분명히 한다** — *"실패했습니다"* 라고만 하면 사용자는 오늘 일한 결과물까지 안 올라간 줄 안다.

> 오늘 작업한 내용은 모두 올라갔습니다. **기록 문서만 아직 올리지 못했습니다.**

## 4. 테스트 로그 규약

> ⚠️ **이 절의 규약은 2026-08-25 에 `code-convention` Part D 로 이관됐다.** 심는 것도 지우는 것도 소스 파일 편집이기 때문이다. **현재 유효한 원본은 그쪽이고, 이 절은 설계 경위 기록으로 남긴다.**
>
> **이관 후 달라진 것 셋** — ① 마커가 `AIDEBUG` 에서 **`AITESTLOG_<컨텐츠명>`** 이 됐다. 우리 문서가 전부 「테스트 로그」라고 부르는데 마커만 `DEBUG` 라서 둘이 다른 것처럼 보였다 ② 로그 3분류는 **빌드 가드가 범위 밖이라 2분류**로 시작한다 ③ 4.5 의 *"빌드 가드가 필요하다고 알린다"* 는 **"출시 빌드에도 나간다고 알린다"** 로 바뀌었다.
>
> **아래 §4 본문의 `AIDEBUG` 표기는 당시 기록이므로 고치지 않는다.**
>
> 판정 근거는 [`../code-convention/plan.md`](../code-convention/plan.md) 에 있다.

### 4.1 상위 맥락 — Log-First 디버깅

로그 제거는 독립 작업이 아니라 **디버깅 루프의 마지막 단계**다.

```
추측 수정 금지
  → 의심 경로 분기점에 로그를 먼저 심는다
  → 빌드·실행, 사용자 테스트 요청
  → 로그 분석으로 실제 실행 경로 식별
  → 원인 특정 후 수정
  → 마무리에서 로그 제거          ← §2 의 1단계
```

한 번 추측 수정이 실패하면 즉시 로그 방식으로 전환한다.

### 4.2 마커는 2중이다 ★

목적이 다른 마커가 **둘** 필요하다. 하나만 있으면 반쪽이다.

| 마커 | 위치 | 목적 |
|---|---|---|
| **`[AIDEBUG]`** | **로그 문자열 안** | **런타임 출력 필터링** — 수천 줄 로그에서 이번에 심은 것만 골라 본다 |
| **`// TODO: AIDEBUG — 제거 예정 (조건)`** | 주석 | 소스 검색으로 찾아 제거 |

첫 번째가 빠지면 **"로그를 AI 가 읽는다"는 목적 자체가 성립하지 않는다.** 두 번째가 빠지면 지울 때 못 찾는다.

키워드는 **전 프로젝트 공통 `AIDEBUG`** 로 한다. 스킬이 여러 프로젝트 공용이라 검색어가 하나여야 한다.

> **전제의 한계** — "에이전트가 심으니 마커 누락이 없다"는 **에이전트가 새로 심는 로그에만** 성립한다. 사용자가 붙여넣은 코드, 이전 세션의 수동 로그, 인스펙터에서 켠 디버그 옵션, 서드파티 logger 를 쓰는 코드는 마커가 없다. 그래서 규칙을 **"에이전트가 새로 심는 임시 로그는 반드시 2중 마커"** 로 좁혀 쓰고, 마커 없는 로그는 §4.4 의 **목록 제시 → 확인** 경로로 처리한다.

> **릴리스 검증** — `[AIDEBUG]` 가 릴리스 빌드 산출물에 남아 있으면 **실패로 판정한다.** 사용자에게 노출되는 문자열이다.

### 4.3 형식

**한 줄 로그**

```csharp
Debug.Log($"[AIDEBUG] 보스 페이즈 전환: {phase}, HP {hp}");   // TODO: AIDEBUG — 제거 예정 (원인 특정 후)
```

주석은 줄 **위**가 아니라 줄 **끝**에 붙인다. 제거가 한 줄 삭제로 끝난다.

**테스트용 코드 블록**

```csharp
// [AIDEBUG-BEGIN] 치트키 — 제거 예정 (보스 페이즈 버그 수정 후)
if (Input.GetKeyDown(KeyCode.F9)) { SpawnBoss(); }
// [AIDEBUG-END]
```

치트키·강제 스폰·조건 우회처럼 로그가 아닌 테스트용 코드가 대상이다. 로그 한 줄만 지우면 빈 `if` 껍데기가 남는 문제를 막는다.

**세 형식 모두 `AIDEBUG` 한 단어로 찾힌다.**

> **`TEMP` 를 쓰지 않는 이유** — `tempPos` 같은 변수명, *"임시 우회 — 서버 패치 전까지 유지"* 처럼 **남아야 할** 주석까지 걸린다. 지우면 안 되는 것과 지워야 하는 것이 같은 단어를 쓴다.

### 4.4 제거 절차

1. `AIDEBUG` 를 찾는다 — **검색 범위는 깃이 추적하는 파일**이다. 빌드 캐시·중간 산출물을 훑지 않는다
2. **삭제 범위를 먼저 보고한다** — 파일별 줄 범위. 블록은 통째로 지우므로 미리보기 없이 삭제하지 않는다
3. 라인 마커는 해당 줄 삭제 · 블록 마커는 블록 통째 삭제
4. 마커 없는 의심 로그는 **목록만 제시하고 확인받는다** (규약 도입 이전 로그)
5. 사용자가 "이건 남겨줘" 하면 §4.5 로 간다

**블록 삭제 안전 규칙 ★**

블록 삭제는 강력해서 잘못되면 정상 코드가 같이 사라진다.

- **`END` 없는 `BEGIN` 은 삭제하지 않는다.** 보고만 하고 사용자 판단을 받는다
- **중첩(`BEGIN` 안의 `BEGIN`)은 삭제하지 않는다.** 규약 위반이므로 보고한다
- 한 파일에 블록이 여러 개면 **각각의 범위를 따로 계산**하고 전부 보고한다
- 삭제 후 실제 삭제 범위를 확인한다

**마커 없는 로그 탐색 (보조)**

규약 도입 이전 로그를 잡으려면 로그 API 자체를 훑는다. `Debug.Log` 한 줄이 전부가 아니다 — `LogWarning` · `LogError` · `print` · 커스텀 logger · `ILogger` wrapper 도 있다. 프로젝트가 쓰는 진입점을 목록에 넣는다.

**이 탐색 결과는 자동 삭제하지 않는다 — 목록 제시 후 확인이다.**

**로그 제거는 소스 편집이므로 `code-convention` 이 함께 발동한다.**

**로그 때문에 생긴 찌꺼기는 함께 정리한다.** ★ 로그 한 줄을 지우면 **그 로그만 쓰던 변수나 import 가 남는다.** 그건 로그의 일부이므로 같이 없앤다. `code-convention` 이 *"본인 수정으로 새로 생긴 미사용 심볼 정리"* 를 허용하고 있고, **판정의 원본은 그쪽이다.**

**다만 두 가지는 건드리지 않는다.**

- 로그와 **무관한** 인접 코드 — 정리·스타일 보정·자발적 리팩터 금지
- 디버그 출력과 **같은 블록에 있는 정상 로직**

> 마커를 파일에 남기는 이유는 **컨텍스트가 날아가도 기록이 남기 때문**이다. 긴 세션은 중간에 요약이 일어나 "어디에 로그를 심었는지"를 잊는다. 이전 세션에서 못 지운 로그도 다음 마무리에서 같이 걸린다.

### 4.5 이미 심은 것을 남기기로 할 때 ★

**임시 로그와 계속 쓸 디버그 도구는 다른 물건이다.**

| | 정체 | 처리 |
|---|---|---|
| **임시 로그** | 원인 특정 후 사라질 것 | **제거** — 본 절 |
| **상주 디버그 도구** | 계속 쓸 콘솔 커맨드 · 디버그 드로우 · 치트 | **빌드 가드** — 범위 밖 |

사용자가 *"이건 남겨줘"* 하는 순간이 **상주 전환**이다. 마커만 떼고 끝내면 안 된다. **빌드 가드가 필요하다는 것을 알린다.**

> **에디터에서 되는 것이 빌드에서 된다는 뜻이 아니다.** 에디터 전용 가드 안에만 있는 심볼을 가드 밖에서 참조하면 **에디터는 무증상이고 빌드에서만 깨진다.** Origin 프로젝트에서 최초 쉬핑 빌드에 미가드 18곳이 한꺼번에 터진 사례가 있다 (2026-07-16).

**이 절은 「이미 심은 것을 나중에 남기기로 할 때」만 다룬다.** 심기 전에 임시인지 상시인지 가르는 규칙과 빌드 가드 상세는 **`code-convention` 소관**이다 (§10).

| 26 | **단순 질문은 트리거가 아니다** | *"어제 뭐 했지"* 는 질문이지 루틴 지시가 아니다. 트리거에 넣으면 물어보기만 했는데 받아온다. **규칙으로 굳히지 않고 에이전트 판단에 맡긴다** — 규칙이 하나 준다 |
| 27 | 발화가 **애매하면 실행 전에 묻는다** | 축약 발화까지 잡되, 어느 루틴인지 모호하면 선택지를 낸다. 이미 명시적으로 지시받은 것은 되묻지 않는다 |
| 28 | **로그 찌꺼기는 함께 정리**한다 | 로그만 쓰던 변수·import 는 로그의 일부다. `code-convention` 이 「새로 생긴 미사용 심볼 정리」를 허용하고 있고 판정의 원본은 그쪽이다 |
| 29 | **애매하게 끝난 올리기를 실패로 보지 않는다** | 대용량 파일 올리기는 시간 제한을 넘겨 **성공했는데 실패로 보인다.** 오판하면 개발 이력을 아예 안 쓰게 된다 |
| 30 | 문서 올리기 실패에 **별도 규칙을 두지 않는다** | 날짜별 새 파일이라 충돌 여지가 거의 없고 인원도 한두 명이다. 막히면 평문 보고하되 **작업물은 올라갔다는 사실을 분명히** 한다 |
| 31 | 문서 **병합·정리를 맡지 않는다** | 사용자가 원할 때 하는 일이지 규칙으로 굳힐 성질이 아니다. `document-convention` 이 넘긴 문장을 **회수해야** 한다 |
| 32 | 재검사는 **출력을 답변에 남긴다** | *"다시 확인한다"* 는 방금 본 것을 또 보라는 말이라 넘어간다. 출력을 남기면 안 돌린 것이 드러난다 |
| 33 | 진입점에는 **블록 삭제 미리보기만** 올린다 | 판정 기준은 **「그 순간에 다른 스킬이 뜨는가」**다 (§9) |

## 9. 진입점에 올릴 파국 방지 룰

[`CLAUDE.md`](../../../CLAUDE.md) §1.3 대로, **스킬이 안 떴을 때가 정확히 사고 나는 순간**이므로 가장 위험한 룰만 진입점에 복제한다. 절차 전체를 복제하지 않는다.

### 판정 기준 — 「그 순간에 다른 스킬이 뜨는가」 ★

**뜨면 중복이고, 안 뜨면 진입점에 올린다.** 진입점은 뒤가 잘릴 수 있는 문서라 항목을 늘리는 것이 공짜가 아니므로, 기준 하나로 자른다.

| 후보 | 그 순간에 뜨는 스킬 | 판정 |
|---|---|---|
| **블록 삭제 전 범위 미리보기** — `END` 누락·중첩이면 삭제하지 않는다 | 로그를 지우는 순간에는 `code-convention` 이 뜨는데, **거기엔 `AIDEBUG` 블록 개념이 없다** | **올린다.** 아무도 안 막아주는 구간이고, 사고가 나면 **정상 코드가 지워진다** |
| 검증하지 못한 것을 완료로 쓰지 않는다 | 개발 이력을 쓰는 것은 `.md` 편집이라 **`document-convention` 이 뜬다.** 거기 *"확인하지 못한 것은 보류로 내린다"* 가 이미 있다 | 안 올린다. **이미 막히는 것을 또 적으면 같은 말이 세 곳에 다르게 존재**하게 된다 |
| 받아올 것과 겹치면 받지 않는다 | — | 안 올린다. **git 이 알아서 거부**하므로 데이터가 날아가지 않는다 |

**올릴 문구는 한 줄로 압축한다.**

> `AIDEBUG` 블록을 지울 때는 범위를 먼저 보고한다. `END` 없는 `BEGIN` 과 중첩은 삭제하지 않고 보고한다

## 10. 다른 스킬에서 해야 하는 것

**이 스킬 하나로 끝나지 않는 항목들이다. 순서는 이 스킬을 확정한 뒤 한 번에.** 아직 없는 절을 미리 가리키면 에이전트가 없는 곳을 읽으러 간다.

### `code-convention` 으로 옮길 것 — ✅ **완료 (2026-08-25)**

> **이관 완료.** `code-convention` **Part D** 신설로 §4 전체가 넘어갔다. 아래 표는 당시 계획이며, **실제로는 「심기」뿐 아니라 「제거 절차」까지 함께 갔다** — 지우는 것도 소스 편집이라 같은 판정이 적용됐다 (사용자 결정). **빌드 가드는 범위 밖으로 빠졌다.** 결과는 [`../code-convention/plan.md`](../code-convention/plan.md).

**로그를 심는 순간에 뜨는 스킬은 `code-convention` 이지 이 스킬이 아니다.** 이 스킬은 *"마무리하자"* 에 뜨는데, 로그는 그 한참 전에 심는다. 심기 전 규칙을 여기 두면 **그 순간에 도달하지 않는다.**

| 옮길 것 | 내용 |
|---|---|
| **로그 3분류** | ① 임시 진단 로그 — 마커 붙이고 마무리에서 제거 · ② 상시 개발 로그 — 마커 없이 **빌드 가드 필수** · ③ 운영 로그 — 그대로 나감 |
| **심기 전 판정** | 로그를 심어달라는 요청을 받으면 **심기 전에 어느 종류인지 정한다.** 물어볼 문장은 하나면 된다 — *"원인을 찾으면 없어질 로그인가요, 계속 보실 로그인가요?"* |
| **기본값은 임시** | 되돌리는 비용이 비대칭이다. 임시로 잘못 심으면 지워지고 다시 심으면 되지만, **상시로 잘못 심으면 가드 없이 출시 빌드에 남는다** |
| **빌드 가드** | 에디터 전용 · 개발 빌드 전용 · 호출 자체를 컴파일에서 제거. Unity 심볼 표는 그쪽에서 정한다 |
| **`AIDEBUG` 이름 최종 확정** | 위 셋과 함께 정한다 (§8 미결정 1) |

**②에 마커를 붙이지 않는 것이 핵심이다.** 마커는 *"이건 지울 것"* 이라는 뜻이라, 남길 로그에 붙이면 다음 마무리에서 지워진다.

옮긴 뒤 이 문서의 §4 를 포인터로 바꾼다.

## 11. `description` 초안

**이 스킬은 발동 축이 발화**라, `description` 의 트리거 키워드가 곧 발동 조건이다. 파일이나 명령으로는 뜨지 않으므로 **키워드가 잘리면 이 스킬은 존재하지 않는 것과 같다.** `skill-pipeline` §4.4 대로 **트리거를 첫 문장에** 둔다.

```
시작루틴·아침루틴·마무리루틴·이어서 하자·정리하고 올리자 언급 시 로드한다. 줄여 말한 것도 대상.
세션을 열 때는 받기와 최근 개발 이력 읽기, 닫을 때는 디버그 로그 제거·작업물 올리기·개발 이력 작성이다.
각 단계의 순서와 멈춤 조건, 완료 정의의 단일 진실원. 규약 자체는 다른 스킬이 갖는다.
```

- 목표는 **250자 안팎**이다
- **트리거는 루틴 이름 중심**이다. *"어제 뭐 했지"* 같은 단순 질문은 **넣지 않는다** (결정 26) — 물어보기만 했는데 받아오게 된다
- **`줄여 말한 것도 대상`** 이 목록을 열어준다. 예시에 없는 축약도 잡힌다 (결정 27)
- **뺀 것** — 로드한 뒤 따를 절차(본문에 있다) · 호출하는 스킬 이름(본문에서 가리킨다) · 유사어 중복 · 낫표(매칭에 기여하지 않고 자릿수만 쓴다)
- 실제 길이와 잘림 여부는 **배포 후 실측으로 확인한다** (`skill-pipeline` §4.4 의 예산 실측과 같은 방식)
