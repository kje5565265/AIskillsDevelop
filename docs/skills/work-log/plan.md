## 이 스킬이 왜 필요한가

**개발 이력이 쌓이면 두 가지가 깨진다.** 배포 프로젝트 Project_A 실측(2026-09-08) 기준 `docs/develop-history/` 는 **214건 · 796KB** 다.

**하나 — 읽는 비용.** 아침루틴 4단계가 최근 10건을 읽는데 **42.6KB(약 16K 토큰)** 다. 이건 한 번 읽고 끝이 아니라 **그 세션의 모든 턴에 프리픽스로 다시 실린다.**

**둘 — 보류가 사라진다. 이쪽이 더 심각하다.** 보류는 각 DH 문서 안에 흩어져 있고, **모아 보는 곳이 없다.** 최근 10건이라는 창이 유일한 수집 수단이므로, **창 밖으로 밀려난 보류는 아무도 모르게 증발한다.**

`document-convention` 의 취소선 규칙은 *처리한 것이 계속 뜨는 것*은 막지만 ***안 처리한 것이 안 뜨는 것***은 못 막는다. 후자가 더 위험하다.

**work-log 는 이 둘을 한 파일로 해결한다.** 아침 읽기가 16K → 약 9K 로 줄고(work-log 7.5K + DH 최신 1건 1.6K), 열린 보류가 한곳에 모인다.

## 담당 범위

| 담당한다 | 담당하지 않는다 |
|---|---|
| 한 줄의 **형식**과 추가 규칙 | 문서 위치·명명·링크 문법 → `document-convention` |
| **마무리 줄(`✅`) 판별**과 DH 링크 부착 | DH·PLAN 문서의 **내용 형식** → `document-convention` |
| `## 열린 보류` **현황판** 유지 | 보류의 **원본 기록**과 취소선 → `document-convention` |
| **아카이브 분리** 기준과 절차 | **언제** 읽고 **언제** 갱신하나 → `session-routine` |
| 충돌 시 처리 | 소스 파일 편집 → `code-convention` |

### 충돌 검사

| 겹침 | 판정 | 근거 |
|---|---|---|
| `document-convention` §1 **위치와 명명** | **포인터 + 행 추가** | 위치의 단일 진실원은 그쪽이다. `docs/work-log/` 를 표에 추가하되 **「형식과 갱신 규칙은 `work-log` 스킬」이라는 포인터를 함께 적는다** → D24 |
| `document-convention` §1 **「작업 하나 = 문서 하나. 누적하지 않는다」** | **규칙 대상 한정** | 예외 목록을 만들지 않는다. 예외는 반드시 늘고, 늘면 매 문서마다 *"내 경우도 예외인가"* 판정이 생긴다. **규칙 문장을 *"기록 문서(계획 · 개발 이력)는"* 으로 한정**하면 work-log 는 애초에 사정권 밖이다 |
| `document-convention` §1 **폴더 README 규칙** | **준수** | 초안은 README 가 내용 본문이 되어 충돌했다. 아카이브가 생겨 파일이 여러 개가 되면서 **폴더 + 설명 전용 README** 형태가 규칙에 그대로 맞는다 → D14 정정 |
| `document-convention` §2 **링크 문법** | **포인터** | `[DH:slug](경로)` 형식·앵커 금지·절 참조 방식 전부 그쪽이 원본 |
| `document-convention` §3 **취소선 근거 문장** | **문장 교체** | 근거가 *"최근 10건 창 안에 있는 동안 매일 아침 브리핑에 뜬다"* 인데, **그 창을 없애는 것이 이 설계다.** 근거가 거짓이 된다 → D21 |
| `document-convention` §3 **「하지 말 것」 — 처리한 보류를 행째로 지우기** | **예외 명시** | work-log 규칙이 정면으로 반대다. work-log 를 만지는 것은 `.md` 편집이라 `document-convention` 이 **확정적으로 함께 떠 있으므로**, 예외를 §1 에만 두면 반대 지시가 그대로 남는다 → D22 |
| `session-routine` 아침 4·5단계 | **분리 + 변경** | 그쪽은 **언제 읽나**, 이쪽은 **무엇이 적혀 있나**. 읽기 대상을 **DH 10건 → work-log + DH 최신 1건**으로 변경 |
| `session-routine` 마무리 4단계 | **분리 + 변경** | **work-log 갱신**을 추가한다 (마무리 줄 + 새 보류 + 해소 보류 줄 삭제 + 아카이브 검사) |
| `session-routine` **머지 충돌 절** | **예외 명시** | *"개발 이력은 매번 새 파일이라 충돌 여지가 거의 없다"* 는 **파일이 매번 다르기 때문**에 성립한다. work-log 는 단일 파일이라 그 전제를 깬다 → D17 |
| `skill-pipeline` §6 **문서 배치 표** | **행 추가** | **AI_Develop 자체의 문서 위치 진실원은 `document-convention` 이 아니라 여기다.** §6 에 행이 없으면 이 저장소에 `docs/work-log/` 를 둘 근거가 없고, **파이프라인 ③ 테스트를 할 수 없다** → D23 |

**변경이 필요한 기존 스킬이 셋이다** — `document-convention`(§1 · §3) · `session-routine`(4단계 둘 + 충돌 절) · `skill-pipeline`(§6). 이 스킬 단독으로 완결되지 않는다.

**`document-convention` §3 의 DH 문서 *형식*(절 구조 · 보류 표)은 건드리지 않는다.** D13 의 단방향 규칙이 그것을 구조적으로 막는다.

| **D35** | **D22 의 `document-convention` 예외 문구에 조건을 함께 박는다** | *"work-log 는 행 삭제 예외"* 로만 쓰면 **무조건 허용**이 되어 **D26 이 그 자리에서 무력화된다.** work-log 를 만지면 `document-convention` 이 확정적으로 함께 떠 있고, **두 문서가 다른 말을 하면 눈앞의 것이 이긴다** |
| **D36** | **`description` 을 다시 쓴다** (D30 정정) | **길이는 문제가 아니었다** — 약 120자로 우리 5종 평균(180자) 이하이고, 6종이 되어도 평균은 오히려 내려간다. 문제는 셋이다. ① **마무리루틴 축을 문장 맨 끝에 뒀다** — `skill-pipeline` §4.4 가 *"잘리는 것은 항상 뒤다"* 라고 못 박은 바로 그 자리에, 중요하다며 추가한 것을 놓았다 ② **시점 조건은 작동하지 않는다** — *"마무리루틴의 개발 이력 작성 직후"* 는 스킬 선택 시점에 참이 아니다. 실제로 작동하는 것은 **`"마무리루틴"` 이라는 단어가 목록에 있다는 사실**이므로 그 단어가 앞쪽에 있어야 한다 ③ **발화에 동사가 없어** *"어디까지 했는지 알려줘"* 같은 **읽기 질문까지 잡는다.** 경로도 파일이 아니라 **폴더(`docs/work-log/`)** 로 써야 아카이브 파일이 함께 잡힌다.<br>**확정 문구:**<br>`docs/work-log/ 편집 또는 마무리루틴·"작업 로그"·"작업기록"·"작업 남겨줘"·"어디까지 했는지 남겨줘" 언급 시 로드한다. 작업 로그의 줄 형식과 갱신·보류 해소·아카이브 규칙의 단일 진실원.` |
| **D37** | **보류 「이관 누락」 검사를 추가한다 — DH 최신 1건의 보류 표에 취소선 없는 행이 있는데 work-log 에 대응 줄이 없으면 이관 누락** | **D26 · D29 는 「해소」만 본다. 「이관」은 아무 겹도 검사하지 않는다.** DH 에는 적혔는데 work-log `## 열린 보류` 에 안 올라간 보류는 **이 설계가 애초에 막겠다고 한 「증발」을 그대로 겪는다.** D16 으로 그 문서를 이미 읽고 있어 **추가 비용이 0** 이다 |

**D24 의 「네 겹」 계산도 정정한다.** `description` 의 마무리루틴 축은 **시점 조건으로 작동하지 않으므로 로드 보장으로 세지 않는다.** 겹②가 실제로 잡는 것은 **파일 축과 발화 축 둘**이고, 마무리루틴 축의 실질 보장은 `description` 이 아니라 **`session-routine` 마무리 4단계 본문의 호출 한 줄**이다.

**`session-routine` §0 에 한 줄이 더 필요하다** — *"작업 기록만 남기는 발화는 루틴이 아니다."* *"오늘 작업 남겨줘"* 가 §0 표의 *"오늘 마무리"* 와 어휘가 겹쳐 **매번 되묻게 되는데**, work-log 의 설계 의도는 *"수시로, 마찰 없이"* 다. 마찰이 반복되면 §0.1 이 스스로 경고한 대로 **확인을 생략하는 쪽으로 흐른다.**

### 진입점에 올릴 파국 방지 룰

> **`docs/work-log/work-log.md` 는 파일을 통째로 다시 쓰지 않는다.**

> **두 번 정정됐다.** 이 한 줄의 이력이 곧 「안전망을 어떻게 쓰면 안 되는가」의 사례다.
>
> | 판 | 문구 | 무엇이 잘못됐나 |
> |---|---|---|
> | 초안 | *"줄 단위로만 **추가**한다"* | **안전망이 필수 동작을 금지했다** — 보류 줄 삭제와 아카이브 이동이 막힌다 → D27 |
> | 2판 | *"줄 단위로만 **변경**한다"* | **안전망이 위험 동작을 허가했다** — 삭제의 조건(취소선 성공 후)은 `SKILL.md` 에만 있는데, 진입점 룰이 존재하는 이유가 바로 **스킬이 안 뜬 상태**다. 그 상태에서 *"변경은 허용이구나"* 로 읽고 보류 줄을 지우면 **D26 이 막으려던 무증상 실패를 안전망이 허가**한다 → D31 |
> | **현재** | *"파일을 통째로 다시 쓰지 않는다"* | **금지 한 문장.** 허용을 적지 않는다 |
>
> **원인은 안전망에 허용 범위를 적어 넣은 것이다.** 금지 대상이 「통째 재작성」 하나뿐이면 허용을 나열할 이유가 없고, 나열하는 순간 그 목록이 **조건 없는 허가**가 된다. 허용 범위(추가·삭제·이동)와 조건(취소선 성공 후)은 `SKILL.md` 로 내린다.
>
> **부수 효과 하나** — `session-routine` 의 *"문구가 어긋나면 **진입점 쪽이 맞다**"* 라는 판정 규칙이 있어서, 2판 상태에서는 **아카이브(여러 줄 이동)가 금지 쪽으로 떨어졌다.** `SKILL.md` 에 아무리 예외를 써도 그 규칙을 못 이긴다. 금지 한 문장으로 좁히면 아카이브는 통째 재작성이 아니므로 애초에 부딪히지 않는다.

**이것만 올린다.** 통째 재작성이 **유일하게 회복 불가능한 사고**이기 때문이다 — `## 최근 작업` 이 날아가는 것은 D20 논리대로 손실이 아니지만(DH 원본이 있다), **`## 열린 보류` 는 원본이 214건에 흩어져 있고 「어느 것이 아직 열려 있는지」는 work-log 에만 있다.** 복구하려면 214건을 다시 훑어야 한다.

진입점의 **테스트 로그 블록 삭제 전 범위 보고**와 같은 종류다 — 범위 계산이 틀리면 정상 내용이 함께 지워지는데 마커가 없다.
