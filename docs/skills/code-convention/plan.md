## 이 문서가 지금 생긴 이유

**이 스킬만 설계 문서가 없었다.** 2026-08-19 에 `Origin_AISkills` 의 `code-architecture-rules`(UE5) 를 이식해 만든 첫 산출물이라, **파이프라인 ①의 「설계 대화 → 플랜 문서」를 거치지 않고** 번역 작업으로 들어왔다.

그동안은 문제가 없었다. 이식한 내용을 그대로 유지만 했기 때문이다. **이번에 처음으로 없던 규칙을 추가**하면서 판정이 여러 개 생겼고, 근거를 남길 곳이 필요해졌다.

**소급해서 전부 적지 않는다.** 이 문서는 **Part D 부터** 시작한다. 기존 Part A·B·C 의 근거는 이식 원본(`Origin_AISkills` 의 `code-architecture-rules`)과 `SKILL.md` 맨 아래 출처 주석뿐이며, **그 이식에 대한 개발 이력 문서는 남아 있지 않다.**

## Part D 는 무엇을 담나

**테스트 로그를 심는 것부터 지우는 것까지 한 덩어리로.**

| 절 | 내용 |
|---|---|
| Log-First | 추측 수정 대신 로그를 먼저 심는 디버깅 루프 |
| 심기 전 판정 | *"원인을 찾으면 없어질 로그인가, 계속 보실 로그인가"* |
| 마커 2중화 | 로그 문자열 안 + 주석. 목적이 달라 하나로는 반쪽 |
| 형식 3종 | 라인 · 블록 · 주석 |
| 제거 절차 | 검색 → 범위 보고 → 삭제 → 찌꺼기 정리 |
| 남기기로 할 때 | 마커를 떼고, 출시 빌드에 나간다는 것을 알린다 |

### 왜 Part A·B 가 아니라 Part D 인가

| 안 | 왜 아닌가 |
|---|---|
| Part A 에 원칙 4 | Part A 는 *"구조를 어디에 두는가"* 다. 로그는 구조가 아니다 |
| Part B 에 §7 | Part B 는 *"기존 코드를 어떻게 건드리는가"* 이고 **"어떤 층도 무효화할 수 없다"** 는 선언이 붙어 있다. 성격이 다른 것을 끼우면 그 선언의 사정거리가 흐려진다 |
| L2 언어 층에 분산 | **지금 상태가 그것이고, 그래서 같은 말이 C# 과 TS 에 다르게 있다.** 언어가 늘 때마다 복제된다 |

**원본도 같은 판단을 했다.** `Origin_AISkills` 는 이걸 **별도 스킬**(`debug-cheat-define-rules`)로 떼어내고 이유를 *"이 규칙은 디버그 코드를 만지는 그 순간에만 필요하다"* 라고 적어놨다. 우리는 스킬까지 나누지 않는다 — 로그를 심는 것 자체가 소스 편집이라 **이 스킬이 어차피 뜨기 때문**이다. 대신 **파트로 독립**시킨다.

## 마커 — `AITESTLOG_<컨텐츠명>`

```csharp
Debug.Log($"[AITESTLOG_Inventory] 슬롯 병합 진입: {slotId}, 수량 {count}");   // TODO: AITESTLOG_Inventory — 제거 예정 (병합 버그 수정 후)
```

**접두어와 접미가 하는 일이 다르다.**

| | 하는 일 |
|---|---|
| `AITESTLOG_` **고정** | **전수 검색.** 마무리에서 남은 것을 하나도 빠뜨리지 않는다 |
| `_<컨텐츠명>` **가변** | **선택 필터 · 선택 제거.** 런타임 로그에서 그 시스템 것만 보고, *"인벤토리 것만 지워줘"* 가 된다 |

**접미가 없으면 원래 목적이 반쪽이 된다.** 마커 2중화의 명분이 *"수천 줄에서 이번에 심은 것만 골라 본다"* 였는데, 하루에 두세 시스템을 만지면 `AITESTLOG` 하나로는 안 좁혀진다.

**접두어를 프로젝트별로 두지 않았다.** 원본은 `[XXXDEBUG]` 처럼 프로젝트마다 정하는 방식이었는데, 그러면 **마무리루틴이 검색어를 모른다.** 알려면 L4(`project-rules.md`)를 로드해야 하고, *"마무리루틴이 돌려면 code-convention 의 L4 가 먼저 떠야 한다"* 는 **스킬 간 의존**이 새로 생긴다.

## 빌드 가드를 뺀 이유 — 그리고 그 결과

**개발/테스트 빌드 구분과 치트 가드는 이번 범위 밖이다** (사용자 결정, 2026-08-25). 아직 계획 단계이고 작업 규모가 크다.

### 결과 ① — 로그 분류가 3분류가 아니라 2분류다

원래 안은 **① 임시 진단 / ② 상시 개발 / ③ 운영** 이었다. 그런데 **②를 ③과 가르는 유일한 기준이 빌드 가드**다. 가드가 없으면 둘 다 출시까지 나가는 로그라 **구분할 실익이 없다.**

그래서 지금은 **마커 붙는 것 / 안 붙는 것** 2분류다. 빌드 가드 작업이 시작될 때 ②를 갈라내며, **그때 갈라도 늦지 않다** — 그 시점에 어차피 기존 로그를 전수로 훑어야 한다.

### 결과 ② — 「기본값은 임시」의 근거가 바뀐다

원래 근거는 *"상시로 잘못 심으면 가드 없이 출시 빌드에 남는다"* 였다. **가드가 없으면 상시 로그는 원래 다 나가므로** 그 논리가 서지 않는다.

대신 더 단순한 것이 남고, 이쪽이 오히려 강하다.

> **마커를 안 붙이면 아무도 안 지운다.** 붙였다가 남기기로 하면 떼면 되지만, 안 붙였다가 나중에 찾으려면 못 찾는다.

### 결과 ③ — 「남기기로 할 때」에서 가드 얘기를 뺀다

`session-routine` §4.5 는 *"빌드 가드가 필요하다는 것을 알린다"* 였다. 가드 규칙이 없는 상태에서 그렇게 알리면 **없는 절차를 가리키게 된다.**

대신 **그 로그가 출시 빌드에도 출력된다는 사실만** 알린다. 가드를 붙이라고는 하지 않는다.

## 결정 이력

| # | 결정 | 근거 |
|---|---|---|
| 1 | **로그 관련 전부를 이 스킬로** — 심기도 지우기도 | 둘 다 **소스 파일 편집**이다. 심는 쪽과 지우는 쪽을 다른 스킬에 두면 **마커 형식이 바뀔 때 한쪽만 낡는다** (사용자 결정) |
| 2 | **Part D 신설** — Part A·B 에 끼우지 않음 | Part A 는 설계 원칙, Part B 는 변경 안전 절차이고 **"어떤 층도 무효화할 수 없다"** 선언이 붙어 있다. 성격이 다른 것을 넣으면 선언 범위가 흐려진다 |
| 3 | 마커는 **`AITESTLOG_<컨텐츠명>`** | 접두어 고정으로 전수 검색, 접미 가변으로 선택 필터·선택 제거 (사용자 결정) |
| 4 | **블록 마커에도 컨텐츠명을 붙인다** | 블록만 이름이 없으면 선택 제거가 반쪽이 된다 |
| 5 | 접두어를 **프로젝트별로 두지 않는다** | 프로젝트마다 다르면 마무리루틴이 검색어를 모른다. L4 로드 의존이 새로 생긴다 |
| 6 | **빌드 가드는 범위 밖** | 계획 단계이고 작업이 크다 (사용자 결정). 그 결과 분류가 2분류가 되고, 「기본값 임시」의 근거가 바뀐다 |
| 7 | 언어 무관 규칙을 **L2 에서 L1 으로 올린다** | 같은 말이 `lang-csharp.md` 와 `lang-typescript.md` 에 **다르게** 있었다. 언어가 늘 때마다 복제된다 |
| 8 | `description` 에 **로그·디버그 키워드 추가** | 지금 것으로는 *"로그 심어줘"* 에 안 걸린다. **Part D 를 통째로 못 쓰게 되는 조용한 실패 지점**이다 |
