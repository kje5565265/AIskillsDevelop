## 이 스킬의 경계 — 레포 안 `.md` 파일만 본다

**대상은 저장소에 커밋되는 마크다운 문서다.** 그 밖의 기록 수단은 이 스킬이 다루지 않는다.

| 담당한다 | 담당하지 않는다 |
|---|---|
| 문서 **위치·명명** | 코드를 어떻게 쓰는가 → `code-convention` |
| 문서 간 **링크 규칙** | **언제** 문서를 쓰는가 → `session-routine` |
| 개발 이력 문서 **포맷** | **memory 기록** (포맷·시점 전부) → `session-routine` |
| 계획 문서 **형식** | 문서-only **검증 실행 절차** → `session-routine` |
| | 문서를 커밋하는 절차 → `git-procedure` |

**포맷을 정하는 것과 언제 쓸지 결정하는 것은 다른 일이다.** 이 스킬은 앞쪽만 한다.

**문서 언어(한국어/영어)는 이 스킬이 정하지 않는다.** 프로젝트 운영 문서(`CLAUDE.md` 등)에서 정한다. 나중에 이 스킬 전용 프로젝트 레퍼런스가 생기면 그쪽으로 옮긴다.

> **`code-convention` 의 `project-rules.md` 를 문서 언어의 암묵적 출처로 쓰지 않는다.** 그 파일은 코드 스킬의 L4 레퍼런스다. 문서 언어를 정하려고 그걸 읽게 하면 **문서 스킬이 코드 스킬 레퍼런스에 기대는** 숨은 의존이 생긴다.

### 기존 스킬과의 충돌 검사

| 겹침 | 판정 | 근거 |
|---|---|---|
| `code-convention` §0 — *"순수 문서(`.md`) 편집"* 이 **제외**로만 적혀 있음 | **포인터 보강 필요** | 지금은 막다른 길이다. *"문서 편집은 내 소관이 아니다"* 라고만 하고 어디로 가라고는 안 한다. **§0 표를 `document-convention` 을 가리키도록 갱신해야 한다** — 안 하면 문서 편집 시 아무 스킬도 안 뜬다 |
| `code-convention` Part B §4(영향 분석)·§5(구조/정책 분리) | **포인터** | 문서 작성처럼 보이나 **발동 시점이 코드 변경 순간**이고 어겼을 때 망가지는 것이 코드다 |
| `lang-*.md` 주석 규칙 | **분리** | 주석은 **소스 파일 안**이다. 이 스킬은 `.md` 만 본다 |
| `session-routine` 의 memory 기록 | **이관** | 통째로 `session-routine` 이 가져갔다 |
| AI_Develop 저장소 문서 배치 — 계획 문서를 `docs/skills/<스킬명>/plan.md` 에 둔다 | **분리** | 이 스킬의 `docs/plan/` 은 **배포 대상 프로젝트**의 기능 계획용이다. AI_Develop 의 산출물은 스킬이라 계획의 대상이 다르고, 폴더가 이미 구분자라 날짜도 안 붙인다. **AI_Develop 에는 `docs/plan/` 을 두지 않으며 그 선언은 `skill-pipeline` §6 에 있다** (2026-08-25 · 진입점 §6 이 그 스킬로 이관됨) |

> Part B §4·§5 겹침은 2026-08-20 시점에 미해결로 남았던 쟁점. **1·2회차 교차 검증 양쪽에서 「포인터」로 확인, 종결.**

## 1. 기록의 진실원은 레포 안 문서다

작업 기록의 단일 진실원은 **`docs/develop-history/` 의 문서**다. 다른 곳에 요약본이 있더라도 그것은 **인덱스이지 진실원이 아니며**, 내용이 갈리면 문서가 이긴다.

## 2. 문서 위치와 명명

| 성격 | 위치 | 언제 쓰나 |
|---|---|---|
| 계획 문서 | `docs/plan/YYYY-MM-DD-<slug>.md` | 개발 **시작 전** |
| 개발 이력 | `docs/develop-history/YYYY-MM-DD-<slug>.md` | 개발 **완료 후** |

**작업 하나 = 문서 하나.** 기존 문서에 누적하지 않고 **매번 새로 만든다.** 쓰는 시점에 *"기존 문서에 합칠까?"* 를 판단하면 실패 지점이 늘고, 그 판단은 나중에 여러 건을 함께 볼 때가 더 정확하다.

> **병합·정리는 어느 스킬도 맡지 않는다** (2026-08-25 정정). 처음에는 `session-routine` 으로 넘겼으나 **그쪽이 반려**했다 — 사용자가 원할 때 하는 일이지 루틴으로 굳힐 성질이 아니다. 이 스킬이 정하는 것은 **「쓸 때 합치지 않는다」까지**다.

> **예외 — 스킬 개발 문서.** AI_Develop 처럼 스킬을 개발하는 저장소는 `docs/skills/<스킬명>/` 아래에 둔다 (§5). 일반 게임 프로젝트는 스킬을 개발하지 않으므로 위 표대로 간다.

**폴더명은 점으로 시작하지 않는다.** 옵시디언은 dotfolder 를 인덱싱 자체를 하지 않아 문서가 보이지 않는다 (2026-08-21 실측 — `.docs` 로 만들었다가 되돌림). 표시 옵션으로 켤 수 있는 것이 아니다.

### slug 규칙

- **2~4 단어, 30자 이내** kebab-case
- **영문 소문자·숫자·하이픈만.** 한글 slug 금지 — Windows 에서 파일명은 동작하지만 셸로 텍스트 처리할 때 인코딩 사고가 난다 (2026-08-21 실측: UTF-8 파일을 ANSI 로 읽어 문서 하나가 통째로 깨짐)
- 한 문서가 여러 주제를 다뤄도 **대표 주제 하나만** slug 으로 쓴다
- **같은 네임스페이스 안에서 유니크하다.** `DH:` 끼리, `PLAN:` 끼리 겹치지 않으면 된다
  - **`PLAN:` 과 `DH:` 는 같은 slug 을 공유하는 것이 정상이다.** 계획을 쓰고(`PLAN:character-dash`) 개발한 뒤 이력을 남기면(`DH:character-dash`) 짝이 한눈에 보인다. prefix 가 둘을 구분한다
  - 충돌은 우연적(같은 주제 동시 작업)이라 드물고, 겹치면 **머지에서 파일명 충돌로 드러난다** → 더 구체적인 slug 으로 분기
  - 같은 날 같은 slug 이 불가피하면 `-2` · `-3` 접미

> slug 이 안 좁혀진다는 것은 **문서가 한 주제가 아니라는 신호**다. 그때는 문서를 둘로 나눈다.

### 인용 키

`DH:<slug>` / `PLAN:<slug>`. **번호는 쓰지 않는다** — 중앙 카운터 × 분산 작업 구조라 분기에서 충돌이 필연이고, 재번호 시 참조가 깨진다.

인용 키에 날짜를 넣지 않는 대신 **slug 유니크로 충돌을 막는다.** 키가 짧아야 본문에 자연스럽게 녹는다.

## 3. 문서 간 링크 규칙

- **표준 마크다운 링크만 쓴다** — `[표시텍스트](./상대경로.md)`. 옵시디언과 VS Code 양쪽에서 동작한다
- **`[[wiki-link]]` 금지** — 옵시디언 전용 문법이라 VS Code·GitHub 에서 클릭이 안 된다
- **섹션 앵커(`#heading`) 금지** — 옵시디언과 GitHub 의 슬러그 생성 규칙이 달라 한쪽에서 깨진다

**인용 형식** — 링크 텍스트는 인용 키, 링크 대상은 **실제 파일 경로**다.

```markdown
콤보 리셋 전이는 [DH:combo-reset](../develop-history/2026-06-18-combo-reset.md) 참조
```

### 절을 가리켜야 할 때

앵커를 금지했으므로 **절 번호가 앵커를 대신한다.** 그래서 두 가지를 지킨다.

> **모든 문서에 절 번호를 붙이라는 뜻이 아니다.** 짧은 문서는 번호 없이 쓴다. 아래는 **절을 참조할 일이 있어 번호를 붙인 문서**에만 적용된다.

- **한번 붙인 절 번호는 재배열하지 않는다.** `§3` 은 문서가 개정돼도 `§3` 이다. 절을 추가할 때는 뒤에 붙이거나 `§3.1` 로 파생시킨다
- 절을 가리킬 때는 **번호를 링크 텍스트에 포함**한다 — `[DH:combo-reset §4](../develop-history/2026-06-18-combo-reset.md)`. 클릭하면 문서가 열리고, 절은 `Ctrl+F` 로 찾는다

> 번호를 불변으로 두는 비용이 앵커를 양쪽 도구에서 검증하는 비용보다 싸다.

## 4. 개발 이력 문서 포맷

```markdown
---
id: DH:<slug>
title: <제목>
date: YYYY-MM-DD
---

# <제목>

| 날짜 | 작성자 | 내용 |
|------|--------|------|
| YYYY-MM-DD | <git user> | 최초 작성 |

## 한 일
- 행위 + 의미 (파일·줄 수 나열 금지 — diff 에 있다)

## 판단과 근거
- 왜 그렇게 했나. 대안을 버린 이유

## 검증
- 무엇으로 확인했는가 (명령 · 기준 · 결과)
- 확인 못 한 것은 여기 적지 말고 아래 보류로

## 보류 — 나중에 할 것
| 항목 | 왜 미뤘나 | 재개 조건 |
|---|---|---|
| 없음 | — | — |

## 남은 것 / 다음 스텝
```

**작성자 칸은 세션 컨텍스트의 `Git user:` 값을 그대로 쓴다.** 예시를 따라 쓰지 않는다.

### `## 보류` 절

**"나중에 하자"가 여기 적히지 않으면 증발한다.** 이 절이 이 포맷의 핵심이다.

- **왜 미뤘는지와 어떤 조건이면 재개하는지를 함께** 적는다. 조건이 없으면 나중에 판단할 근거가 없다
- **보류가 없으면 `| 없음 | — | — |` 행을 남긴다.** 절을 지우거나 헤더만 두지 않는다 — 읽는 쪽이 "보류 없음"과 "절을 안 썼음"을 구분하지 못한다
- **보류 항목을 하나라도 추가하면 `| 없음 | — | — |` 행은 삭제한다.** 둘이 함께 남으면 "보류 없음"과 "보류 있음"이 동시에 표기된다
- 표는 **사람과 에이전트가 읽는 것**이지 기계 파싱 대상이 아니다. 셀 안에 자연어를 자유롭게 쓴다

## 5. 계획 문서 형식

**`작업 → 검증` 형식은 실행 계획에만 적용한다.**

```
1. [작업] → 검증: [확인 명령/기준]
```

- **각 단계마다 검증 방법을 명시**한다. 검증이 붙는 형식이라 **검증 없는 완료 주장**이 구조적으로 막힌다
- **비싼 검증은 마지막에 통합**한다 (패키징 빌드 30분+, 풀 플레이 테스트 5분+)

**절차를 지시하지 않는 문서는 자유 서술이다** — 리뷰 · 브리핑 · 회고 · 설계 설명 · 사양서 · 개발 이력. 이들에 단계별 검증을 요구하면 형식만 남고 내용이 빈다.

### 질문 우선

- 사용자 미명시 가정이 계획에 **1건 이상** 들어가면 질문으로 분리한다. 0건이면 면제
- 1줄 수정 · 오타 · 로그 추가 · 명시된 컴파일 에러 수정 같은 **자명한 작업은 질문 면제**
- **답을 알면서 승인만 받으려는 안전빵 질문 금지**

## 6. 문서 검증 — 무엇을 확인하는가

문서를 고친 뒤 확인할 것은 넷이다. **명령은 환경마다 다르므로 고정하지 않는다** — `rg` 가 없는 환경이 있고, PowerShell 과 Bash 의 정규식 이스케이프가 다르다.

| 확인 | 왜 |
|---|---|
| **갱신 누락된 참조** | 경로·이름을 바꾸면 다른 문서가 옛 값을 가리킨다 |
| **상대 링크 유효성** | 링크 대상 파일이 실제로 존재하는가 |
| **stale 경로** | 지운 문서를 아직 가리키는 곳이 있는가 |
| **slug 중복** | 인용 키에 날짜가 없으므로 slug 이 겹치면 참조가 애매해진다 (§2) |

> **명령을 고정하지 않는 것이 확인을 면제한다는 뜻은 아니다.** 그 환경에서 **쓸 수 있는 도구로 반드시 확인한다.** 확인하지 못했으면 확인했다고 쓰지 않는다.

```bash
# 예시 (Git Bash). 환경에 맞게 바꾼다
rg "옮긴-경로|바뀐-이름"
rg -o "\]\(\./[^)]+\)" docs
```

> **검증을 언제 실행하는지는 `session-routine` 소관이다.** 이 절은 *무엇을 확인하는가*만 정한다.

| 4 | `code-convention` Part B §4·§5 는 **포인터** | 발동 시점이 코드 변경 순간이고 어겼을 때 망가지는 것이 코드 |
| 5 | 인용 키에 **번호를 쓰지 않는다** (`DH:<slug>`) | 중앙 카운터 × 분산 작업이라 분기 충돌이 필연 |
| 6 | slug **전 문서 유니크 + 영문 소문자** | 키에 날짜가 없어 중복 시 인용이 애매해짐. 한글은 인코딩 사고 (실측) |
| 7 | 앵커 금지 + **절 번호 불변** | 앵커는 도구별 슬러그가 다름. 번호를 고정하는 쪽이 검증 비용 0 |
| 8 | `## 보류` 빈 상태를 **`| 없음 | — | — |`** 로 표기 | "보류 없음"과 "절을 안 씀"을 구분해야 읽는 쪽이 안정적 |
| 9 | `작업 → 검증` 은 **실행 계획에만** | 설명·회고·브리핑에 강제하면 형식만 남고 내용이 빈다 |
| 10 | **memory 규약을 `session-routine` 으로 이관** | memory 는 레포 파일이 아니고, 시점이 하나뿐이며, Claude 전용이라 3종 공용 스킬에 안 맞는다 |
| 11 | **문서 언어를 정하지 않는다** | `lang-*.md` 가 주석 언어를 `project-rules.md` 소관으로 뒀다. 문서 언어도 같은 곳이어야 갈리지 않는다 |
| 12 | 검증은 **"무엇을 확인하는가"만** 고정, 명령은 예시 | `rg` 부재·셸별 이스케이프 차이로 명령 고정이 깨진다. 단 **확인 의무는 면제되지 않는다** |
| 13 | **문서 언어 출처에서 `project-rules.md` 를 뺀다** | 그 파일은 `code-convention` 의 L4 다. 문서 스킬이 코드 스킬 레퍼런스에 기대는 **숨은 의존**이 생긴다 |
| 14 | slug 유니크는 **네임스페이스 안에서만** | `PLAN:` → 개발 → `DH:` 흐름에서 **같은 slug 을 공유해야 짝이 보인다**. 원본(`document-rules` §1.3)도 *"전 DH 문서에서 유니크"* 로 네임스페이스 한정. 3회차 Codex 권고("prefix 넘어서")를 되돌림 |
| 17 | **작업마다 신규 문서**를 만든다 (기존 문서에 누적하지 않음) | 쓰는 시점에 *"합칠까?"* 판단을 넣으면 마무리에 실패 지점이 는다. 원본도 이 방식으로 **~110건 축적 실적**이 있다. ~~병합·정리는 `session-routine` 소관~~ → **어느 스킬도 맡지 않는다** (2026-08-25 정정) |
| 18 | 발동 기준은 **`.md` 를 건드리는가** — 오탈자 한 글자도 포함 | *"구조를 안 건드리는 편집은 제외"* 를 넣었다가 되돌렸다. **그 판정은 편집을 해봐야 알 수 있다** — 오타를 고치다 링크를 건드리고, 한 줄 다듬다 절을 추가한다. 시작 시점에 판정 불가한 기준은 곧 실패 지점이다. `code-convention` 과 **같은 축**(대상으로 판정)이어야 헷갈리지 않는다 |
| 15 | description 은 **생성 + 갱신** 둘 다 잡는다 | 생성만 잡으면 링크 수정·slug 변경·보류 갱신에서 안 뜬다 |
| 16 | 절 번호 불변은 **번호를 붙인 문서에만** 적용 | 전 문서에 번호를 강제하는 것으로 읽히면 짧은 문서가 무거워진다 |

## 10. 구현 시 함께 해야 하는 것

| # | 작업 | 왜 |
|---|---|---|
| 1 | **`code-convention` §0 표 갱신** — *"순수 문서 편집 → `document-convention`"* | 안 하면 문서 편집 시 아무 스킬도 안 뜬다. **A급** |

**description 범위** — 생성뿐 아니라 **갱신**까지 잡아야 한다.

> 문서를 **새로 만들거나**, **위치·이름·slug 을 정하거나**, **문서 링크·인용 키를 수정하거나**, **개발 이력 · 실행 계획 · 보류 항목을 작성·갱신**할 때 사용한다.

README 오탈자 같은 소소한 편집까지 잡지는 않으면서, **링크 수정 · slug 변경 · 보류 갱신** 처럼 이 스킬이 꼭 필요한 유지보수는 놓치지 않는 폭이다.
