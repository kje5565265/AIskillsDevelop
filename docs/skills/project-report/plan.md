## 1. 왜 만드나

**대표가 여러 프로젝트가 지금 어디까지 왔는지 알고 싶어 한다.** 그걸 알려면 사람이 각 저장소 기록을 열어봐야 하고, 커밋 메시지는 개발 용어라 그대로 전달할 수 없다.

**커밋 메시지 품질은 이미 충분했다** (2026-09-28 실측) — 네 프로젝트 모두 한국어 · 기능 단위로 적혀 있었다. **없는 것은 수집과 번역이다.** 이 스킬은 그 둘을 한다.

## 2. 담당 범위 — 기존 스킬과의 충돌 판정

| 겹침 | 판정 | 근거 |
|---|---|---|
| **`work-log` 의 트리거 「작업기록」** | **분리 — 문구를 가른다** | 최초 발화 *"작업기록 정리해서 보고해"* 가 `work-log` 트리거와 정확히 겹쳤다. 대상이 다르다 — `work-log` 는 **이 저장소 안의 작업을 적는 것**, 이 스킬은 **다른 저장소들의 커밋을 읽는 것**. 부르는 길은 결정 11 |
| **`git-procedure` 의 받기** | **분리** | 그쪽은 **내 작업 저장소에 받아서 합치는 것**, 이 스킬은 **자기 복제본에서 fetch 만** 한다. `git-procedure` 발동 조건(commit · pull · push 실행)에도 걸리지 않는다 |
| **`session-routine` 아침 브리핑** | **분리** | 그쪽은 **지금 저장소**의 받기와 작업 로그 브리핑, 이 스킬은 **다른 여러 저장소**의 현황. 아침루틴에 넣으면 무거워지고, 대표 보고는 매일 필요한 것이 아니다 |
| 진입점 **「실 프로젝트는 읽기만」** (`skill-pipeline` §5.1) | **충돌 없음** | 작업 저장소를 아예 쓰지 않고 **보고 전용 복제본**만 쓴다 (결정 24) |
| **「올려줘」 어휘** — `git-procedure` · `session-routine` 트리거 | **본문에 경계 명시** | *"현황 정리해서 올려줘"* 의 「올려」는 메신저 게시다. **게시 뜻이면 보고서만 만들고 커밋 · 푸시 · 게시를 하지 않는다** → 결정 11 |

| 36 | **보고서 구성** — ① 「확인해 보실 것」을 한눈에 바로 아래로 ② 프로젝트마다 굵은 핵심 2~3개 + 분류별 한 줄의 「그 밖」 ③ 기록 커밋 · 개발 도구는 맨 아래 한 줄 ④ 본문에 브랜치 원래 이름을 쓰지 않는다 ⑤ 플랫폼으로 판정되지 않는 브랜치가 거의 같은 내용이면 하나로 합친다 | 첫 보고서를 자체 평가해 사용자가 승인 (2026-09-29). 대표에게 가장 중요한 주의 신호가 맨 끝에 있었고, 한 프로젝트가 1쪽 반을 브랜치 설명과 함께 차지했다. ⑤는 **결정 22 의 범위를 플랫폼 라인으로 좁힌다** — 작업 가지들은 출시 라인이 아니다 |
| 37 | **추적할 프로젝트는 PC 로컬 설정에 둔다** — `~/.project-report/config.json`(환경 변수 `PROJECT_REPORT_HOME` 으로 변경). 저장소에는 **가짜 예시(`config.example.json`)만** 둔다. 기준점 · 복제본 · 보고서는 설정의 `baseDir`, 없으면 설정과 같은 폴더 | **사용자 요청 (2026-10-06)** — *"이 스킬을 어느 회사에서든지 사용할 수 있어야"*. 조직을 옮겨도 스킬은 그대로 두고 PC 에서 프로젝트만 새로 등록한다. **결정 28 을 뒤집는다.** ✗ 스킬 폴더 안 `config.local.json`(커밋 제외) — `.claude` · `.agents` 두 사본 중 어디에 둘지 갈리고, 스킬을 다시 복사하면 사라진다. 사용자가 사용자 폴더를 골랐다 |
| 38 | **등록은 명령으로 한다** — `init` · `add` · `map` · `unmap` · `remove` · `list`. `add` 는 **등록 전에 이 PC 의 계정으로 저장소가 읽히는지 확인**하고 안 읽히면 등록하지 않는다. **브랜치 → 플랫폼은 추측하지 않고 묻는다** | 손으로 JSON 을 고치면 형식 · 중복 · key 규칙이 깨진다. 안 읽히는 주소가 등록되면 보고 때마다 fetch 실패가 뜬다. 틀린 플랫폼 대응은 **대표에게 틀린 출시 정보**로 간다 |
| 39 | **이 스킬과 plan 을 개인(공개) 저장소에 둔다.** 조직 정보는 가명으로 바꾸고, 실측 수치는 설계 근거라 남긴다 | 사용자 요청 (2026-10-06). 결정 37 로 스킬에 조직 정보가 남지 않게 됐다. **결정 21 을 뒤집는다** |

> **결정 37 구현 중 실측 (2026-10-06)** — 처음에는 예시 설정에 `baseDir: "~/.project-report"` 를 넣었는데, `init` 이 그 값을 그대로 복사해 **설정 위치를 바꿔도 기록이 사용자 폴더로 갔다.** 예시에서 `baseDir` 을 빼고, `init` 은 `--base-dir` 를 줬을 때만 넣게 했다. **「기본값」은 예시 파일이 아니라 코드가 정한다.**
